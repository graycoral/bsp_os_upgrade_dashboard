# 제품 내부 BSP 역할 지침

실제 Linux BSP 프로젝트에 설치할 역할 템플릿의 기준이다. 대시보드 저장소의 CLAUDE.md를 대상 BSP 지침으로 그대로 복사하지 않는다. 실제 경로·도구 지원 확인 후 역할별 파일로 배포하고 버전을 기록한다.

## 모든 역할의 공통 계약

[에이전트 상태·결과 보고 계약](../design/AGENT_STATUS_CONTRACT.md)을 함께 전달한다. 입력·출력 필드, 단계별 보고 시점, 성공/실패 예시는 그 문서만을 기준으로 하며 기존 중복 목록은 삭제했다. 아래는 각 역할의 업무 내용이다. 보고서에 작성해야 할 내용과 서버가 자동 해석하는 필드를 혼동하지 않는다.

완료 주장과 실제 증거를 분리한다. 누락된 입력을 추측해 실행하지 않는다. 현재 v1에서는 판단 필요 내용을 근거에 남기고 운영자가 등록한다. 목표 v2에서는 구조화된 역할 보고·판단 후보를 worker에 반환하고 서버가 저장한 결과를 오케스트레이터가 읽는다. 어느 역할도 DB나 Jira에 직접 상태를 쓰지 않는다. 새 계약은 아직 미구현이다.

## coordinator — 작업별 오케스트레이터

- [오케스트레이터 명세](../design/ORCHESTRATOR_SPEC.md)를 역할 지시서로 함께 전달한다. 입력은 서버의 영속 snapshot·확인된 보고이며, 출력은 구조화된 계획/재시도/전환/판단/검증 제안이다.
- 사용자 목적과 벤더 변경을 모아 최초 확인할 계획을 작성한다. 필수 분석 누락·순환 의존·미결정 영향을 명시한다. 상태 조회마다 모듈 목록을 재생성하지 않는다.
- 실패 원인과 이전 시도의 차이를 비교하고 다음 행동을 제안한다. 일반 수정 실패와 사람이 새로 결정해야 하는 문제를 구분한다. 기존 승인 범위의 정상 작업은 계속 진행시킨다.
- 실제 프로세스 배정·수정/빌드·상태 확정·Jira 전송은 서버/담당 역할에 맡긴다. 종합 검토로 별도 코드 리뷰·장비 시험·최종 사람 검토를 대체하지 않는다.
- 조정 응답에도 호출 ID·입력 기준·근거를 연결하고 미지원 동작/근거 부족을 명시한다. 모듈 결과용 outcome과 조정 호출 성공을 혼동하지 않는다.

## analyst — 요구사항 분석

- old_base/vendor_tree/new_base를 비교하여 벤더 변경의 목적과 신규 OS 반영 근거를 확인한다.
- 변경별 already_upstream / port_required / excluded 제안 / needs_decision을 기록한다. 제외는 승인 근거가 있어야 확정한다.
- 관련 파일·기능·초기화·호환성·의존 모듈·필수 시험을 제시한다. 소스는 읽기 전용이다.
- 부트로더와 무관하게 분석할 수 있으나 후속 실행 허가를 대신하지 않는다.

## designer — 이식 설계

- 확인된 요구사항을 API·인터페이스·설정·초기화·전원/부팅 영향과 수정 파일로 구체화한다.
- 선택한 방법, 대안, 호환성 위험, 검증 방법을 작성한다. 새 판단이 필요한 부분과 독립 구현 부분을 나눈다.
- 서버가 최초 확인 및 선행 조건을 통과시킨 작업만 수행한다.

## implementer — 구현

- 확인된 설계·현재 diff를 이어서 필요한 범위만 변경한다. 기존 벤더 의도나 사용자 변경을 근거 없이 제거하지 않는다.
- 구현 결과에 변경 ID, 수정 파일, revision/diff, 수행 시험, 실패 원인을 포함한다.
- 실패 시 동일 코드 재생성으로 반복하지 말고 원인과 시도 차이를 기록한다. 전환 시 현재 변경을 보존한다.
- 명시된 쓰기 경로 밖 수정, 장비 자동 플래시, 임의 Jira 전송을 하지 않는다.

## reviewer — 코드 검토

- 정확한 작성 revision을 검토한다. 요구사항 누락·벤더 변경 회귀·호환성·검증 부족을 우선 확인한다.
- 발견 항목별 근거, 영향, 수정 방향, 방지 시험을 제시한다. 직접 수정했다면 작성자 이력에 반영하고 해당 변경을 별도 리뷰 대상으로 만든다.
- 읽기 검토만 수행했다면 실행 시험 PASS를 보고하지 않는다.

## verifier — 검증 해석

- 등록된 시험 결과와 산출물 기준을 비교하고 PASS/FAIL/NOT_RUN 및 증거를 정리한다.
- 로그에 PASS라는 단어가 있다는 이유로 전체 통과 처리하지 않는다. 필수 사례와 자동 연결된 이미지/소스 기준을 확인하고 선택 정보가 제공됐으면 그 일치도 확인한다.
- 수동 장비 시험 결과를 만들어내지 않는다. 사람이 등록한 PASS/FAIL과 제공된 근거만 사용한다. 보드·수행자·근거 파일 등 선택값이 비어 있다는 이유로 결과를 거부하지 않는다.

## builder / integration — 빌드와 통합

- 등록된 프로필로 실제 빌드·회귀를 수행하고 대상 소스·종료 코드·산출물·검증 결과를 보고한다. 통합은 포함한 각 모듈의 실제 기준도 기록한다.
- 파일 쓰기 완료와 해시를 확인한 뒤 응답한다. 반환 뒤 별도 프로세스로 소스를 계속 바꾸지 않는다. 필요한 초기화는 설정된 환경에서 수행하고 임의 명령을 제안 응답에서 실행하지 않는다.

## 각 역할의 보고 인계

보고 필드와 예시는 [모듈 보고 계약 11절](../design/AGENT_STATUS_CONTRACT.md)에서 단독 관리한다. 분석은 변경별 분류, 설계는 수정·검증 계획, 구현은 실제 diff와 시도 차이, 리뷰는 정확한 revision/diff와 발견 사항, 빌드는 이미지/로그, 검증·통합은 사례별 결과를 보고한다. 실행 중 퍼센트나 완료 상태를 대화로 추측해 보고하지 않는다. 현재 연결은 v1, 향후 구조화 보고는 v2 지원 확인 후 사용한다.

## 실제 Claude 조정 역할 파일

[agent 정의](../../.claude/agents/bsp-upgrade-orchestrator.md)를 프로젝트에서 직접 사용할 수 있다. [사용 안내](../agents/CLAUDE_ORCHESTRATOR_GUIDE.md)에 입력 준비·모델 호출·응답 검사·내보내기 순서를 기록했다. 이 패키지는 조정자 역할만 제공하며 외부 analyst/designer/implementer 등의 구현이나 설치 목록을 만들어내지 않는다. 역할 보고 기준은 위 공통 계약을 그대로 따른다.


## D-42 기존 역할 파일 연결

다른 에이전트 프로젝트의 지침 폴더와 역할별 Markdown 경로를 설정할 수 있다. 내장 호출은 내용을 읽어 새 job에 고정하며 기존 파일/agent 등록을 덮어쓰지 않는다. 사용자 정의 agent의 권한/자동 배정기를 그대로 실행하지 않고 서버가 배정한 한 역할의 자료로 사용한다. 내장 코드 역할은 편집, 빌드/검증/통합은 지정 명령, 장비시험은 사람이 담당한다. 상세는 [환경 안내](../agents/ENVIRONMENT_AND_BRIDGES.md)와 [보고 계약](../design/AGENT_STATUS_CONTRACT.md)을 따른다.

## 1. 사용자 확정 요구사항

새 탭에서 다음 상위 노드를 **왼쪽에서 오른쪽으로 한 줄로 연결**한다. BackEnd 아래에 두 그룹을 형제 노드로 나열하는 형태로 바꾸지 않는다.

```text
FrontEnd(ACON) → BackEnd(bsp-os-upgrade) → 선행 IP 모듈 그룹 → 일반 IP 모듈 그룹
                                         │                  │
                                         ├─ ▶ IP A          ├─ ▶ IP C
                                         │  구현 · 60%      │  선행 대기 · 20%
                                         │  ██████░░░░      │  ██░░░░░░░░
                                         │                  │
                                         └─ ◀ IP B → 요구사항분석 → 설계 → 구현 → 검증 → Test
                                            검증 · 80%
```

IP 이름·진행률은 설명용 예시이며 운영 화면에 기본 데이터로 삽입하지 않는다.

- 각 그룹에 실제 소속 IP를 표시한다. 각 IP 클릭으로 그 IP 오른쪽의 단계 순서도를 독립적으로 접고 펼친다.
- 단계 순서는 `요구사항분석 → 설계 → 구현 → 검증 → Test`다. 2026-11-04 후속 사용자 요청으로 기존 아래 펼침을 오른쪽 가로 펼침으로 변경한다. 펼친 행의 너비만큼 그룹 공간을 확보해 다음 그룹과 겹치지 않으며, 캔버스에서 좌우 스크롤한다.
- 접힌 IP에도 현재 단계·상태, 백분율과 작은 진행 막대를 표시한다.
- 연결 정상/실행 중은 푸른색 점, 연결 끊김/중단은 빨간색 점, 시작 전은 회색 점으로 나타낸다. 연결과 실행은 서로 다른 상태이므로 문구로 구분한다.
- Archify 느낌의 노드·연결선을 사용하고 진행 중인 화살표에 방향성 있는 흐름 효과를 제공한다.
- 회사 이식을 쉽게 하도록 기능을 전용 폴더로 분리하고, 기존 앱에는 탭과 데이터 연결을 최소한으로 추가한다.

## 2. 기존 정책과 표시 의미

상위 화살표는 구성 관계와 선행 그룹의 게이트를 설명한다. 모든 단계의 직렬 실행이나 실제 네트워크 경로를 의미하지 않는다. **요구사항분석과 분석 재시도는 모든 IP에서 병렬 가능**하다. 최초 전체 분석 후 계획 확인 전에는 선행 그룹도 설계 이후 실행하지 않는다. 일반 IP의 설계 이후 단계는 선행 그룹 전체 완료 후 진행한다. [상태·실행 정책](WORKFLOW_AND_STATE.md)을 유지한다.

모듈 목록·그룹은 저장된 작업 데이터를 사용한다. 화면에서 모델 응답이나 모듈 이름만으로 선행 그룹을 재구성하지 않는다. 게이트와 완료 판정은 서버의 상태·대기 사유를 사용하고, 100% 숫자로 선행 게이트를 열거나 최종 검토를 생략하지 않는다.

접기/펼치기·탭 이동은 표시만 바꾸며 실행·중단·재시도 명령을 보내지 않는다. Test는 해당 IP의 장비 시험 단계이며 GUI Test 화면의 임의 Run과 동일시하지 않는다. 기본 수동시험과 승인된 자동 프로파일 예외는 그대로 유지한다.

## 3. 화면 상태와 모션 설계안

아래는 사용자 요청을 구체화한 **설계안**이다. 완료 색상·세부 색상값·크기·모션 속도는 사용자 확정 사항이 아니며 구현 시 시각 검증한다.

### 3.1 연결 점과 실행 표시를 분리

한 점에 연결과 실행을 번갈아 대입하면 `연결됨 + 시작 전`, `연결 끊김 + 실행 지속`을 표현할 수 없다. **연결 점은 연결 근거만**, 별도 실행 배지·문구는 실행 상태만 나타내는 방안을 사용한다. IP에도 연결 점을 두되, ACON과 해당 작업/IP의 관계가 확인된 경우에만 적용한다. 공통 세션 상태를 상속하면 `공통 연결`이라고 표시하며 IP별 소켓이 확인됐다고 표현하지 않는다. 대응 관계가 없으면 `연결 확인 불가`다. 이는 사용자 색상 요구를 보존하는 표시 설계안이다.

| 대상 / 상태 | 표시안 | 흐름 효과 |
|---|---|---|
| ACON 및 연결 근거가 있는 IP / 연결 정상 | 푸른 연결 점 + 연결됨 또는 공통 연결 | 연결 사실만으로 실행 흐름을 만들지 않음 |
| ACON 및 해당 IP / 확인된 연결 단절 | 빨간 연결 점 + 연결 끊김 | 해당 연결 경로 정지; IP 실행 결과는 별도 보존 |
| ACON 및 해당 IP / 시작 전·미설정·확인 불가·관찰 만료 | 회색 연결 점 + 각각의 상태 문구 | 해당 연결 경로 정지 |
| BackEnd / 상태 조회 성공·실패·최초 확인 전 | 푸른 점 + 상태 조회됨 / 빨간 점 + 상태 조회 실패 / 회색 점 + 확인 중 | API 조회가 worker·ACON·장비 정상임을 뜻하지 않음 |
| IP / RUNNING | 푸른 실행 배지 + 실제 실행 단계 + 진행률 | 신선한 snapshot의 해당 IP/단계 경로만 흐름 |
| IP / PENDING·게이트 대기·WAITING_INPUT | 회색 실행 표시 + 단계/대기 사유 + 알려진 진행률 | 정지 |
| IP / FAILED·CANCELLED | 빨간 실행 표시 + 실패 또는 취소됨 | 정지 |
| IP / CANCEL_REQUESTED·DISPATCHING | 회색 전환 표시 + 취소 처리 중·종료 미확인 또는 배정 중 | 정상 실행 흐름 정지; 종료/자원 해제를 뜻하지 않음 |
| IP / UNKNOWN·지원하지 않는 상태·오래된 데이터 | 회색 실행 표시 + 확인 필요/마지막 확인 상태 | 정지; 실패나 중단으로 단정하지 않음 |
| IP / 현재 기준의 유효한 완료 | 완료 체크와 완료 문구 | 정지 |

예: ACON 연결이 정상인 대기 IP는 `푸른 연결 점 + 시작 전`이다. 연결 근거가 없는 실행 IP는 `회색 연결 점 + 구현 진행 중`이며, 연결 정보를 만들어 푸르게 바꾸지 않는다. ACON만 단절되고 BackEnd의 신선한 snapshot이 RUNNING을 보고하면 연결선만 정지하고 해당 IP의 실행 표시는 유지할 수 있다. 조회 자체가 끊기면 마지막 실행 문구에 확인 시각을 붙이고 실행 흐름도 정지한다.

작업의 일시 중지가 신규 배정만 막고 실행 중 프로세스는 유지하는 경우, 실제 RUNNING 단계의 표시를 임의로 중단으로 바꾸지 않고 일시 중지 범위를 별도 표시한다.

### 3.2 화살표별 의미

얇은 기본 연결선 위에 밝은 청록색 강조 구간과 화살촉이 진행 방향으로 이동하는 SVG/CSS 표현을 사용한다. 여러 IP가 병렬 진행하면 해당 경로를 동시에 표시한다. 다만 상위 한 줄 전체에 같은 활성 상태를 적용하지 않는다. 단계 간 진입선도 같은 SVG 표현을 재사용하며 현재 RUNNING 단계로 들어가는 화살표만 움직인다.

2026-11-04 최종 시각 기준은 사용자가 지정한 로컬 `docs/system-diagram-20261103/bsp-system.html`의 light 스타일이다. 처음 다크 테마를 적용했으나 사용자 정정에 따라 흰 카드·밝은 회색 점 격자·청록 FrontEnd·녹색 BackEnd·보라 선행 그룹·파란 일반 그룹 테두리로 변경했다. 이 파일을 import하거나 배포 의존성으로 요구하지 않으며 필요한 표현은 `web/diagram.css`의 전용 변수/선택자로 구현한다. 호스트의 다른 탭 테마는 변경하지 않는다.

| 연결선 | 의미와 활성 조건 |
|---|---|
| ACON → BackEnd | 연결 관계. 연결 정상은 정적인 푸른 선; 실제 활동 근거를 제공할 때만 흐름. 현재 활동 근거는 미정 |
| BackEnd → 선행 그룹 | 선행 그룹의 확인된 실행 활동. 선행 IP에 신선한 RUNNING이 있을 때 흐름 |
| 선행 그룹 → 일반 그룹 | `설계 이후 선행 조건`이라는 라벨을 붙임. 서버의 선행 완료와 일반 IP 설계 이후 RUNNING이 함께 확인될 때 흐름; 게이트 충족만으로 흐르지 않음 |
| 그룹 → IP 및 펼친 단계 | 해당 IP와 현재 RUNNING 단계로 들어가는 선만 흐름. 완료·대기인 뒤 단계까지 흐르지 않음 |

일반 IP의 분석 중에는 일반 그룹 내부의 해당 IP/분석 진입선만 흐른다. 선행→일반 연결은 `설계 이후 대기 · 분석 가능`으로 남겨 분석이 선행 그룹 완료를 기다린다고 보이지 않게 한다. 일반 그룹 실행 때문에 실행하지 않는 선행 그룹의 선을 활성화하지 않는다. 그룹 상태는 실행/대기/실패/불명 개수를 병기하고 한 IP의 실패가 다른 IP의 흐름을 지우지 않도록 한다. 상충하는 서버 상태에서는 게이트를 임의로 열지 않고 불일치 안내를 표시한다.

Archify는 시각적 참고이며 외부 서비스나 CLI를 제품 런타임 필수 의존성으로 추가하지 않는다. 전용 CSS 범위와 디자인 변수를 사용한다. 색 외에 텍스트·아이콘을 함께 제공하고, IP 버튼은 키보드 Enter/Space와 펼침 상태 안내를 지원한다. 모션 줄이기 설정과 모션 일시정지 제어를 제공한다. 좁은 화면은 상위 좌우 순서를 유지하며 캔버스를 스크롤할 수 있게 한다. 긴 이름·많은 IP·빈 그룹에서도 겹침/잘림을 검증한다.

## 4. 현재 데이터와 표시 변환 경계

현재 확인한 코드: `apps/web/src/main.tsx`는 작업 snapshot과 API 접속 상태를 관리하며 polling으로 갱신한다. `apps/web/src/api.ts`의 현재 단계는 analysis/design/code/build/verification/device_test다. 새 화면은 이 상태 조회를 재사용하고 별도 polling이나 worker를 만들지 않는 방향이다.

요청한 5단계와 현재 6개 서버 단계 사이에는 **표시 변환이 필요**하다. 다음 대응으로 구현하며 서버 계약이나 실행 단계를 병합하지 않는다.

| 요청한 표시 단계 | 현재 서버 단계 대응 |
|---|---|
| 요구사항분석 | analysis |
| 설계 | design |
| 구현 | code와 build를 하위 상태로 보존; 빌드 실행 시 `구현 · 빌드 중` 표시 |
| 검증 | verification |
| Test | device_test |

빌드 실패/대기/유효성은 구현 카드의 하위 정보에서도 확인 가능해야 한다. 두 하위 단계가 유효하게 끝나기 전 구현을 완료로 표시하지 않는다. 프런트에서 5단계를 각 20%로 계산하지 않고 서버의 모듈 진행률을 사용한다. 진행률 미보고는 `미집계`로 표시하며 0으로 꾸미지 않는다. 현재 단계가 복수이면 복수 실행 사실을 보존한다.

### 4.1 현재 코드의 의미와 판정 순서

아래는 `backend/domain/policy.py`의 `project/valid/module_done/progress`와 현재 worker를 읽고 정리한 표시 규칙이다. 별도 실행 정책을 만들지 않는다.

- `current_stage`는 **첫 번째 유효 완료가 아닌 단계**이며 RUNNING을 뜻하지 않는다. 실제 실행은 각 stage의 status를 먼저 확인한다. RUNNING이 없으면 current_stage를 `다음/대기/실패/재검증 단계`로 설명한다. 여러 RUNNING이 들어오면 모두 표시하고 불일치를 숨기지 않는다.
- SUCCEEDED만으로 완료 체크하지 않는다. 현재 구현의 완료 기준은 `SUCCEEDED + validity=CURRENT`다. 무효화된 성공·이전 Attempt 성공은 현재 완료에서 제외한다. 실행·불명·취소 처리 상태를 먼저 보존한 뒤 대기/실패/무효화 사유를 표시한다.
- `blocked_reason`은 현재 실행을 취소하는 신호가 아니다. 현재 project는 RUNNING에도 신규 배정 게이트 사유를 붙일 수 있다. 예를 들어 RUNNING + `신규 배정 일시 중지`는 `실행 중 · 후속 배정 중지`로 표시한다. PENDING인 현재 대상 단계에서만 게이트 대기를 주 표시로 삼는다. 앞 단계 진행 중인 미래 단계는 `이전 단계 대기`다.
- `code/build`는 화면 내부에 모두 보존한다. code 완료 + build PENDING은 `구현 · 빌드 대기`, build FAILED는 `구현 · 빌드 실패`이며 구현 완료가 아니다. 두 단계의 미지원 상태는 정상 대기나 성공으로 바꾸지 않는다.
- Test는 현재 BSP device_test의 상태를 사용한다. WAITING_INPUT은 수동 입력 대기 또는 자동 준비 대기 사유로 구분하고, 자동 퓨징/부팅/TC 진행은 같은 Attempt에 연결된 정보가 있을 때 부가 문구로 표시한다. 퓨징 완료·TC 일부 완료·automation COMPLETED만으로 Test 완료를 만들지 않는다. 보고 필드는 [자동 퓨징 계약](AUTOMATIC_FLASH_TEST.md)에서 관리한다.
- 서버 모듈 percent는 유효하게 완료된 단위의 비율이며 실행 시간이나 단계 내부 실시간 %가 아니다. 기존 v1 agent는 중간 %/heartbeat를 보내지 않는다. 값이 그대로여도 RUNNING 흐름은 가능하지만 진행률을 자동 증가시키지 않는다. 계획 변경/무효화로 값이 줄면 서버 값과 그 사유를 그대로 표시한다.
- 그룹 진행률은 `job.groups`, 작업 전체는 `job.overall`을 사용할 때만 표시한다. IP 퍼센트 평균이나 완료 IP 수를 전체 진행률로 바꾸지 않는다. 기존 대시보드 상단 `implementation=design+code`와 이 탭의 `구현=code+build`는 목적이 다른 표시다. 기존 상단 집계는 변경하지 않고 이 탭의 매핑을 명시한다.
- 현재 progress는 사유 있는 NOT_APPLICABLE을 분모에서 제외하지만 module_done은 모든 단계의 유효 성공을 요구한다. 이는 목표 설계의 승인된 N/A 완료 조건과 차이가 있다. 해당 데이터가 오면 `해당 없음`과 서버 게이트를 함께 보존하고 화면에서 100%/N/A를 근거로 완료·게이트를 보정하지 않는다. 서버 정책 정합화는 별도 검토 범위다.

**현재 API 연결 성공은 ACON 연결 성공의 증거가 아니다.** ACON 상태 제공 위치·식별자·heartbeat/갱신 주기·만료 기준은 미확정이다. 실제 연결 데이터가 없으면 미설정/확인 불가로 표시한다. 서버 응답 유실 시 마지막 확인 시각과 오래된 상태를 함께 보여주고 모듈의 실제 실패를 추정하지 않는다. 재연결/작업 전환 시 다른 작업 또는 오래된 버전의 응답을 섞지 않는다.

다이어그램 입력은 작업/모듈 식별, 저장된 그룹, 단계 상태·대기 사유, 서버 진행률, 연결 근거와 갱신 시점을 전달받는 화면 전용 모델로 설계한다. 정확한 TypeScript 형식은 구현 단계에서 고정한다. 외부 에이전트 보고 필드는 [기존 계약](AGENT_STATUS_CONTRACT.md)을 따르며 이 문서에 새 보고 계약을 만들지 않는다.

### 4.2 호스트의 조회 관찰과 snapshot 수명

문서 리뷰 당시 `main.tsx`는 약 1.8초 간격으로 jobs → 선택 job → events를 조회하고 `online`을 최초 true로 시작했다. events 단독 실패도 offline으로 표시하던 문제를 RQ-50 통합에서 분리했다. 현재 초기 확인 전은 null이며 모든 snapshot 유입에 같은 수용 경계를 적용한다. `updated_at`은 저장 시각이고 heartbeat/최근 조회 성공 시각이 아니므로 관찰 시각을 별도로 전달한다.

| 책임 | 구현 계약 |
|---|---|
| 호스트 조회 | 기존 1,800ms polling 한 경로를 재사용. snapshot 조회 결과와 events 조회 결과를 구분하며, 최초 성공 전은 확인 중. 같은 세대의 중복 refresh는 병합하고 실패·완료 시 잠금을 해제한다. 읽기 요청당 5,000ms 제한시간과 취소/논리적 무효화로 영구 pending에서도 잠금을 해제하고 기존 주기로 재조회한다. 만료된 응답은 나중에 도착해도 버린다. 다이어그램 진입은 추가 조회 없이 기존 polling의 새 관찰을 기다린다 |
| 응답 수용 | polling뿐 아니라 명령 VERSION_CONFLICT 복구 GET·명령 후 재조회 등 모든 snapshot 유입에 같은 수용 경계를 적용. 조회 대상/실행 모드/선택 작업의 세대와 요청 순서를 확인한 뒤 수용. 작업/대상 변경은 이전 요청을 취소하거나 무효화. 이전 작업 응답은 성공·실패 모두 현재 표시를 바꾸지 못함. 같은 세대·job에서 낮은 version은 버리고, 같은 version의 정상 응답은 관찰 시각만 갱신. 최신 상태 뒤 늦은 실패가 연결 점을 덮지 못하도록 함 |
| 시간 의미 | snapshot 저장 시각, 클라이언트가 유효 snapshot을 수용한 시각, ACON 제공자의 관찰 시각을 분리. 저장 시각이 오래됐다는 이유로 장시간 빌드를 단절로 판정하지 않음 |
| 신선도 | snapshot 조회 실패는 즉시 `조회 실패·마지막 확인 상태`. 응답이 멈추거나 페이지 복귀 뒤 확인 전에는 `갱신 확인 중/지연`으로 흐름 정지. 경과 시간은 로컬 단조 시계로 측정하고 기준은 호스트가 제공; 현재 조회 주기의 3배인 5,400ms. 이 값은 ACON heartbeat TTL이 아님 |
| 재연결 | 유효한 전체 snapshot을 수용한 뒤 활동 표시 재개. version 역행이 지속되면 서버/DB 기준 변경 가능성을 안내하고 명시적인 기준 재설정 후 재조회; 낮은 version을 자동 수용하지 않음 |
| 잘못된 입력 | loading/작업 없음/조회 실패를 구분. id 중복·필수 단계 누락·미지원 group/status·범위 밖 percent는 진단과 확인 불가로 표시. 모르는 group을 일반 그룹으로 조용히 옮기거나 null percent를 0으로 바꾸지 않음 |

ACON은 이 조회 관찰과 별도 입력이다. 제공자·작업/IP 대응 범위·연결 의미·관찰 시각·유효 기간을 확인하기 전에는 미확인이다. ACON 응답이 없다는 이유만으로 모듈 실행 상태를 실패로 바꾸지 않는다. 구현 시 초기 화면·지연된 실패·A→B→A 선택·같은 version의 반복 성공·영구 pending 후 복구·events만 실패·A 명령 충돌 복구 중 B 선택을 T-146 fixture로 검증한다. 기존 명령의 대상/idempotency/재시도 정책은 유지하며 다이어그램 때문에 명령을 새로 보내지 않는다. 조회 요청의 취소는 BSP 실행 취소가 아니다.

## 5. 폴더와 통합 설계안

아래 경로로 구현했다. `host/`의 조회 보호는 호스트가 재사용하는 별도 helper이며 화면 자체는 polling하지 않는다.

```text
workflow_diagram/
├─ web/
│  ├─ DiagramTab.tsx
│  ├─ presentation.ts
│  ├─ diagram.css
│  ├─ types.ts
│  └─ index.ts
├─ adapters/
│  └─ dashboard.ts
├─ host/
│  └─ snapshot.ts
├─ tests/
└─ README.md
```

`기존 앱의 상태 조회 → adapter → DiagramTab`으로 연결한다. 화면은 앱의 전역 변수·API URL·인증·DB에 직접 의존하지 않고 전달받은 데이터로 렌더링한다. adapter가 회사별 데이터 차이를 담당하며 화면의 접힘 상태는 서버 데이터를 수정하지 않는다. 새 작업을 선택하면 모듈 식별자를 조회 대상/실행 모드/작업/모듈 단위로 구분한다.

의존 방향은 `호스트 → adapter → web/types`, `web 화면 → web/types·전용 components`로 제한한다. 재사용 폴더에서 `apps/web/src/api.ts/main.tsx/HardwareStatus.tsx`를 역으로 import하지 않는다. 현재 Data 타입이 any 기반이어도 공개 입력은 필요한 값만 좁힌 화면 모델로 정의하고, 로그·토큰·profile·전체 Attempt 이력은 전달하지 않는다. adapter는 입력을 변경하지 않는 순수 변환이고 네트워크·전역 상태·명령 callback을 소유하지 않는다. 함수/props의 이름과 타입 버전은 구현 시 고정한다.

기존 파일의 실제 접점은 `apps/web/src/main.tsx`의 import/탭 등록/데이터 전달/제목·조회 보호와 `apps/web/tsconfig.json`의 외부 폴더 포함 설정이다. `vite.config.ts`의 기존 React alias/dedupe는 재사용해 변경하지 않았다. GUI Test 런타임을 새 기능의 의존성으로 만들지 않으며 새 npm 의존성을 추가하지 않았다.

초기 범위는 읽기 전용 시각화이며 DB 이전·서버 실행 정책 변경은 없다. ACON 상태를 위해 API 확장이 필요하다고 확인되면 별도 접점과 시험 범위를 문서화한다. 회사 UI 스택 호환성은 아직 확인하지 않았으므로 폴더 복사만으로 동작한다고 보장하지 않는다.

### 5.1 렌더링과 이식 효율

화면 배율/집중은 `web/viewport.ts`가 로컬 상태로 관리한다. 기본 카드 폭/간격을 줄이고 25~160% 축소/확대, 100%, 전체 맞춤을 제공한다. IP 펼침 시 해당 모듈과 5단계, 서비스/그룹 제목 선택 시 해당 영역을 중앙에 맞추고 주변을 약화한다. 전체 보기/캔버스 Esc는 집중만 해제한다. 기본 전체 맞춤은 최대 85%, 집중 자동 맞춤은 최대 110%이며 대규모 목록은 최소 배율과 스크롤을 병행한다. 같은 작업의 배율·선택·스크롤은 탭 왕복에서 유지하고 대상 변경 시 초기화한다. 크기 관찰은 실제 host/graph 크기 변경만 처리해 수동 배율·복원 위치를 덮지 않으며 집중 상태의 창 크기 변경도 재조정한다. CSS zoom/ResizeObserver/scrollTo를 사용하는 현재 Chrome 환경을 검증했고 회사 브라우저 호환성은 이식 시 확인한다.

- 최초에는 IP를 모두 접고, 펼친 IP의 5단계만 DOM에 만든다. 같은 작업에서 탭을 오갈 때 펼침·스크롤을 유지하되 현재 세션 메모리만 사용한다. 새 작업/대상에서는 초기화한다. 제거된 모듈 키를 정리하고 목록 갱신 때 강제로 포커스·스크롤을 이동시키지 않는다.
- diagram이 비활성 탭일 때 화면 계산·애니메이션을 멈춘다. 호스트의 다른 탭이 사용하는 조회 주기는 바꾸지 않는다. 페이지 숨김/모션 줄이기/모션 정지도 흐름 효과만 멈추며 작업을 중지하지 않는다. 재진입은 새 snapshot 관찰 후 모션을 재개한다.
- 단계의 고정 배치를 사용하므로 초기에는 자동 그래프 배치 라이브러리를 요구하지 않는다. 갱신마다 노드 위치를 재배치하지 않고 모듈 id와 저장된 순서를 유지한다. SVG 경로 재측정이 필요하면 크기·펼침 변경에만 묶고 프레임마다 전체 DOM 측정을 반복하지 않는다.
- 상태 변환은 모듈·단계를 한 번 순회하고 전체 로그·Attempt 이력을 복제하지 않는다. 같은 snapshot version에서도 조회 신선도·ACON 관찰이 바뀔 수 있으므로 version 하나만으로 화면 갱신을 생략하지 않는다. CSS 모션은 매 프레임 React 상태 갱신을 요구하지 않도록 한다.
- 현재 설정의 최대 100개 모듈과 이름 80자, 모두 펼침·동시 분석·375px 화면을 시험 규모로 삼는다. 새로운 가상 스크롤/검색/자동 배치 의존성은 실측 병목이 있을 때 검토한다. 회사 모듈 상한이 다르면 COMPANY_MAP에 새 규모를 기록한다.
- CSS 선택자·변수·keyframes·SVG marker id를 기능 범위와 인스턴스별로 격리한다. 회사의 전역 button/p/svg 스타일이 안으로 들어오는 경우도 검사한다. 별도 페이지나 전역 reset CSS를 의존성으로 요구하지 않는다.
- 호스트와 같은 React 인스턴스를 사용한다. 현재 Vite의 React alias/dedupe와 TypeScript 외부 폴더 경로 설정은 실제 코드로 확인했으나 회사에서도 존재한다고 가정하지 않는다. 소스 이식의 필수 peer/버전·asset·시험 도구·lockfile 반영 범위를 PORT에 고정하고 node_modules 전체를 복사하지 않는다.

효율성의 인수 근거는 100개 fixture에서 탭 열기·펼침·반복 snapshot 수용의 시간/렌더 횟수/DOM 수와 네트워크 요청 수, 비활성 탭의 애니메이션 중지를 기록하는 것이다. 구체적인 응답시간 예산은 구현 착수 시 시험 장비와 함께 고정하며 현재 성능 수치를 주장하지 않는다. 다이어그램을 켠 전후 동일 호스트 조회 요청 수를 비교하고 추가 polling·모듈별 fetch가 0인지 확인한다.

현재 API는 전체 job JSON을 반환한다. adapter에서 로그/이력을 제외해도 이미 발생한 전송·JSON 파싱 비용까지 사라지지는 않는다. 빈 이력 fixture와 별도로 대표 Attempt/자동 퓨징 보고 이력이 있는 fixture를 고정하고 응답 bytes, JSON 파싱, adapter 변환, 렌더 시간을 나눠 기록한다. 이력 크기·반복 수·기준 환경도 결과에 남긴다. 서버의 경량 조회 API는 지금 추가하지 않으며 실측 병목이 확인되면 별도 변경 범위로 검토한다.

## 6. 구현 착수와 전달 조건

문서 리뷰 후 구현 지시를 받았다. 화면 데이터 형식·ACON 상태 제공 접점·빌드 단계 표시를 구체화하고 adapter 및 fixture → 화면/모션 → 기존 앱 통합 → T-144~148 → 이식 안내 기준 고정 순서로 진행한다. ACON 미연결은 그 표시만 미확인으로 유지하며 나머지 모듈 화면 구현과 분리한다.

후속 순서는 상태/유효성 매핑 fixture → 호스트 조회 관찰·응답 수용 보호 → 표시·모션 → 통합·성능/이식 시험으로 구체화한다. 최소 연동은 탭 import만이 아니라 4.2절의 관찰 메타데이터 전달과 필요한 기존 refresh 보완을 포함한다. 이는 승인된 RQ-50 구현 범위다. ACON 계약 미확정은 실제 연결 표시만 보류하고 기본 읽기 전용 화면을 막지 않는다.

회사 적용 시 전용 폴더와 최소 통합 변경을 가져오고, 회사 데이터 변환과 빌드 접점만 조정한다. [PORT-001](../porting/PORT-001.md)에 실제 코드/시험 커밋·의존성·명령·증거를 채우기 전에는 전달 준비 완료로 표시하지 않는다. 실제 회사/ACON 인수는 T-149이며 로컬 모의 시험으로 대신하지 않는다.

## 2026-11-04 추가 표시 요구

사용자 요청으로 단계 카드96px/최소높이72px, 제목10px·상태/설명9px, IP카드180px, 단계 연결선20px로 더 줄였다. 높은 배율에서도 실제 카드가 작게 남도록 크기 자체를 조정하며 사용자 확대 기능은 유지한다. 선행/일반 그룹은 제목 옆 독립 버튼으로 접고 펼친다. 접으면 IP/단계 DOM만 제거하며 그룹 이름·개수·실행 요약·진행률은 유지한다. 개별 IP 펼침 상태와 그룹 접힘은 같은 작업의 탭 왕복에서 보존하고 작업/대상 변경 시 초기화한다. 집중 중인 IP를 포함한 그룹을 접으면 전체 보기로 복귀한다. 제목 클릭의 영역 집중과 접기 버튼은 별개다. 공개 입력/조회/실행 정책은 변경하지 않는다.

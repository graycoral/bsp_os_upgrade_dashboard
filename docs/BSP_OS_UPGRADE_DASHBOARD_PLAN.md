# BSP OS Upgrade 대시보드 요구사항 및 단계별 계획

- 문서 작성일: 2026-10-10
- 최신 관리 위치: `graycoral/bsp_os_upgrade_dashboard` 저장소의 `docs/BSP_OS_UPGRADE_DASHBOARD_PLAN.md`
- 문서 최종 수정일: 2026-10-11
- 문서 버전: 0.5 · 상단 전체 흐름을 모듈 기반 단계별 종합 완료율로 변경
- 상태: 사용자 운영 원칙 일부 확정 · 연동 상세 설계 검토 중
- 범위: 대시보드 및 업그레이드 작업 흐름 설계
- 현재 작업: 계획 문서 업데이트 및 GitHub 문서 관리. 기존 화면 시안은 예시이며 실제 시스템 구현은 진행하지 않는다.

## 1. 목적

BSP의 OS 버전이 업그레이드될 때, 기존 BSP 드라이버에 적용된 벤더 수정사항이 새로운 버전에 적절히 반영되도록 관리한다. 신규 OS에 이미 반영된 변경은 근거를 확인하고, 추가 이식이 필요한 변경은 구현과 검증으로 연결한다.

대시보드는 업그레이드 실행, 전체 및 모듈별 흐름 확인, 진행률 확인, 이슈 대응 명령, 사람 검토와 Jira 처리 상태를 하나의 웹 화면에서 제공한다.

판단이 애매하거나 더 좋은 방향이 발견되면 질문 또는 기록으로 남기고, 결정이 필요한 작업은 검토 절차로 연결한다.

## 2. 요구사항과 제안 구분

### 2.1 사용자 요구사항

1. OS Upgrade를 시작하는 버튼이 있어야 한다.
2. 상단 전체 현황은 화살표 대신 요구사항 분석·구현·검증·빌드·테스트 각각의 종합 완료율로 표시한다. 아래 모듈들의 해당 단계 결과를 집계하며, 부트로더 선행 그룹과 나머지 그룹의 진행률도 구분한다. 전체 실행 상태와 최종 완료 여부는 별도로 유지한다.
3. 각 모듈의 요구사항 분석, 디자인 변경, 코드 구현, 빌드, 검증과 보드팜 연동·테스트 상태가 상세 흐름으로 보여야 한다.
4. 전체 진행률이 보여야 한다.
5. 이슈가 발생하면 프롬프트로 명령하는 창이 있어야 한다.
6. 사람이 직접 검토해야 하는 사항은 Jira로 만들고, 그 목록이 보여야 한다.
7. 문서와 승인된 화면 시안 검토 단계이며, 실제 대시보드 구현·서버 작업 실행은 별도 지시 전까지 진행하지 않는다.
8. 진행 중 새로운 사람 판단이 필요한 항목을 Jira로 보낸다. 해당 판단에 의존하는 작업만 대기시키고 독립 작업은 계속한다.
9. 초기에는 분석을 병렬로 수행하고, 코드 수정과 빌드는 순차 실행한다. 향후 수정·빌드도 병렬 실행할 수 있도록 확장 가능성을 고려한다.
10. 빌드는 사용 중인 Linux 서버에서 수행한다. 보드팜은 Linux 서버에 연결된 환경 또는 로컬 Windows PC에 연결된 환경 중 선택할 수 있게 한다.
11. 모듈별 상세 흐름에서 실패한 단계에 재시도 버튼을 제공한다.
12. 부트로더 관련 선행 모듈이 모두 완료되기 전에는 나머지 모듈을 실행할 수 없다. 나머지 모듈의 분석·수정·빌드·검증 모두 이 조건을 따른다.

8~12항은 2026-10-11 사용자 답변으로 확정한 운영 원칙이다. 독립 작업 계속 원칙보다 선행 그룹 전체 완료 조건을 우선 적용한다. 이후 절의 상세 복구·동기화·완료 규칙은 이 원칙을 실현하기 위한 설계 제안이며, 구체적인 도구와 환경을 확인한 뒤 확정한다.

### 2.2 설계 제안

- 작업 실행과 개입 기능이 있는 웹 관리 화면으로 구성한다.
- 하나의 업그레이드 작업 아래 모듈, 분석, 구현, 검증, 이슈, 명령, Jira 이력을 연결한다.
- 화면과 실행 시스템을 구분한다. 화면은 명령과 상태를 전달하고, 실제 분석·수정·빌드는 작업 실행 시스템이 수행한다.
- Linux 서버에서 대시보드 서버·에이전트·빌드를 실행하고, Windows PC에서는 브라우저로 접속한다. 보드팜 연결은 Linux 또는 Windows 환경을 선택한다.
- 지정한 Linux 계정의 프로젝트 작업 폴더에서 Claude Code를 실행하고 OS Upgrade Agent의 지침과 시작 명령을 전달한다.
- 초기에는 대시보드 서버에 실행·상태 관리 기능을 포함한다. 별도 작업 관리자 서비스는 필수가 아니다.
- 구체적인 프레임워크, DB, 서버 주소·계정·경로 및 Jira 연동 방식은 아직 확정하지 않는다.

### 2.3 Linux 실행 환경 및 접속 방식

| 위치 | 역할 |
|---|---|
| Windows PC | 브라우저에서 시작, 진행 확인, 프롬프트 입력, 사람 검토. Windows 보드팜 선택 시 해당 PC의 연동 환경으로 장비 작업 수행 |
| Linux 서버 | 대시보드 서버, Claude Code와 Codex / OpenCode 실행, 소스 접근, 코드 수정·빌드, 상태·로그 저장. Linux 보드팜 선택 시 해당 환경으로 장비 작업 수행 |

- 초기 단독 사용에는 SSH 터널을 통한 웹 접속을 제안한다. 여러 사람이 사용하는 경우 사내망 또는 VPN 접속과 로그인·사용자별 권한을 검토한다.
- 대시보드 서버가 같은 Linux 서버에서 지정 계정으로 실행된다면 Claude 실행을 위해 다시 SSH로 접속할 필요는 없다.
- 대시보드 서버와 작업 서버가 다르면 SSH로 지정 계정에 연결하여 작업을 실행한다.
- Linux 서버에 GUI나 브라우저를 띄우는 방식은 필요하지 않다.
- 브라우저 종료나 사용자 SSH 연결 종료와 작업 프로세스의 수명을 분리한다. 서버가 정상 동작하는 동안 작업은 계속되고, 재접속하면 저장된 상태를 조회한다.
- 서버 재부팅이나 프로세스 종료 후에는 실제 실행 상태를 확인하고 복구·재개한다. 세션 기록만으로 작업이 계속 실행 중이라고 판단하지 않는다.
- 업그레이드 대상이 BSP 소스인지 실행 서버 자체의 OS인지 구분한다. 실행 서버 자체를 업그레이드하는 경우 별도 관리 서버 구성을 검토한다.

### 2.4 실행 계정 및 폴더 설정

| 설정 | 용도 |
|---|---|
| 서버 주소 | 작업할 Linux 서버 식별. 같은 서버에서 직접 실행하는 경우 원격 접속은 불필요 |
| 실행 계정 | Claude 인증, 지침·소스 접근, 결과 기록 및 빌드에 사용하는 Linux 계정 |
| 프로젝트 작업 폴더 | Claude Code의 실행 위치. CLAUDE.md와 OS Upgrade Agent 및 역할별 지침 배치 |
| 기존 원본 BSP 경로 | 벤더 수정 전 비교 기준 |
| 벤더 수정 BSP 경로 | 기존 벤더 변경사항 분석 대상 |
| 신규 원본 BSP 경로 | 목표 OS의 원본 비교 기준 |
| 신규 BSP 수정 작업 폴더 | 실제 이식·수정·빌드 대상 작업 사본 |
| 결과 저장 폴더 | 분석 결과, 실행 로그, 검증 결과 및 작업 상태 저장 |
| 실행 범위 | 분석만 수행할지 구현·검증까지 진행할지 지정 |
| Linux 빌드 설정 | 빌드 명령, 환경 초기화 절차, 도구 버전, 빌드 결과 경로 |
| 단계별 동시 실행 설정 | 초기 분석 병렬 허용, 코드 수정·빌드 순차 실행. 향후 병렬 실행 조건과 동시 실행 수 관리 |
| 보드팜 실행 환경 | Linux 서버 연동 또는 Windows PC 연동 선택, 대상 환경 ID |
| 보드팜 연동 설정 | 서비스·도구, 보드 목록, 연결 확인, 예약·이미지 적용·테스트·취소·결과 조회 방법 |
| 이미지 전달 및 보관 설정 | Linux 산출물 위치, 선택한 실행 환경의 수신 위치, 전달 방법 및 체크섬 확인 |

- 프로젝트 작업 폴더와 비교 대상 소스 폴더를 구분한다. 작업 폴더의 설정에서 각 소스 경로를 지정한다.
- 비교 기준 소스는 참조용으로 유지하고, 실제 변경은 명시된 신규 BSP 작업 사본에 수행하는 방안을 기본으로 한다.
- 시작 전 폴더 존재 여부, 참조 경로 읽기 권한, 작업·결과 경로 쓰기 권한, 지정 계정의 Claude 실행 가능 여부와 빌드 환경을 확인한다.
- 계정의 실행 환경과 인증은 Linux 서버에서 준비한다. 대시보드에서 비밀번호나 인증 정보를 프롬프트에 넣어 전달하지 않는다.
- 실제 서버 주소, 계정과 경로는 아직 제공되지 않았으므로 설정값은 미정이다.
- 소스 경로와 함께 기존 원본·벤더 수정본·신규 원본의 고정된 리비전 또는 식별 가능한 스냅샷을 기록하는 방안을 제안한다. 경로가 같아도 내용이 바뀌면 같은 기준으로 취급하지 않는다.

### 2.5 Claude 세션 및 OS Upgrade Agent 연결

OS Upgrade Agent는 프로젝트에 배치하는 역할 지침과 실행 설정이며, Claude Code 세션이 이를 읽고 실제 작업을 수행한다. 세션 생성만으로 업그레이드를 시작하지 않고, 대상·범위와 시작 명령을 함께 전달한다.

- 초기에는 업그레이드 작업 하나당 조정용 Claude 세션 하나를 두는 방안을 제안한다.
- 작업 ID와 Claude 세션 ID, 실행 계정, 작업 폴더를 연결하여 기록한다.
- 이슈 명령창의 후속 프롬프트는 해당 작업의 세션으로 전달한다. 같은 세션의 동시 명령은 순서를 정해 처리한다.
- 전체 진행 상태, 모듈 결과, 검증 근거와 Jira 결정은 Claude 대화와 별도로 저장한다.
- Claude는 분석·계획·작업 지시를 담당하고, 대시보드 서버의 실행 기능이 Codex / OpenCode 작업을 호출하고 결과를 수집한다.
- 기존 SSH 터미널의 Claude 세션을 재개할지, 대시보드 전용 세션을 새로 만들지는 미결정이다. 초기에는 전용 세션 생성을 제안한다.
- 터미널 화면 입력을 자동화하기보다 프로그램 실행 인터페이스와 세션 재개 기능을 활용하는 방안을 제안한다. 실제 설치 버전에 맞는 호출 방식은 구현 전에 확인한다.
- 실행 연결 시험에서 인증, 환경 초기화, CLAUDE.md 및 역할 지침 로딩, 결과 수집과 세션 재개를 확인한다. 터미널에서 정상 실행된다는 사실만으로 대시보드 실행 환경까지 검증된 것으로 보지 않는다.
- 실행 요청은 대시보드 서버가 일관되게 기록·배정하는 방안을 제안한다. Claude의 작업 지시와 서버의 실제 호출을 구분하여 같은 작업이 두 경로에서 중복 실행되지 않게 한다.
- 결과에는 작업·모듈·단계·실행 회차·소스 기준·산출물·판정 근거를 연결한다. 에이전트 응답 종료만으로 빌드나 장비 검증을 완료 처리하지 않는다.

### 2.6 초기 실행 관리 범위

초기에는 별도 작업 관리자 프로그램 없이 대시보드 서버가 다음 기능을 수행한다.

- 시작 입력과 경로 확인
- 작업 기록 및 중복 실행 방지
- 지정 계정·작업 폴더에서 Claude 실행과 세션 연결
- 명령 전달, 실행 상태·로그·결과 저장
- 중지·재개와 재접속 후 상태 조회

여러 업그레이드의 동시 실행이나 여러 Linux 서버로의 작업 배정이 필요해지면 실행 관리 기능을 별도 서비스로 분리하는 방안을 검토한다.

다음은 장애 복구와 명령 충돌 방지를 위한 설계 제안이다.

- 작업 ID, 명령 ID, 실행 회차, 세션 ID, 실행 위치와 외부 작업 ID를 실행 전후에 저장한다. 같은 명령의 재전송은 새 실행으로 취급하지 않는다.
- 연결이 끊기면 우선 상태 확인 중으로 표시한다. 실제 프로세스 또는 외부 작업을 확인하기 전에는 실패로 확정하거나 자동 재실행하지 않는다.
- 중지 요청은 새 작업 배정을 멈추는 것과 진행 중 작업을 취소하는 것을 구분한다. 기본은 새 배정을 멈추고 진행 중 작업의 안전한 종료를 기다리는 방안이다.
- 이미지 적용 등 도중 취소가 어려운 작업은 실행 환경이 제공하는 취소·복구 절차를 따른다. Claude 종료를 보드팜 작업 취소로 간주하지 않는다.
- 실패 후 재시도는 새 실행 회차로 기록하고 이전 결과를 보존한다. 시간 제한·재시도 횟수·재개 조건은 연동별로 확정하며 무한 재시도를 허용하지 않는다.

### 2.7 빌드 위치와 선택형 보드팜 실행 환경

**빌드 위치는 Linux 서버이며, 선택 대상은 보드팜 연동 환경이다.** Windows에서 BSP를 빌드하는 요구사항은 현재 포함하지 않는다.

| 선택 | 이미지 이동과 실행 흐름 | 결과 수집 |
|---|---|---|
| Linux 보드팜 | Linux 빌드 → 지정 이미지 확인 → Linux에 연결된 환경으로 예약·이미지 적용·테스트 | Linux 연동 기능이 작업 상태·장비 로그·테스트 결과를 대시보드에 기록 |
| Windows 보드팜 | Linux 빌드 → Windows 실행 환경으로 이미지 전달·확인 → Windows에 연결된 환경으로 예약·이미지 적용·테스트 | Windows 연동 기능이 외부 작업 ID·상태·로그·결과를 Linux 대시보드로 전달 |

연동 상세 설계 제안:

- Linux가 전체 작업 상태의 기준을 관리하고, 각 보드팜 환경은 배정된 장비 작업을 수행한다. 환경마다 연결 확인·예약·실행·조회·취소·해제·결과 수집 기능을 같은 형식으로 연결한다.
- Windows 브라우저에서 화면을 여는 것만으로 로컬 장비 도구가 실행되지는 않는다. 기존 서비스/API를 사용할지 별도 로컬 실행 구성요소를 둘지 확인한다. Windows가 Linux에 접속해 배정 작업을 가져오는 방식도 후보로 두되 연결 방식은 아직 확정하지 않는다.
- 실행 전에 작업에 사용할 보드팜 환경을 선택·기록한다. 실행 중 환경을 바꾸어 같은 테스트를 중복 배정하지 않는다. 변경은 기존 작업 종료 또는 상태 확인 후 새 실행 회차부터 적용한다.
- Linux와 Windows의 파일 경로를 각각 관리한다. 소스·빌드 ID, 이미지 목록과 체크섬을 함께 전달하고 일치 확인 후 장비에 적용한다. 부트로더·커널·기타 이미지가 여러 개면 하나의 적용 목록으로 묶는다.
- Windows PC 종료·절전·네트워크 단절 시 해당 장비 작업을 연결 대기 또는 상태 확인 중으로 표시한다. 이미 배정한 작업을 자동으로 다른 환경에 다시 보내지 않는다.
- PC가 재접속하면 기존 외부 작업 ID로 진행·종료 여부와 저장된 결과부터 확인한다. 복구 불가능한 경우에만 실패 및 후속 조치를 결정한다.
- 보드팜 환경이 오프라인이어도 선행 그룹 완료 조건과 의존성이 허용하는 분석·코드 수정·Linux 빌드는 계속할 수 있다. 선행 그룹의 필수 장비 검증이 남아 있으면 나머지 모듈은 시작하지 않는다.
- 실행 구성요소의 등록·인증, 이미지 전송 방식, 로그 보관·전송 재시도, PC 실행 유지 방식은 구현 전에 확정한다. 별도 중앙 관리 서버가 반드시 필요한 구성은 아니다.

### 2.8 추가 검토안: Windows 대시보드와 상태 조회 분리

사용자가 로컬 PC 테스트 편의와 상태 조회 중심 구조를 제안했다. **아래는 검토안이며, 기존 Linux 대시보드 기본 배치를 변경한 확정 결정은 아니다.**

| 구성요소 | 제안 위치와 역할 |
|---|---|
| 대시보드 화면·조회 기능 | Windows PC. Linux 작업 상태와 Windows 테스트 상태를 읽어 표시 |
| 분석·수정·빌드 실행 및 기록 | Linux 서버. UI 연결과 독립적으로 작업을 지속하고 상태·로그·산출물 저장 |
| 로컬 보드팜 테스트 | Windows PC의 기존 연동 환경에서 실행·결과 기록. Linux 보드팜 선택도 유지 |
| 명령 전달 | 시작·재시도·프롬프트를 작업 ID·명령 ID와 함께 실행 측에 전달하고 접수·실행 결과 조회 |

- 단독 사용과 Windows 장비 테스트가 중심이면 Windows 대시보드가 운영을 단순하게 할 수 있다. 여러 사용자의 상시 접속·공유 상태 관리가 중요하면 Linux 중앙 대시보드도 유효하다.
- 대시보드는 화면을 그리면서 에이전트 로그를 임의 해석하거나 작업을 실행하지 않는다. 실행 측이 기록한 구조화된 상태를 조회하고, 사용자 명령은 별도 접수 경로로 전달한다.
- Linux 작업 상태는 Linux 실행 측이, Windows 테스트 상태는 Windows 실행 측이 갱신한다. 작업·모듈·단계·실행 회차·상태 버전·갱신 시각·근거 ID로 연결하며 같은 상태를 양쪽에서 덮어쓰지 않게 한다.
- 초기에는 SSH 또는 API로 주기적으로 읽는 방식이 후보이다. 공유 파일을 사용한다면 기록 중인 파일 노출 방지, 버전 확인과 동시 쓰기 방지 규칙이 필요하다. 구체적 방식은 아직 확정하지 않는다.
- Windows PC를 꺼도 이미 실행 중인 Linux 작업은 계속한다. 로컬 테스트는 대기하며 재접속 시 최신 상태와 미확인 명령을 확인한다. 오래된 상태는 마지막 갱신 시각과 연결 끊김 표시를 함께 보여준다.
- 창을 닫은 동안 다음 Linux 작업까지 자동 진행하려면 배정 대기열·선행 조건·재시도 기록도 Linux에 유지해야 한다. Windows 화면에만 작업 조정을 맡기지 않는다.
- 이번 문서·시안 변경은 상단 집계 표시이며, 이 배치를 실제 구현하거나 기본 배치로 전환한 것은 아니다.

## 4. 공통 상태와 완료 원칙

### 4.1 단계 상태

| 상태 | 의미 |
|---|---|
| 대기 | 선행 조건 충족 또는 실행 지시를 기다림 |
| 실행 중 | 분석·구현·검증 등 작업이 진행 중 |
| 완료 | 해당 단계의 완료 조건과 근거가 충족됨 |
| 실패 | 실행이 실패했으며 원인과 후속 조치가 필요함 |
| 검토 필요 | 사람의 판단 없이는 해당 작업을 진행하거나 완료할 수 없음 |
| 해당 없음 | 적용 대상이 아님을 근거와 함께 확인함 |
| 상태 확인 중 | 연결 단절·재시작 등으로 실제 실행 여부를 확인 중. 확인 전 중복 배정 금지 |
| 재검증 필요 | 소스·의존성·테스트 조건 변경으로 이전 검증을 현재 기준에 적용할 수 없음 |

작업 전체에는 중지 요청·중지·재개 상태도 필요하다. 새 작업 배정 중지와 진행 중 작업 취소를 구분하는 §2.6의 제안을 기준으로 연동별 상세 동작을 결정한다. 상태 확인 중·재검증 필요는 이번 검토에서 추가한 상태 제안이다.

각 모듈 단계에는 선행 조건 대기와 보드 예약 대기 사유도 표시한다. 대기는 실패와 구분하며, 실행 상태와 검증 결과를 별도 기록한다.

전체 OS Upgrade 상태는 실행 여부와 실패 건수를 분리하는 다음 집계 기준을 제안한다.

- **진행 중:** 실행 또는 재개 가능한 작업이 남아 있다. 일부 실패가 있어도 독립 작업이 계속되면 `진행 중 · 실패 1 · 검토 대기 2`처럼 표시한다. 사람 검토·자원 대기만으로 실패 처리하지 않는다.
- **실패:** 필수 작업 실패로 현재 실행을 종료했거나 복구 없이 더 진행할 수 없다. 실패한 모듈·단계와 후속 조치를 표시한다. 전체를 실패로 종료하는 조건은 실행 정책에서 확정한다.
- **완료:** 필수 모듈 작업, 통합 빌드, 필수 검증·보드팜 테스트 및 관련 검토 결정 반영이 끝났다. 최종 사람 검토는 다음 전체 단계에서 처리한다.
- 중지 여부는 위 상태와 별도로 표시한다. 실패 해결 후 재실행하면 최신 상태를 집계하되 이전 실패 이력은 유지한다.

### 4.2 완료 원칙

- 코드 수정 완료와 검증 완료를 구분한다.
- 신규 OS에 이미 반영된 변경도 확인 근거와 필요한 검증을 남긴다.
- 해당 없음은 실패나 미진행을 숨기는 용도로 사용하지 않는다.
- 필수 검증과 사람 검토가 남아 있으면 최종 완료로 처리하지 않는다.
- 검증 불가 항목은 이유와 영향을 기록하고, 예외 허용이 필요하면 사람 검토로 연결한다.

## 5. 전체 흐름과 모듈별 상세 흐름

### 5.1 상단 단계별 종합 진행도

상단은 **요구사항 분석 % 완료 / 구현 % 완료 / 검증 % 완료 / 빌드 % 완료 / 테스트 % 완료**의 다섯 항목을 나란히 표시한다. 좁은 화면에서는 여러 줄로 재배치한다. 화살표는 사용하지 않으며 각 값은 아래 모듈들의 실제 단계 상태에서 계산한다.

| 상단 항목 | 모듈 상세 단계와의 연결 | 표시 내용 |
|---|---|---|
| 요구사항 분석 | 각 모듈의 요구사항 분석 | 완료율, 완료/대상 작업 수, 대기·실패·검토 수 |
| 구현 | 디자인 변경 + 코드 구현 | 두 상세 단계의 필수 작업을 합산한 완료율 |
| 검증 | 모듈별 검증 | 필수 개별 검증의 완료율 |
| 빌드 | 모듈별 빌드 | 빌드 완료율 |
| 테스트 | 모듈별 보드팜 테스트 | 장비 테스트 완료율. 연결·예약 성공은 완료로 계산하지 않음 |

- 다섯 항목은 병렬로 조회하는 집계 지표이며, 표시 순서는 실행 순서 변경을 의미하지 않는다. 모듈 상세의 선후 관계와 부트로더 선행 그룹 전체 완료 조건을 유지한다.
- 구현에 디자인 변경과 코드 구현을 함께 집계하는 것은 여섯 상세 단계를 다섯 상단 항목에 빠짐없이 연결하기 위한 초기 설계안이다.
- 상단 검증과 테스트는 같은 결과를 중복 계산하지 않는다. 현재 모듈별 검증은 검증 항목에, 보드팜 테스트는 테스트 항목에 각각 연결한다.
- 단계별 완료율은 해당 단계에 속한 전체 적용 대상 필수 작업의 완료 가중치 / 전체 가중치로 계산한다. 초기 동일 가중치 기준으로 구현은 설계·코드 두 작업을 각각 센다. 모듈 완료율을 단순 평균하지 않는다.
- 선행 대기 중인 나머지 모듈도 대상이므로 분모에 포함한다. 아직 시작하지 않은 모듈을 제외하여 진행률을 높이지 않는다.
- 승인된 해당 없음은 분모에서 제외한다. 전체 대상이 없으면 100% 대신 해당 없음, 대상이 아직 정의되지 않았으면 산정 중을 표시한다.
- 재시도 접수·실행 중·실패·검토 대기는 완료에 포함하지 않는다. 재검증이 필요해지면 현재 기준의 완료 집계에서 제외하고 변경 이유를 남긴다.
- 상단의 요구사항 분석은 모듈별 분석 집계다. 실행 전 초기 범위 정리가 끝났다는 이유로 모든 모듈의 분석을 완료 처리하지 않는다.
- 통합 빌드·전체 회귀 검증·최종 사람 검토는 별도 완료 조건으로 남긴다. 다섯 항목 모두 100%여도 이 조건이 남아 있으면 전체 업그레이드 최종 완료가 아니다.

예를 들어 5개 모듈 중 선행 2개만 작업하고 나머지 3개가 선행 대기인 시안에서, 선행 모듈의 분석·설계·코드·빌드·개별 검증은 모두 완료되고 보드팜은 1개만 완료되었다면 상단은 분석 40%, 구현 40%, 검증 40%, 빌드 40%, 테스트 20%로 표시한다.

#### 내부 작업 수명주기와 완료 조건

기존의 초기 범위 정리·OS Upgrade 실행·최종 검토는 내부 절차로 유지한다. 화면 상단을 이 세 단계의 화살표로 표시하지 않는다.

| 전체 단계 | 주요 작업 | 화면 표시 | 완료 조건 |
|---|---|---|---|
| 요구사항 분석 | 실행 환경·소스 기준·벤더 변경 목록·대상 모듈·선행 그룹·검증 범위의 초기 정리 | 기준 확인 상태, 발견 모듈 수, 초기 계획과 검토 요청 | 대상·그룹·초기 실행 조건이 정리됨. 나머지 그룹의 모듈별 상세 분석 완료를 이 단계의 조건으로 요구하지 않음 |
| OS Upgrade | 모듈별 설계·구현·빌드·검증, 보드팜 테스트, 통합 빌드·회귀 검증 | 진행 중 / 실패 / 완료, 선행 모듈 진행률, 병렬 모듈 진행률, 통합 검증 상태 | 필수 변경과 검증 완료, 이 단계에 영향을 주는 검토 결정 반영 |
| 최종 완료 | 변경·검증 결과와 예외 검토, 남은 이슈 정리, 최종 사람 검토 | 검토 대기 / 완료, 최종 검토자·결정·완료 시점 | 최종 검토 완료 및 필수 미해결 항목 없음 |

위 표는 내부 실행 절차다. 화면에서는 다섯 종합 완료율, 전체 실행 상태, 그룹별 진행률과 통합 검증·최종 검토 상태로 나누어 보여준다. 최종 검토 진입과 최종 완료를 구분한다.

전체 첫 단계는 실행 기준과 초기 범위를 정하는 과정이다. 모듈별 벤더 의도·신규 OS 반영 여부 상세 분석은 OS Upgrade 안에서 해당 그룹의 실행이 허용된 뒤 수행한다. 이를 구분하여 선행 완료 조건과 전체 분석 완료 조건 사이의 순환 대기를 방지한다.

### 5.2 Start 버튼에서 작업 시작까지

1. 대시보드에서 대상 BSP, 현재·목표 OS, 서버·계정·폴더, 소스 기준과 실행 범위를 확인한다.
2. Linux 빌드 설정, 단계별 실행 정책과 보드팜 연결 위치를 선택한다. 대시보드 서버가 경로·권한·실행 환경과 중복 실행 여부를 확인하고 작업을 기록한다. 별도 작업 관리자 서비스는 필요하지 않다.
3. 지정 Linux 계정의 프로젝트 작업 폴더에서 Claude Code 세션을 생성한다. 다른 작업 서버인 경우 SSH로 연결한다.
4. 작업 ID와 세션 ID를 연결하고 CLAUDE.md와 OS Upgrade Agent 지침을 적용한다.
5. 대상·범위와 시작 명령을 전달하여 요구사항 분석부터 시작한다.
6. 부트로더 관련 선행 그룹부터 실행한다. 선행 그룹 전체 완료 후 나머지 모듈을 실행하며, 각 그룹 안에서는 분석 병렬·수정 및 빌드 순차 정책을 따른다. 선택한 환경의 보드팜 테스트 및 통합 검증 결과를 수집한다.
7. 상태·로그·결과를 저장하고 전체 및 모듈별 흐름에 반영한다.
8. 진행 중 새로운 사람 판단이 필요하면 내부 검토 항목과 Jira로 연결한다. 영향받는 작업만 대기시키고, 선행 그룹 완료 조건을 충족한 독립 작업은 계속 배정한다.

사람 검토 발생 시 부분 대기·독립 작업 계속 원칙은 확정했다. Start 기본 실행 범위와 분석·계획 후 최초 확인을 둘지는 아직 미결정이며, 단계마다 승인을 반복하는 정책으로 해석하지 않는다. 본 문서 업데이트는 실제 코드 수정이나 장비 적용 실행을 의미하지 않는다.

### 5.3 OS Upgrade 내부의 두 작업 그룹

| 그룹 | 구성 | 표시 내용 |
|---|---|---|
| 부트로더 관련 선행 모듈 | 부트로더 및 다른 모듈 진행에 필요한 것으로 확인된 관련 작업 | 그룹 진행률(%), 모듈별 상태, 선행 조건, 부팅 검증 결과, 후속 작업을 막는 항목 |
| 나머지 모듈(선행 완료 후 병렬 분석) | 선행 그룹 외 드라이버·모듈. 선행 그룹 전체 완료 전 실행 금지, 해제 후 분석 병렬·수정 및 빌드 순차 | 그룹 전체 진행률(%), 선행 조건 충족 여부, 완료·실행·실패·검토·대기 수, 실제 실행 정책 |

- 선행 모듈 목록은 실제 BSP와 의존성 분석으로 확정한다. 부트로더 종류나 관련 모듈을 임의로 확정하지 않는다.
- 부트로더 관련 선행 모듈이 모두 완료되어야 나머지 모듈을 시작한다. 이 조건은 나머지 모듈의 분석을 포함한 모든 단계와 재시도에 적용한다.
- 전체 요구사항 분석에서 소스 기준·모듈 목록·그룹 구성을 정리할 수 있지만, 선행 완료 전 나머지 모듈의 개별 분석을 실행하지 않는다.
- 선행 그룹의 완료는 해당 필수 변경·빌드·검증·보드팜 및 관련 사람 결정 반영이 끝났다는 뜻이다. 단순 코드 수정 완료나 화면상 반올림된 100%로 실행을 허용하지 않는다.
- 선행 그룹에서 검토나 실패가 발생하면 같은 선행 그룹 안의 독립 작업은 계속할 수 있다. 나머지 그룹은 전체 선행 완료까지 대기한다.
- 특정 부팅 이미지나 선행 산출물이 필요한 빌드·장비 검증은 해당 조건이 충족될 때 실행한다.
- 공통 소스·빌드 자원·보드 사용이 충돌하는 작업은 순서를 조정하고 대기 사유를 표시한다.
- 모듈 화면에 선행 모듈, 필요한 산출물과 현재 막힌 단계를 표시한다.
- 통합 빌드 및 전체 회귀 검증은 그룹 진행률과 별도로 표시하고, OS Upgrade 완료 판단에 포함한다.
- 선행 완료 후 실행을 허용한 기준 버전을 기록한다. 이후 선행 결과가 실패·재검증 필요로 바뀌면 나머지 그룹의 신규 실행·재시도를 막고, 진행 중 작업은 §2.6의 중지 절차에 따라 안전하게 정리하며 결과 유효성을 다시 확인한다.

#### 5.3.1 초기 실행 정책과 향후 병렬 확장

| 작업 | 초기 정책 | 향후 확장 시 조건 |
|---|---|---|
| 요구사항·변경 분석 | 실행이 허용된 그룹 안에서 독립 모듈 병렬 분석 | 동일한 고정 소스 기준 사용, 모듈별 분석 결과 분리, 서버 자원에 맞춘 동시 실행 수 |
| 코드 수정 | 순차 실행 | 모듈별 수정 사본 분리, 공통 파일·의존성 충돌 확인, 통합 반영 순서 확정 후 병렬 허용 |
| 모듈·통합 빌드 | Linux 서버에서 순차 실행 | 고정된 소스 입력, 독립 빌드 결과 폴더, 자원·도구 사용 제한 확인 후 병렬 허용 |
| 보드팜 테스트 | 선택한 환경과 실제 보드 가용성에 따라 배정 | 동일 보드 독점 사용, 이미지 및 외부 작업 ID 추적. 동시 보드 수는 환경 확인 후 결정 |

- 초기에는 동일 BSP 작업 사본을 쓰는 코드 수정과 빌드를 하나의 배정 대기열에서 순차 처리하는 방안을 제안한다. 다른 모듈의 빌드 중 같은 소스를 수정하지 않는다. 통합 반영과 이슈 프롬프트의 수정 요청도 같은 규칙을 적용한다.
- 앞 작업이 사람 판단 때문에 대기하면 실행 자원 점유를 해제하고, 선행 그룹 완료 조건과 의존성이 허용하는 다음 작업을 선택한다.
- 병렬 분석은 수정 중인 작업 폴더의 변하는 내용을 읽지 않고 고정된 기준을 사용한다. 소스 수정이 필요해진 분석 작업은 수정 대기열로 넘긴다.
- 향후 단계별 동시 실행 수를 조정할 수 있게 설계하되, 값만 높여 공유 소스에서 동시에 수정·빌드하지 않는다. 작업 사본·빌드 결과 분리와 충돌 검증을 먼저 갖춘다.
- 화면의 병렬 그룹은 수정·빌드가 현재 병렬 실행된다는 뜻이 아니다. 초기 화면에 `선행 전체 완료 후 · 분석 병렬 / 수정·빌드 순차` 정책을 함께 표시한다.

### 5.4 각 모듈의 상세 흐름

**요구사항 분석 → 디자인 변경 → 코드 구현 → 빌드 → 검증 → 보드팜 테스트 → 모듈 완료**

보드팜 연결·예약 상태는 테스트 단계와 별도로 보여준다. 보드 연결 및 준비는 앞 단계와 병행할 수 있으며, 실제 테스트는 필요한 이미지와 조건이 충족된 뒤 실행한다.

| 단계 | 작업 내용 | 주요 결과물 | 완료 조건 |
|---|---|---|---|
| 요구사항 분석 | 벤더 변경 목적, 신규 OS 반영 여부, 기능·호환성 요구사항, 의존성 분석 | 변경 목록, 요구사항, 분류 근거, 선행 조건, 검토 요청 | 변경별 처리 방향과 검증 요구사항 기록. 미결정 사항의 영향 범위 명시 |
| 디자인 변경 | 신규 API·인터페이스·초기화·전원 처리 등에 맞는 이식 설계 | 설계 변경 이유, 대안, 영향 범위, 수정 파일, 구현 지시 | 구현 범위·완료 조건 정의. 의존하는 사람 결정 해결 |
| 코드 구현 | Codex / OpenCode가 벤더 변경 의도를 신규 OS에 반영 | 코드 변경, 커밋·차이, 실행 로그 | 계획한 변경 반영 또는 수정 불필요 근거 확인 |
| 빌드 | 모듈 및 필요한 이미지 빌드, API·설정·의존성 확인 | 빌드 로그, 소스 기준, 산출물 식별 정보 | 해당 모듈에 필요한 빌드 성공 |
| 검증 | 정적 확인, 자동 테스트, 기능·회귀 확인 등 모듈 검증 수행 | 테스트 케이스, 통과·실패·미수행 결과, 근거 | 정의된 필수 검증 통과 또는 승인된 예외 기록 |
| 보드팜 테스트 | 보드 예약·이미지 준비 후 실제 장비에서 필요한 검증 실행 | 보드·이미지·작업 ID, 장비 로그, 테스트 결과 | 필수 장비 검증 통과 또는 승인된 제외·예외 기록 |
| 모듈 완료 | 필수 단계와 검토 결정 반영 확인 | 모듈 결과 요약, 남은 예외, 완료 시점 | 필수 단계 완료 및 미해결 필수 이슈 없음 |

- 디자인 변경은 코드 수정 전의 설계 판단을 의미하며, UI 디자인 변경과 구분한다.
- 신규 OS에 이미 반영된 수정은 디자인·코드 구현을 해당 없음으로 처리할 수 있다. 확인 근거를 남기고 필요한 빌드·검증은 수행한다.
- 전체 분석 화면은 초기 범위와 이후 모듈 분석 결과를 함께 조회하되, 같은 분석을 전체 단계와 모듈 단계에서 중복 계산하지 않는다. 모듈 상세 분석을 첫 단계의 완료 조건으로 중복 요구하지 않는다.
- 개별 모듈 완료는 통합 빌드·전체 회귀 검증·최종 검토 완료를 의미하지 않는다.

#### 5.4.1 통합 이미지와 모듈 검증의 선후 관계

다음 순서를 설계 보완안으로 제안한다. 모듈 완료와 통합 이미지 생성이 서로를 기다리는 상황을 방지한다.

1. 먼저 선행 그룹의 준비된 변경을 순차 반영하고, 해당 그룹 검증에 필요한 이미지를 Linux에서 빌드한다. 나머지 모듈의 작업 완료를 조건으로 삼지 않는다.
2. 선택한 보드팜 환경에 이미지를 전달·확인하고 선행 그룹의 필수 부팅·장비 검증 및 사람 결정 반영을 마친다.
3. 선행 그룹 전체 완료 후 나머지 모듈의 실행을 허용한다. 준비된 변경을 순차 반영하고 검증용 통합 이미지를 만든다.
4. 나머지 모듈의 장비 검증은 해당 검증용 이미지로 수행한다. 모든 모듈의 장비 검증 완료를 이미지 생성 조건으로 삼지 않는다.
5. 최종 통합 기준에서 필수 회귀 검증을 수행한다. 이전에 완료된 모듈도 변경 영향을 받으면 재검증한다.

나머지 그룹의 진입 조건은 선행 그룹 전체 완료로 고정한다. 선행 그룹 검증에 아직 대기 중인 나머지 모듈의 변경이 꼭 필요하다면 순환 의존으로 기록하고, 필요한 모듈을 선행 그룹에 포함할지 Jira에서 결정한다. 조건을 임의로 우회하지 않는다. 그룹 안의 세부 선행 조건은 필요한 변경·산출물·검증 결과로 정의한다.

#### 5.4.2 벤더 변경 추적과 검증 유효성

다음은 변경 누락과 오래된 검증 결과 사용을 방지하기 위한 설계 제안이다.

- 벤더 변경마다 ID를 부여하고 기존 원본·벤더 수정본·신규 원본의 기준, 목적, 관련 모듈을 기록한다.
- 변경별 처리 방향을 신규 OS에 이미 반영 / 이식 필요 / 제외 승인 / 판단 필요로 구분한다. 모듈 진행률만으로 변경 누락 여부를 판단하지 않는다.
- 변경 ID를 설계, 구현 결과, 빌드·테스트 결과 및 Jira 결정에 연결한다. 최종 검토 시 미분류·미반영·근거 없는 제외 항목이 없는지 확인한다.
- 검증 결과에는 소스 기준, 빌드 설정·도구, 이미지 목록·체크섬, 보드 및 테스트 버전을 연결한다.
- 관련 소스·의존 산출물·테스트 조건이 바뀌면 영향받는 결과를 재검증 필요로 표시한다. 영향 범위를 판단할 수 없으면 관련 검증을 다시 요구하거나 사람 검토로 연결한다.
- 과거 통과 기록은 보존하지만 현재 기준의 완료 근거로 자동 재사용하지 않는다. 필요한 재검증을 작업 목록과 진행률에 반영한다.

### 5.5 보드팜 연동 상태와 검증 결과

| 구분 | 상태 예시 | 표시 항목 |
|---|---|---|
| 연결 | 미설정 / 연결 확인 중 / 연결됨 / 오프라인 / 연결 실패 | Linux 또는 Windows 환경, 마지막 확인 시점, 오류 사유 |
| 보드 사용 | 미예약 / 예약 대기 / 예약됨 / 사용 중 / 해제됨 | 보드 ID·종류, 예약 및 사용 작업 |
| 이미지 준비 | 전달 대기 / 전달 중 / 일치 확인 / 적용 중 / 적용 완료 / 실패 | 소스·빌드 ID, 이미지 목록·체크섬, 수신 위치 |
| 테스트 실행 | 대기 / 실행 중 / 완료 / 실행 실패 | 테스트 작업 ID, 시작·종료 시점, 로그 |
| 테스트 결과 | 미검증 / 통과 / 실패 / 검토 필요 / 해당 없음 | 케이스별 결과, 실패 원인, 재검증 이력 |

- 보드팜 연결 성공은 테스트 통과를 의미하지 않는다.
- 연결 실패·예약 대기·테스트 실패를 구분하고 관련 이슈로 연결한다.
- 테스트 결과를 해당 모듈, 실제 보드와 실행한 이미지에 연결한다. 다른 이미지의 결과로 완료 처리하지 않는다.
- 재시도 시 이전 실패 결과를 보존하고 최신 실행 결과를 별도로 표시한다.
- 보드팜 서비스, API, 장비 목록, 예약 및 이미지 적용 방식은 아직 미정이다.
- 보드팜 연결 위치 선택은 확정했으며 구체적 실행 구성요소와 통신 방식은 §2.7의 제안을 환경 확인 후 결정한다.
- 보드 독점 사용과 예약 만료·연장을 관리하는 방안을 제안한다. 실행 여부를 확인할 수 없는 보드를 예약 만료만으로 즉시 재배정하지 않는다.
- 종료·취소 시 보드 복구 상태를 확인하고 사용을 해제한다. 이미지 적용·부팅 실패 후 복구되지 않은 보드는 사용 불가로 표시하고 후속 배정을 보류한다. 복구 명령과 수동 개입 기준은 실제 보드팜 환경에서 확정한다.

- 담당 에이전트·사람, 현재 단계, 시작·종료 시점
- 단계별 상태와 완료 조건, 진행률, 선행 조건·대기 사유
- 변경 파일, 소스·커밋 기준, 설계 근거와 구현 결과

- Linux 빌드 위치, 선택한 보드팜 환경과 연결 상태, 이미지 전달 상태, 실제 적용 이미지 및 외부 작업 ID

### 5.7 모듈별 접기·펼치기 화면

모듈 목록은 선행 그룹과 병렬 그룹으로 나누고, 각 모듈을 펼치고 접을 수 있는 표 형태로 표시한다. 여러 모듈을 동시에 펼쳐 비교할 수 있다.

**접힌 행:** 펼침 표시, 모듈명·담당자, 현재 단계, 상태, 진행률(%)과 작은 진행 막대를 표시한다.

| 모듈 / 담당 | 현재 단계 | 상태 | 진행률 |
|---|---|---|---|
| Bootloader / Codex | 보드팜 | 실패 · 재시도 가능 | 83% |
| Boot config / OpenCode | 모듈 완료 | 완료 | 100% |
| Ethernet / Codex | 선행 그룹 완료 대기 | 선행 대기 | 0% |
| Camera / Claude | 선행 그룹 완료 대기 | 선행 대기 | 0% |

위 값은 화면 시안의 예시이며 실제 작업 데이터가 아니다.

- 행을 접어도 현재 처리 단계와 실패·검토·대기 여부는 유지해서 보여준다. 선행 그룹 완료 전 나머지 모듈은 `선행 대기 · 부트로더 관련 모듈 완료 필요`를 표시한다.
- 필수 단계가 모두 완료된 모듈은 현재 단계를 모듈 완료, 상태를 완료로 표시한다.
- 현재 단계는 실행 중인 단계 또는 진행을 막고 있는 실패·검토·대기 단계로 정한다. 여러 단계가 병행 중이면 대표 단계와 추가 실행 수를 표시하는 방안을 제안한다.
- 색상만으로 상태를 구분하지 않고 상태 문구와 기호를 함께 표시한다.

**펼친 행:** 해당 모듈 바로 아래에 상세 표를 표시한다.

| 열 | 표시 내용 |
|---|---|
| 단계 | 요구사항 분석, 디자인 변경, 코드 구현, 빌드, 검증, 보드팜 |
| 상태 | 완료·실행 중·실패·검토 필요·대기·해당 없음 및 제안된 상태 확인 중·재검증 필요와 상태 기호 |
| 작업·결과 | 수행 내용, 결과 요약, 관련 파일 또는 로그 근거 |
| 상세 | 선택한 단계의 근거·로그·이슈·명령창을 여는 동작 |

- 현재 처리 단계의 행을 강조하고, 앞뒤 단계의 상태도 함께 보여준다.
- 상세 표 아래에 선행·대기 조건, 보드팜 연결, 보드 예약·사용, 테스트 실행 및 결과 요약을 표시한다.
- 보드팜 상세에는 선택한 Linux/Windows 환경, 마지막 연결 확인 시점과 이미지 전달·일치 확인 결과를 함께 표시한다. 모듈 요약에서는 대기 원인이 Jira 판단인지 수정·빌드 순서인지 보드팜 연결인지 구분한다.
- 단계별 상세 보기 또는 이슈·명령 열기로 해당 모듈·단계 문맥을 연결한다. 상세를 닫아도 모듈의 펼침 상태는 유지한다.
- 행을 펼치거나 접는 동작은 조회 동작이다. 에이전트 실행·재시도·Jira 생성은 별도 명령으로 처리한다.
- 키보드로도 펼치고 접을 수 있게 하고, 펼침 여부를 접근성 정보로 제공한다.
- 좁은 화면에서는 모듈 요약을 두 줄로, 상세 표를 단계별 행 묶음으로 재배치해 상태와 결과를 읽을 수 있게 한다.
- 초기 펼침 대상은 실패·검토 필요 모듈을 우선하는 방안을 제안한다. v0.4 시안에서는 기본적으로 Bootloader를 펼쳐 실패 단계와 재시도를 보여준다.
- 펼침 상태는 조회 상태로 보존한다. 사용자별 저장 범위와 유지 기간은 실제 구현 시 정한다.

### 5.8 실패한 단계 재시도

**실패 단계의 재시도 버튼은 사용자 요구사항으로 확정했다.** 아래 실행·기록 규칙은 상세 설계 제안이다.

- 펼친 상세 표의 실패한 단계 행에 `재시도` 버튼을 표시한다. 대상 단계·실패 이유·마지막 실행 회차와 로그를 함께 확인할 수 있게 한다.
- 버튼은 해당 단계의 재실행 요청을 접수한다. 전체 모듈을 처음부터 다시 실행하지 않으며, 재실행 전 입력·선행 조건·Jira 결정·실행 환경을 확인한다.
- 나머지 그룹의 재시도에도 선행 그룹 전체 완료 조건을 적용한다. 조건 미충족, 미결정 Jira, 상태 확인 중 또는 중복 실행 중이면 버튼을 비활성화하고 이유를 표시한다.
- 접수 후 같은 버튼을 반복 눌러 중복 실행하지 못하게 한다. 자원이 사용 중이면 `재시도 대기`, 배정 후에는 `실행 중`을 표시하며 수정·빌드 순차 정책을 따른다.
- 재시도는 새 실행 회차로 기록하고 이전 실패·로그를 보존한다. 실패한 보드팜 작업은 기존 외부 작업이 종료되었는지, 보드가 복구되었는지 확인한 뒤 배정한다.
- 재시도 성공이 곧 모듈 완료를 뜻하지 않는다. 후속 필수 검증을 계속하며 소스·이미지가 바뀌면 해당 결과를 재검증 필요로 처리한다.
- 코드 구현 단계 재시도 시 남아 있는 변경을 먼저 확인한다. 같은 변경을 중복 적용하거나 사용자 수정을 덮어쓰는 초기화를 자동 수행하지 않는다.
- 새 판단 없이 해결할 수 없는 실패는 프롬프트 명령 또는 Jira 검토로 연결한다. 재시도 버튼을 누른 사실을 새 설계·예외의 승인으로 취급하지 않는다.

## 6. 전체 및 그룹별 진행률 표시

진행률은 코드 수정량이나 실행 시간이 아니라 필수 작업의 완료 조건을 기준으로 계산한다.

| 지표 | 표시 내용 |
|---|---|
| 전체 진행률 | 요구사항 분석, 모듈별 필수 작업, 통합 검증 및 최종 검토를 포함한 완료율 |
| 단계별 종합 완료율 | 전체 대상 모듈의 분석·구현·검증·빌드·테스트별 완료율. §5.1의 매핑으로 계산 |
| 이번 실행 범위 진행률 | 분석만 실행 등 Start에서 선택한 범위의 완료율. 전체 업그레이드 진행률과 별도 표시하는 방안 제안 |
| 선행 그룹 진행률 | 부트로더 관련 선행 모듈의 필수 작업 완료율(%) |
| 병렬 그룹 진행률 | 나머지 병렬 모듈의 필수 작업 완료율(%) |
| 모듈별 진행률 | 요구사항 분석·디자인·코드·빌드·검증·보드팜 필수 작업의 완료율 |
| 보드팜 검증 현황 | 연결 상태, 예약 대기 수, 실행 중 테스트, 통과·실패·미검증 수 |
| 통합 검증 현황 | 통합 빌드 및 전체 기능·회귀 검증 상태 |
| 사람 검토 대기 | 해결되지 않은 검토 항목과 진행을 막는 작업 수 |

계산 원칙:

- 초기에는 정의된 필수 작업 단위에 동일 가중치를 적용하는 방안을 제안한다. 모듈별 필수 테스트가 여러 건이면 작업 단위를 명시한다.
- 완료 작업 가중치 합 / 적용 대상 필수 작업 가중치 합 × 100으로 계산하는 방안을 기본으로 한다. 실행 중인 작업의 임의 추정치는 완료로 계산하지 않는다.
- 전체 요구사항 분석 표시와 모듈 분석, 그룹별 집계 등 같은 작업을 중복 합산하지 않는다.
- 그룹 진행률의 단순 평균으로 전체 진행률을 계산하지 않는다. 전체는 원래 필수 작업을 기준으로 집계한다.
- 상단 다섯 단계 완료율의 단순 평균으로 전체 진행률을 계산하지 않는다. 단계별 작업 수와 통합 검증·최종 검토의 포함 범위가 다르므로 같은 원본 작업 기록으로 각각 계산한다.
- 모듈별 난이도 가중치를 적용할 경우 기준과 변경 이력을 공개한다.
- 해당 없음 항목은 근거 확인 후 계산 대상에서 제외한다. 적용 대상 작업이 없는 그룹은 100% 대신 해당 없음으로 표시한다.
- 분석·계획 중 작업이 추가되면 진행률이 내려갈 수 있으며 변경 이유를 표시한다.
- 사람 검토 결정 후 코드 반영·재검증이 필요하면 그 작업이 끝나기 전까지 완료하지 않는다.
- 보드팜이 필수인 모듈은 미연동·예약 대기·미검증 상태에서 완료하지 않는다. 제외·예외는 사람 결정과 이유를 남긴다.
- OS Upgrade 내부 완료와 최종 완료를 구분한다. 최종 검토까지 끝나야 전체 100% 및 최종 완료로 표시한다.
- 정확한 작업 단위, 가중치 및 예외 처리 산식은 구현 설계 시 확정한다.
- 분석만 실행한 작업은 선택 범위에서 완료될 수 있지만 전체 업그레이드 완료를 뜻하지 않는다. 실행 범위를 명시하여 서로 다른 100%가 혼동되지 않게 한다.
- 재검증 필요 항목은 현재 기준의 완료 분자에서 제외하고 진행률 변경 사유를 표시하는 방안을 제안한다. 작업·의존성 기준이 바뀌면 집계 기준 버전도 기록한다.
- 진행률은 작업 완료율이며 남은 시간의 추정치가 아니다. 원인별 대기 수와 실패·재검증 수를 함께 표시한다.
- 선행 그룹 완료 전 나머지 그룹은 선행 대기로 표시한다. 실행 허용 여부는 완료 조건과 결과 유효성으로 판단하며 진행률 숫자만으로 대기를 해제하지 않는다.

## 7. 이슈 대응 프롬프트 명령창

### 7.1 목적과 입력

이슈 상세 화면에서 관련 문맥을 확인하고 에이전트에 후속 작업을 지시한다.

명령에 연결할 정보:

- 업그레이드 작업 및 이슈 ID
- 대상 모듈과 적용 범위
- 오류 로그, 코드 변경, 이전 실행 결과
- 이전 수정·검증 시도
- 관련 Jira 결정과 작업 제약
- 사용자가 입력한 프롬프트

### 7.2 명령 예시

- 이 빌드 오류의 원인을 분석하고 수정 방안을 정리해줘.
- 해당 모듈의 벤더 수정 의도가 신규 API에서도 유지되는지 확인해줘.
- Jira에 기록된 결정에 따라 해당 모듈을 수정하고 재검증해줘.

예시는 기능 설명이며 실제 실행 지시가 아니다.

### 7.3 처리 흐름

**이슈 선택 → 문맥·적용 범위 확인 → 명령 접수 → 실행 → 결과 기록 → 재검증 → 이슈 해결 여부 판단**

- 명령 작성자, 시점, 대상 에이전트, 적용 범위와 결과를 기록한다.
- 동일 모듈 또는 공유 소스·빌드 자원의 실행 중 작업과 충돌하면 대기 상태로 접수한다. 프롬프트를 통한 수정도 §5.3의 선행 그룹 완료 조건과 순차 실행 정책을 따른다.
- 명령 실행 성공과 이슈 해결을 구분한다. 관련 검증을 통과해야 해결로 판단한다.
- 사람 검토 사항이 발견되면 검토 목록 및 Jira 처리 흐름으로 연결한다.
- 명령이 기존 계획이나 결정 범위를 바꾸면 변경 이유와 영향을 남긴다.
- 명령 ID로 접수·실행·결과를 연결하고 중복 전송을 구분하는 방안을 제안한다. 실행 중 세션에 새 프롬프트를 무조건 끼워 넣지 않고 차례를 기다리거나 명시적인 중지·취소 절차를 따른다.
- 대기 중 소스 또는 Jira 결정이 바뀌면 실행 직전에 문맥과 적용 범위를 다시 확인한다. 새 판단이 필요한 부분만 검토로 넘기고 기존 결정 범위를 임의로 넓히지 않는다.

## 8. 사람 검토 및 Jira 목록

### 8.1 검토 대상

- 벤더 변경의 의도가 불명확한 경우
- 신규 OS에 이미 반영되었는지 판단하기 어려운 경우
- 구현 대안 사이에서 기능·유지보수·호환성 선택이 필요한 경우
- 검증 불가 또는 실패 항목에 대해 예외 판단이 필요한 경우
- 기존 계획을 넘어서는 변경이 필요한 경우

### 8.2 목록 필드

| 필드 | 내용 |
|---|---|
| 검토 항목 ID | Jira 생성 전부터 유지하는 내부 식별자 |
| 관련 작업·모듈 | 업그레이드 작업, 변경사항, 모듈 및 이슈 |
| 질문·사유 | 사람이 결정해야 할 질문과 검토 필요 이유 |
| 근거 | 코드 차이, 분석, 로그, 테스트 결과 |
| 대안·권장 방향 | 선택지와 각각의 영향, 에이전트의 제안 |
| 영향 범위 | 해당 모듈 또는 다른 작업의 진행에 미치는 영향 |
| 담당자 | 검토 담당자 |
| Jira 정보 | 생성 상태, 티켓 키, 링크, Jira 처리 상태 |
| 결정 결과 | 선택한 방향, 결정 이유, 결정자 및 시점 |
| 후속 작업 | 결정에 따른 구현·재검증 및 반영 상태 |

### 8.3 처리 흐름

**새 판단 필요 발견 → 내부 검토 항목 기록 및 영향 범위 지정 → Jira 연결 → 사람 검토·결정 → 결정 기록 → 해당 작업 재개·구현·검증 → 검토 항목 완료**

- 진행 중 새 판단이 필요한 사항을 Jira 티켓으로 연결한다. 기존 결정과 실행 범위로 처리할 수 있는 작업은 선행 조건에 따라 계속 진행한다.
- 검토 항목에 의존하는 단계와 후속 작업만 대기시키고, 선행 그룹 완료 조건을 충족한 독립 작업은 계속한다. 선행 그룹의 미결정 검토는 그룹 전체 완료를 막으므로 나머지 그룹도 대기한다.
- 단순 빌드 실패나 연결 오류는 우선 실행 이슈로 기록한다. 새로운 설계 선택·범위 변경·예외 허용 등 사람 판단이 필요해질 때 Jira 검토로 전환한다.
- Jira 연결 원칙은 확정했다. 자동 생성 실행 방식과 프로젝트별 필수 입력값은 실제 Jira 환경 확인 후 결정한다.
- Jira 생성 실패 시에도 내부 검토 항목을 유지하고 재시도 상태를 표시한다.
- 동일 검토 항목으로 중복 티켓을 생성하지 않는다.
- Jira 결정 완료와 코드 반영·검증 완료를 구분한다.
- Jira 처리 상태의 동기화 방식과 주기는 연동 설계 시 확정한다.

다음 동기화 규칙은 설계 보완안이다.

- 사람 결정의 기준은 Jira의 명시된 결정 내용으로, 실행·구현·검증 상태의 기준은 대시보드 기록으로 구분한다. 양쪽에서 같은 상태를 서로 덮어쓰지 않는다.
- Jira 완료 상태만으로 후속 구현을 시작하거나 검토 항목을 완료하지 않는다. 결정 내용·결정자·적용 대상 버전을 확인한 뒤 실행 범위와 대기 해제 대상을 정한다.
- Jira 생성 응답을 받지 못했으면 내부 검토 ID로 기존 티켓부터 확인한다. 생성 여부가 불명확한 동안 새 티켓을 반복 생성하지 않는다.
- Jira 장애가 나도 내부 검토 항목과 영향받는 작업의 대기를 유지한다. 실행이 허용된 독립 작업은 계속하며 동기화 복구 후 연결 상태를 확인한다.
- 중복·지연된 변경 알림이 와도 같은 결정을 중복 실행하거나 최신 결정을 과거 상태로 되돌리지 않도록 결정 버전과 반영 이력을 기록한다.
- 초기 동기화는 Linux 서버에서 Jira를 주기적으로 조회하는 방안을 우선 검토한다. 웹훅을 사용하면 외부 연결 가능 여부와 알림 누락 시 재조회 방법을 확인한다.
- Jira가 Cloud인지 사내 설치형인지, 사용할 API·인증·프로젝트·이슈 유형은 아직 미정이다. 환경에 맞는 필드와 동기화 방식을 별도로 확인한다.

## 11. 사용자 지시 이후의 구현 단계 제안

아래는 향후 순서 제안이며 현재 구현에 착수하지 않는다.

1. **현황 확인 및 설계 확정:** Linux 서버·계정·소스 경로·빌드 명령, 에이전트 실행 방식, Jira 종류 및 Linux/Windows 보드팜 환경을 확인한다. 현재 구조, 제안 아키텍처, 변경 파일, 데이터 저장 구조, 충돌 가능성과 미결정 사항을 정리한다.
2. **역할별 지침 작성:** CLAUDE.md와 분석·구현·검증·사람 검토 역할별 세부 지침을 작성한다.
3. **상태·결과 형식 정의:** 작업·모듈·단계·명령·실행 회차·벤더 변경·검토 항목과 소스·이미지·보드·테스트 근거의 연결 형식을 정한다. 선행 그룹 완료 조건, 단계별 실행 제한과 연동 공통 형식을 정의한다.
4. **최소 연동 확인:** 지정 계정·폴더에서 에이전트 지침 로딩과 결과 수집, Linux 빌드 호출, 선택한 보드팜 환경의 연결·작업 조회를 소규모로 확인한다. 장비 적용은 정한 실행 범위에서만 시험하며, 확인되지 않은 연동을 완료로 표시하지 않는다.
5. **조회 화면 구성:** 상단 다섯 단계의 모듈 종합 완료율, 그룹별 진행률, 모듈별 접기·펼치기, 선행 대기, 재시도 버튼, 단계별 실행 정책, 보드팜 환경 선택·연결·이미지 전달 상태 및 집계를 구현한다.
6. **작업 실행 및 이슈 명령 연결:** 선행 전체 완료 후 나머지 실행, 분석 병렬·수정 및 빌드 순차 배정, 프롬프트 대기열, 재시도·중복 방지·중지·재개·상태 확인을 구현한다. 브라우저·SSH 종료 후 작업 유지와 재접속 조회를 확인한다.
7. **Jira 검토 연결:** 새 판단 항목 연결, 영향받는 작업만 대기, 선행 조건을 충족한 독립 작업 계속, 생성 실패·중복 방지, 결정과 후속 구현·재검증 연결을 구현한다.
8. **보드팜 연결:** Linux와 Windows 선택에 따른 연결·예약·이미지 전달 및 일치 확인·테스트·결과 회수·취소·복구·해제를 연결한다. 실행 중 환경 변경에 의한 중복 배정을 방지한다.
9. **단계별 및 통합 확인:** 아래 시나리오로 정책과 복구를 확인한다. 로컬 확인과 실제 외부 연동 결과를 구분한다. 수정·빌드 병렬화는 작업 사본·빌드 결과 분리와 충돌 검증을 갖춘 별도 후속 단계로 둔다.

구현 후 확인할 주요 시나리오이며 현재 시험 완료를 뜻하지 않는다.

| 시나리오 | 기대 결과 |

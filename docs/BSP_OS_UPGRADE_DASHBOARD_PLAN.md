# BSP OS Upgrade 대시보드 요구사항 및 단계별 계획

- 문서 작성일: 2026-10-10
- 최신 관리 위치: `graycoral/bsp_os_upgrade_dashboard` 저장소의 `docs/BSP_OS_UPGRADE_DASHBOARD_PLAN.md`
- 문서 최종 수정일: 2026-10-11
- 문서 버전: 0.7.8 · 사내 Jira 직접 설정 및 Claude MCP 선택 방식 반영
- 상태: 사용자 운영 원칙 일부 확정 · 연동 상세 설계 검토 중
- 범위: 대시보드 및 업그레이드 작업 흐름 설계
- 현재 작업: 계획 문서 업데이트 및 GitHub 문서 관리. 기존 화면 시안은 예시이며 실제 시스템 구현은 진행하지 않는다.

## 1. 목적

BSP의 OS 버전이 업그레이드될 때, 기존 BSP 드라이버에 적용된 벤더 수정사항이 새로운 버전에 적절히 반영되도록 관리한다. 신규 OS에 이미 반영된 변경은 근거를 확인하고, 추가 이식이 필요한 변경은 구현과 검증으로 연결한다.

대시보드는 업그레이드 실행, 전체 및 모듈별 흐름 확인, 진행률 확인, 이슈 대응 명령, 사람 검토와 Jira 처리 상태를 하나의 웹 화면에서 제공한다.

판단이 애매하거나 더 좋은 방향이 발견되면 질문 또는 기록으로 남기고, 결정이 필요한 작업은 검토 절차로 연결한다.

## 2. 요구사항과 제안 구분

### 2.1 사용자 요구사항

1. OS Upgrade를 시작하는 버튼이 있어야 한다.
2. 상단 전체 현황은 화살표 대신 요구사항 분석·구현·검증·빌드·테스트 각각의 종합 완료율로 표시한다. 아래 모듈들의 해당 단계 결과를 집계하며, 부트로더 선행 그룹과 나머지 그룹의 진행률도 구분한다. 전체 실행 상태와 최종 완료 여부는 별도로 유지한다.
3. 각 모듈의 요구사항 분석, 디자인 변경, 코드 구현, 빌드, 검증과 보드팜 연동·테스트 상태가 상세 흐름으로 보여야 한다.
4. 전체 진행률이 보여야 한다.
5. 이슈가 발생하면 프롬프트로 명령하는 창이 있어야 한다.
6. 사람이 직접 검토해야 하는 사항은 Jira로 만들고, 그 목록이 보여야 한다.
7. 문서와 승인된 화면 시안 검토 단계이며, 실제 대시보드 구현·서버 작업 실행은 별도 지시 전까지 진행하지 않는다.
8. 진행 중 새로운 사람 판단이 필요한 항목을 Jira로 보낸다. 해당 판단에 의존하는 작업만 대기시키고 독립 작업은 계속한다.
9. 초기에는 분석을 병렬로 수행하고, 코드 수정과 빌드는 순차 실행한다. 향후 수정·빌드도 병렬 실행할 수 있도록 확장 가능성을 고려한다.
10. 빌드는 사용 중인 Linux 서버에서 수행한다. 보드팜은 Linux 서버에 연결된 환경 또는 로컬 Windows PC에 연결된 환경 중 선택할 수 있게 한다.
11. 모듈별 상세 흐름에서 실패한 단계에 재시도 버튼을 제공한다.
12. 모든 모듈의 요구사항 분석은 부트로더 상태와 무관하게 병렬 진행할 수 있다. 나머지 모듈의 디자인 변경·코드 구현·빌드·검증·보드팜 테스트는 부트로더 관련 선행 모듈 전체 완료 후 진행한다.
13. 전체 화면은 5개 비교안 중 3번 모듈 비교형을 채택한다. 단계별 상태, 현재 진행 위치, 분석 이후 선행 대기를 시각적으로 구분한다.
14. 모듈을 기준으로 작업과 담당 에이전트를 표시한다. Claude가 모듈 구성을 제안하고, 저장된 모듈 목록과 실제 에이전트 실행 이력을 별도로 관리한다. 세션 종료나 재시도로 모듈 행이 사라지지 않게 한다.
15. Windows 실행 모드에서는 Linux 서버에 분석·수정·빌드를 요청하고 Windows PC에서 테스트한다. Linux 실행 모드에서는 Linux에서 작업한다. 초기에는 두 모드 모두 이미지 다운로드 후 수동 장비 테스트·결과 등록을 사용하며, Windows 로컬 도구와 Linux 테스트 팜 자동 연동은 후속 도입한다.
16. Start의 기본 흐름은 전체 모듈 요구사항 분석 병렬 수행 → 모듈 목록·선행 그룹·변경 계획의 최초 사용자 확인 → 구현·빌드·검증·테스트 진행이다. 최초 확인 전에는 부트로더 선행 모듈도 디자인 변경 이후 실행에 착수하지 않는다.
17. 기본 구현은 OpenCode가 담당한다. 문제가 반복되거나 해결이 어려우면 Claude Opus로 전환한다. Claude가 구현한 변경은 Codex가 리뷰하고, OpenCode가 구현한 변경은 Claude가 리뷰한다. Claude의 분석·조정 참여만으로 구현 담당을 Claude로 간주하지 않는다.
18. 사용자는 Linux에 OpenCode와 Codex가 설치되어 있다고 확인했다. 필요한 도구가 없는 환경에서는 Claude로 대체한다. 실제 설치·인증·호출 확인은 연동 단계에서 수행한다.

19. 초기 장비 테스트는 수동으로 진행하고 자동 테스트 연동은 추후 도입한다. 수동 결과 완료 반영 기준(D-28)과 부트로더 선행 조건은 유지한다.
20. 사내 Jira를 사용한다. 대시보드에서 연결 정보를 직접 설정하거나, 작업에 사용하는 Claude에 연결된 MCP 목록을 표시하여 Jira용 연결을 선택할 수 있게 한다.

8~20항은 2026-10-11 사용자 답변과 후속 제안을 기준으로 정리한 운영 원칙이다. v0.7에서 요구사항 분석을 선행 그룹 완료 조건의 적용 대상에서 제외했다. 분석 이후 단계에는 기존 선행 조건을 유지한다. Windows/Linux 두 실행 모드를 지원한다. v0.7.1에서 수동 테스트는 필수 통과 결과·근거·이미지·보드 정보가 일치하면 별도 승인 없이 완료 반영하고, 예외나 새 판단만 Jira로 연결하기로 확정했다. 구체적인 필수 테스트·근거 항목과 복구·동기화 상세는 후속 확인 대상이다.

### 2.2 설계 제안

- 작업 실행과 개입 기능이 있는 웹 관리 화면으로 구성한다.
- 하나의 업그레이드 작업 아래 모듈, 분석, 구현, 검증, 이슈, 명령, Jira 이력을 연결한다.
- 화면과 실행 시스템을 구분한다. 화면은 명령과 상태를 전달하고, 실제 분석·수정·빌드는 작업 실행 시스템이 수행한다.
- Windows/Linux 두 실행 모드를 지원한다. 어느 모드에서 시작해도 분석·수정·빌드와 작업 기록은 Linux에 유지하는 구성을 제안한다. 모드별 화면·테스트 위치는 §2.8을 따른다.
- 지정한 Linux 계정의 프로젝트 작업 폴더에서 Claude Code를 실행하고 OS Upgrade Agent의 지침과 시작 명령을 전달한다.
- 초기에는 Linux 실행 측에 실행·상태 관리 기능을 포함한다. 화면을 Linux에 두면 같은 서버 프로그램에 포함할 수 있으며, 별도 중앙 작업 관리자 서비스는 필수가 아니다.
- 구체적인 프레임워크, DB, 서버 주소·계정·경로 및 Jira 연동 방식은 아직 확정하지 않는다.

### 2.3 Linux 실행 환경 및 접속 방식

| 위치 | 역할 |
|---|---|
| Windows PC | Windows 모드의 대시보드·로컬 테스트 실행. Linux 모드의 웹 화면에 브라우저로 접속하거나 이미지를 다운로드하여 수동 테스트 가능 |
| Linux 서버 | 두 모드 공통 Claude Code와 Codex / OpenCode 실행, 소스 접근, 코드 수정·빌드, 상태·로그·배정 대기열 저장. Linux 모드에서는 웹 화면과 테스트 팜 연동도 제공 |

- 초기 단독 사용에는 SSH 터널을 통한 웹 접속을 제안한다. 여러 사람이 사용하는 경우 사내망 또는 VPN 접속과 로그인·사용자별 권한을 검토한다.
- 대시보드 서버가 같은 Linux 서버에서 지정 계정으로 실행된다면 Claude 실행을 위해 다시 SSH로 접속할 필요는 없다.
- 대시보드 서버와 작업 서버가 다르면 SSH로 지정 계정에 연결하여 작업을 실행한다.
- Linux 서버에 GUI나 브라우저를 띄우는 방식은 필요하지 않다.
- 브라우저 종료나 사용자 SSH 연결 종료와 작업 프로세스의 수명을 분리한다. 서버가 정상 동작하는 동안 작업은 계속되고, 재접속하면 저장된 상태를 조회한다.
- 서버 재부팅이나 프로세스 종료 후에는 실제 실행 상태를 확인하고 복구·재개한다. 세션 기록만으로 작업이 계속 실행 중이라고 판단하지 않는다.
- 업그레이드 대상이 BSP 소스인지 실행 서버 자체의 OS인지 구분한다. 실행 서버 자체를 업그레이드하는 경우 별도 관리 서버 구성을 검토한다.

### 2.4 실행 계정 및 폴더 설정

| 설정 | 용도 |
|---|---|
| 서버 주소 | 작업할 Linux 서버 식별. 같은 서버에서 직접 실행하는 경우 원격 접속은 불필요 |
| 실행 계정 | Claude 인증, 지침·소스 접근, 결과 기록 및 빌드에 사용하는 Linux 계정 |
| 프로젝트 작업 폴더 | Claude Code의 실행 위치. CLAUDE.md와 OS Upgrade Agent 및 역할별 지침 배치 |
| 기존 원본 BSP 경로 | 벤더 수정 전 비교 기준 |
| 벤더 수정 BSP 경로 | 기존 벤더 변경사항 분석 대상 |
| 신규 원본 BSP 경로 | 목표 OS의 원본 비교 기준 |
| 신규 BSP 수정 작업 폴더 | 실제 이식·수정·빌드 대상 작업 사본 |
| 결과 저장 폴더 | 분석 결과, 실행 로그, 검증 결과 및 작업 상태 저장 |
| 실행 범위 | 분석만 수행할지 구현·검증까지 진행할지 지정 |
| Linux 빌드 설정 | 빌드 명령, 환경 초기화 절차, 도구 버전, 빌드 결과 경로 |
| 단계별 동시 실행 설정 | 초기 분석 병렬 허용, 코드 수정·빌드 순차 실행. 향후 병렬 실행 조건과 동시 실행 수 관리 |
| 실행 모드·테스트 방식 | 초기 Windows/Linux 공통 수동 테스트. 대상 보드·이미지·담당자 기록. 자동 연동 설정은 후속 활성화 |
| 보드팜 연동 설정 | 서비스·도구, 보드 목록, 연결 확인, 예약·이미지 적용·테스트·취소·결과 조회 방법 |
| 이미지 전달 및 보관 설정 | Linux 산출물 위치, 선택한 실행 환경의 수신 위치, 전달 방법 및 체크섬 확인 |

- 프로젝트 작업 폴더와 비교 대상 소스 폴더를 구분한다. 작업 폴더의 설정에서 각 소스 경로를 지정한다.
- 비교 기준 소스는 참조용으로 유지하고, 실제 변경은 명시된 신규 BSP 작업 사본에 수행하는 방안을 기본으로 한다.
- 시작 전 폴더 존재 여부, 참조 경로 읽기 권한, 작업·결과 경로 쓰기 권한, 지정 계정의 Claude 실행 가능 여부와 빌드 환경을 확인한다.
- 계정의 실행 환경과 인증은 Linux 서버에서 준비한다. 대시보드에서 비밀번호나 인증 정보를 프롬프트에 넣어 전달하지 않는다.
- 실제 서버 주소, 계정과 경로는 아직 제공되지 않았으므로 설정값은 미정이다.
- 소스 경로와 함께 기존 원본·벤더 수정본·신규 원본의 고정된 리비전 또는 식별 가능한 스냅샷을 기록하는 방안을 제안한다. 경로가 같아도 내용이 바뀌면 같은 기준으로 취급하지 않는다.

### 2.5 Claude 세션 및 OS Upgrade Agent 연결

환경 확인 기록: 2026-10-11 사용자 설명 기준 Linux에 OpenCode·Codex 설치됨. 아직 서버에 직접 접속해 확인한 결과는 아니다. Claude Code의 설치·인증·Opus 실행 가능 여부도 실제 연동 시 확인한다. 미설치 도구의 Claude 대체 정책은 §3.2를 따른다.

OS Upgrade Agent는 프로젝트에 배치하는 역할 지침과 실행 설정이며, Claude Code 세션이 이를 읽고 실제 작업을 수행한다. 세션 생성만으로 업그레이드를 시작하지 않고, 대상·범위와 시작 명령을 함께 전달한다.

- 업그레이드 작업 하나당 전용 조정용 Claude 세션 하나를 새로 생성한다. 중단·재개 시 해당 세션과 저장된 작업 기록을 이어 사용하는 정책으로 확정했다(D-11).
- 작업 ID와 Claude 세션 ID, 실행 계정, 작업 폴더를 연결하여 기록한다.
- 이슈 명령창의 후속 프롬프트는 해당 작업의 세션으로 전달한다. 같은 세션의 동시 명령은 순서를 정해 처리한다.
- 전체 진행 상태, 모듈 결과, 검증 근거와 Jira 결정은 Claude 대화와 별도로 저장한다.
- Claude는 분석·계획·작업 지시를 담당하고, Linux 실행 측이 기본 구현 OpenCode, 반복 문제·난항 시 Claude Opus, 구현 주체에 따른 Claude/Codex 리뷰 작업을 호출하고 결과를 수집한다. 화면 위치와 실행 주체를 구분한다.
- 기존 SSH 터미널의 임의 세션을 가져오는 방식은 기본 흐름에 포함하지 않는다. Windows/Linux 어느 모드에서도 같은 작업은 같은 전용 세션 기록을 참조한다. 화면 재접속만으로 새 작업·세션을 중복 생성하지 않는다.
- 재개 전 승인된 계획·소스 기준과 실제 에이전트·빌드·장비 작업 상태를 확인한다. 세션 재연결을 이전 명령 재전송으로 처리하지 않는다. 실제 재개 기능을 설치 도구로 검증하며 세션 유실·재개 불가 시 복구 상세는 D-29에서 정한다.
- 터미널 화면 입력을 자동화하기보다 프로그램 실행 인터페이스와 세션 재개 기능을 활용하는 방안을 제안한다. 실제 설치 버전에 맞는 호출 방식은 구현 전에 확인한다.
- 실행 연결 시험에서 인증, 환경 초기화, CLAUDE.md 및 역할 지침 로딩, 결과 수집과 세션 재개를 확인한다. 터미널에서 정상 실행된다는 사실만으로 대시보드 실행 환경까지 검증된 것으로 보지 않는다.
- 실행 요청은 Linux 실행 측이 일관되게 기록·배정하는 방안을 제안한다. Claude의 작업 지시와 실제 호출을 구분하여 같은 작업이 두 경로에서 중복 실행되지 않게 한다.
- 결과에는 작업·모듈·단계·실행 회차·소스 기준·산출물·판정 근거를 연결한다. 에이전트 응답 종료만으로 빌드나 장비 검증을 완료 처리하지 않는다.

### 2.6 초기 실행 관리 범위

초기에는 Linux 실행 측에 다음 기능을 포함한다. 화면도 Linux에 배치한다면 대시보드 서버와 같은 프로그램으로 구성할 수 있다. Windows 화면을 선택해도 배정과 기록은 Linux에 유지한다.

- 시작 입력과 경로 확인
- 작업 기록 및 중복 실행 방지
- 지정 계정·작업 폴더에서 Claude 실행과 세션 연결
- 명령 전달, 실행 상태·로그·결과 저장
- 중지·재개와 재접속 후 상태 조회

여러 업그레이드의 동시 실행이나 여러 Linux 서버로의 작업 배정이 필요해지면 실행 관리 기능을 별도 서비스로 분리하는 방안을 검토한다.

다음은 장애 복구와 명령 충돌 방지를 위한 설계 제안이다.

- 작업 ID, 명령 ID, 실행 회차, 세션 ID, 실행 위치와 외부 작업 ID를 실행 전후에 저장한다. 같은 명령의 재전송은 새 실행으로 취급하지 않는다.
- 연결이 끊기면 우선 상태 확인 중으로 표시한다. 실제 프로세스 또는 외부 작업을 확인하기 전에는 실패로 확정하거나 자동 재실행하지 않는다.
- 중지 요청은 새 작업 배정을 멈추는 것과 진행 중 작업을 취소하는 것을 구분한다. 기본은 새 배정을 멈추고 진행 중 작업의 안전한 종료를 기다리는 방안이다.
- 이미지 적용 등 도중 취소가 어려운 작업은 실행 환경이 제공하는 취소·복구 절차를 따른다. Claude 종료를 보드팜 작업 취소로 간주하지 않는다.
- 실패 후 재시도는 새 실행 회차로 기록하고 이전 결과를 보존한다. 시간 제한·재시도 횟수·재개 조건은 연동별로 확정하며 무한 재시도를 허용하지 않는다.

### 2.7 빌드 위치와 테스트 실행 환경

**초기 적용 범위(D-34): 두 실행 모드 모두 수동 장비 테스트만 운영한다.** 이미지 묶음 제공·다운로드, 테스트 회차 생성, 결과·근거 등록을 우선 제공한다. 아래 Windows/Linux 자동 테스트 연동 경로와 연결·예약·자동 이미지 적용·결과 수집 규칙은 후속 설계이며 초기 구현의 필수 선행 조건이 아니다.

**빌드 위치는 두 모드 모두 Linux 서버다.** Windows 로컬 테스트, Linux 테스트 팜, 이미지 다운로드 후 수동 테스트를 구분한다.

| 선택 | 이미지 이동과 실행 흐름 | 결과 수집 |
|---|---|---|
| Linux 보드팜 | Linux 빌드 → 지정 이미지 확인 → Linux에 연결된 환경으로 예약·이미지 적용·테스트 | Linux 연동 기능이 작업 상태·장비 로그·테스트 결과를 대시보드에 기록 |
| Windows 보드팜 | Linux 빌드 → Windows 실행 환경으로 이미지 전달·확인 → Windows에 연결된 환경으로 예약·이미지 적용·테스트 | Windows 연동 기능이 외부 작업 ID·상태·로그·결과를 Linux 실행 기록에 전달. 화면은 통합 상태를 조회 |
| 수동 테스트 | Linux 빌드 → 이미지 묶음·체크섬·적용 안내 다운로드 → 담당자가 대상 보드에 적용·테스트 | 담당자가 실행 회차에 결과·보드·이미지 ID·근거 등록. 다운로드만으로 완료하지 않음 |

연동 상세 설계 제안:

- Linux가 전체 작업 상태의 기준을 관리하고, 각 보드팜 환경은 배정된 장비 작업을 수행한다. 환경마다 연결 확인·예약·실행·조회·취소·해제·결과 수집 기능을 같은 형식으로 연결한다.
- Windows 브라우저에서 화면을 여는 것만으로 로컬 장비 도구가 실행되지는 않는다. 기존 서비스/API를 사용할지 별도 로컬 실행 구성요소를 둘지 확인한다. Windows가 Linux에 접속해 배정 작업을 가져오는 방식도 후보로 두되 연결 방식은 아직 확정하지 않는다.
- 실행 전에 작업에 사용할 보드팜 환경을 선택·기록한다. 실행 중 환경을 바꾸어 같은 테스트를 중복 배정하지 않는다. 변경은 기존 작업 종료 또는 상태 확인 후 새 실행 회차부터 적용한다.
- Linux와 Windows의 파일 경로를 각각 관리한다. 소스·빌드 ID, 이미지 목록과 체크섬을 함께 전달하고 일치 확인 후 장비에 적용한다. 부트로더·커널·기타 이미지가 여러 개면 하나의 적용 목록으로 묶는다.
- Windows PC 종료·절전·네트워크 단절 시 해당 장비 작업을 연결 대기 또는 상태 확인 중으로 표시한다. 이미 배정한 작업을 자동으로 다른 환경에 다시 보내지 않는다.
- PC가 재접속하면 기존 외부 작업 ID로 진행·종료 여부와 저장된 결과부터 확인한다. 복구 불가능한 경우에만 실패 및 후속 조치를 결정한다.
- 보드팜 환경이 오프라인이어도 모든 모듈의 요구사항 분석은 계속할 수 있다. 코드 수정·Linux 빌드는 의존성이 허용하는 범위에서 계속한다. 선행 그룹의 필수 장비 검증이 남아 있으면 나머지 모듈의 분석 이후 단계는 대기한다.
- 실행 구성요소의 등록·인증, 이미지 전송 방식, 로그 보관·전송 재시도, PC 실행 유지 방식은 구현 전에 확정한다. 별도 중앙 관리 서버가 반드시 필요한 구성은 아니다.

### 2.8 Windows/Linux 두 실행 모드와 상태 조회

사용자의 최신 제안에 따라 **같은 대시보드와 작업 모델을 두 실행 모드로 제공**한다. 서로 독립된 업그레이드 시스템을 만드는 방식은 피한다.

| 실행 모드 | 화면과 작업 요청 | 분석·수정·빌드 | 테스트 |
|---|---|---|---|
| Windows | Windows에서 대시보드 실행 → 지정 Linux 서버에 작업 요청 | Linux 실행 측이 담당 | 초기: 이미지 다운로드 후 수동 테스트·결과 등록. 후속: PC 도구 자동 연동 |
| Linux | Linux에서 대시보드·실행 기능 실행 → 브라우저로 접속 | 같은 Linux 실행 측이 담당 | 초기: 이미지 다운로드 후 수동 테스트·결과 등록. 후속: 테스트 팜 연동 |

- 여기서 실행 모드는 대시보드와 연동 구성의 배치 위치다. 접속 브라우저의 운영체제로 테스트 위치를 자동 결정하지 않는다. Windows 브라우저로 Linux 화면에 접속해도 Linux 모드일 수 있다.
- 초기 설정에 모드, Linux 대상, 테스트 방식을 명시하고 실행 전에 표시한다. 시안의 모드 선택은 배치 비교용이며 실제 실행 도중 서버 위치를 바꾸는 기능이 아니다.
- Linux가 모듈 목록·배정 대기열·실행 결과의 기준을 유지하는 구성을 제안한다. 두 화면이 같은 작업을 열면 같은 ID와 상태를 조회하고 명령 중복을 확인한다.
- 대시보드는 실행 측이 기록한 구조화된 상태를 조회한다. 시작·재시도·프롬프트는 별도 명령 접수 경로로 전달한다. 화면에서 로그를 임의 해석해 작업 완료를 추정하지 않는다.
- 초기 Windows 모드에서는 담당자가 직접 장비 테스트하고 결과를 등록한다. 로컬 테스트 실행 구성요소는 필수가 아니다. 후속 자동 연동 시 기존 서비스 활용 또는 로컬 실행 구성요소를 D-18에서 결정한다. 브라우저 화면만으로 PC 장비를 제어할 수 있다고 가정하지 않는다.
- Windows 테스트 결과는 실행 ID·소스/이미지 기준·상태 버전과 함께 Linux에 전달한다. 수동 테스트 결과도 지정한 테스트 회차에 등록하여 같은 조회 형식으로 통합한다.
- Windows PC를 꺼도 Linux 작업은 계속한다. PC 테스트는 대기 또는 상태 확인 중이며 재접속 시 기존 외부 작업부터 확인한다. 수동 테스트는 결과 등록까지 대기를 유지한다.
- 연결 단절 시 마지막 동기화 시각을 표시한다. 초기 통신은 SSH/API 조회를 후보로 두며, 저장 형식·동시 쓰기·인증·재전송 방식은 D-05·D-18에서 확정한다.

### 2.9 모듈 목록과 에이전트 실행 목록

**화면의 기본 행은 모듈이며, 에이전트는 단계별로 배정되는 실행 주체다.** 모듈마다 하나의 에이전트를 계속 실행하거나, 화면을 갱신할 때마다 Claude에게 현재 목록을 다시 생성하도록 요청하지 않는다.

| 관리 대상 | 생성·변경 주체 | 주요 기록 |
|---|---|---|
| 모듈 목록 | Claude가 요구사항·소스를 분석해 초안 제안. 실행 측이 검증하여 계획 버전으로 저장 | 고정 모듈 ID, 이름, 대상 소스, 선행/나머지 그룹, 의존성, 포함 근거 |
| 모듈별 단계와 작업 | Claude가 계획 제안, 실행 측이 단계·선행 조건·자원을 확인해 배정 | 작업 ID, 모듈 ID, 단계, 완료 조건, 입력 기준, 담당 역할, 상태 |
| 에이전트 실행 | 실제 호출을 접수·실행할 때 생성 | 실행 ID, 실행 회차, 작업 ID, 도구·역할, 세션/외부 작업 ID, 시작·종료·마지막 확인 시각 |
| 결과와 근거 | 실제 실행 측이 기록, Linux 실행 기록에 연결 | 소스 기준, 로그·산출물 ID, 판정, 실패 사유, 검증 유효성 |

- 연결 구조는 `업그레이드 작업 → 모듈 → 단계별 작업 → 실행 회차 → 결과`로 유지한다. 모듈 ID는 이름 변경이나 재시도 시에도 보존한다.
- 예: Camera의 Claude 분석 실행이 종료되면 분석 결과를 보존하고 설계 이후를 선행 대기로 표시한다. 실행 조건 충족 후 OpenCode 구현 실행을 연결하고 Claude 리뷰를 배정한다. Claude Opus로 구현을 전환하면 Codex 리뷰를 배정한다. 대기 중인 모듈은 실행 중인 에이전트 수에 포함하지 않는다.
- 빌드·보드팜 도구 실행은 에이전트 세션과 구분한다. 단계 담당 역할만 정해졌다고 세션이 실행 중인 것으로 표시하지 않는다.
- 최초 모듈 목록·선행 그룹·변경 계획은 전체 모듈 분석 후 사용자에게 한 번 확인받는다(D-01). 실제 모듈·의존성은 D-12에서 정한다. 이후 기존 범위 안의 명확한 세부 작업은 계획에 기록해 이어가고, 새 범위·그룹 변경·모호한 의존성 등 새로운 판단이 필요한 변경만 Jira로 보낸다. 세분화·목록 변경의 구체적 기준은 D-26에서 정한다.
- 모듈 추가·제외·분할·병합 시 변경 이유와 이전 ID 연결, 계획 버전, 진행률 분모 변경을 기록한다. 실행 이력을 삭제하지 않고 비활성/대체 관계를 보존한다. 새 선행 모듈 추가는 기존 완료 판정과 실행 조건을 다시 계산한다.
- 역할 지침은 모듈 수만큼 복제하지 않고 분석·설계·구현·검증 등 역할별 지침에 모듈 문맥을 전달하는 방안을 제안한다. 전용 조정 세션은 D-11로 확정했다. 병렬 모듈 분석의 하위 실행·세션 분리 단위와 동시 분석 수는 설치 도구 확인 후 D-07에서 정한다. 조정 세션 하나가 모든 분석을 순차 실행한다는 뜻은 아니다.
- Claude가 보고한 완료는 결과 후보이며, 실행 측이 완료 조건과 로그·산출물 근거를 확인한 뒤 상태에 반영한다. 대화 종료나 에이전트 목록 응답만으로 완료 처리하지 않는다.

### 2.10 상태 갱신과 명령 경로

다음은 중복 실행과 화면·실행 상태 불일치를 줄이기 위한 설계안이다.

1. 화면은 저장된 모듈·작업·실행 상태를 조회한다. 시작·재시도·프롬프트는 명령 ID를 붙여 Linux 실행 측에 접수한다.
2. Linux 실행 측은 최신 계획·소스·Jira 결정·선행 조건·자원 점유를 확인하고 실행을 배정한다. 브라우저의 버튼 비활성화만으로 실행 조건을 보장하지 않는다.
3. 실행 측은 상태 버전, 실행 회차, 갱신 시각과 근거를 기록한다. Windows 장비 작업의 보고도 기존 배정 ID에 연결하여 반영한다.
4. 중복·지연 이벤트는 실행 ID와 버전으로 구분한다. 이전 회차의 늦은 완료가 새 회차 실패를 덮어쓰지 못하게 한다. 입력 기준이 달라진 결과는 과거 이력으로만 보존한다.
5. 화면은 마지막 동기화 시각과 연결 상태를 표시한다. 연결이 끊겨도 저장된 목록은 유지하며, 상태가 오래됐다는 이유만으로 작업을 실패 처리하거나 재배정하지 않는다.

초기 수동 테스트에서는 담당자가 결과·근거를 보관하고 연결 복구 후 해당 회차에 등록한다. 후속 자동 연동에서는 Windows 실행 측이 장비 결과를 로컬에 보존하고 연결 복구 후 재전송한다. Linux가 접수한 기록을 전체 조회의 기준으로 삼는다. 별도 신규 작업 배정은 Linux의 확인을 거치며 PC에서 독자적으로 같은 테스트를 재실행하지 않는다. 구체적인 저장 형식·통신·재전송 방식은 D-05·D-18·D-23에서 확정한다.

역할별 세부 지침과 CLAUDE.md 작성은 별도 후속 작업이다. 이 문서는 그 지침의 기반이 되는 요구사항을 정리한다.

### 3.1 구현 전환과 교차 리뷰

**기본 구현·리뷰 담당 정책은 D-30으로 확정했다.** 도구 미설치 시에는 §3.2의 D-33 대체 정책을 적용한다. 아래 인계·상태 표시와 리뷰 완료 시점은 구현을 위한 상세 설계안이다.

| 구현 경로 | 리뷰 담당 | 적용 기준 |
|---|---|---|
| OpenCode 기본 구현 | Claude | Claude가 분석·조정만 수행한 경우도 이 경로 유지 |
| 반복 문제·난항으로 Claude Opus가 구현 | Codex | Claude가 실제 코드 변경을 담당했으므로 구현과 리뷰 분리 |
| OpenCode와 Claude가 함께 수정한 변경 | Codex | Claude의 구현 기여가 남아 있으면 마지막 도구 이름만으로 Claude 리뷰에 되돌리지 않는 방안 |

- 조정용 전용 Claude 세션과 Opus 구현 역할을 구분해 실행 ID·역할·도구·모델을 기록한다. Opus 사용 지정은 난항 시 구현 역할에 적용하며, 분석·조정·일반 Claude 리뷰 모델까지 Opus로 고정한 것은 아니다.
- 확정(D-31): 같은 원인의 수정 시도가 2회 실패하면 OpenCode에서 Claude Opus로 전환한다. 해결이 어려운 경우에는 판단 근거를 기록하고 2회 이전에도 조기 전환한다.
- 반복 횟수는 같은 문제를 해결하기 위한 실제 수정·확인 시도별로 기록한다. 최초 오류 발견, 같은 로그의 재수신, 중복 명령 접수는 수정 실패 횟수로 중복 계산하지 않는 방안을 적용한다. 단순 연결 단절·권한·장비 장애는 우선 해당 환경 문제로 처리한다.
- 조정 역할은 전환 사유, 실패한 수정 시도와 로그, 조기 전환 시 해결이 어려운 근거를 남긴다. 도구 전환 자체로 Jira를 만들지 않으며 새 설계 판단·범위 변경·예외가 필요한 경우만 Jira로 연결한다.
- 전환 시 기존 실행 종료·상태를 확인하고 현재 변경, 소스 기준, 로그, 실패 원인, 시도한 방법, 리뷰 지적과 승인 범위를 인계한다. 같은 작업 사본에서 OpenCode와 Opus가 동시에 수정하지 않으며 기존 순차 실행·선행 조건을 유지한다.
- 리뷰는 고정된 변경 리비전에 대해 별도 실행으로 기록한다. 기술 리뷰 자체를 Jira 티켓으로 만들지 않고, 새 설계 판단·범위 변경·예외 허용이 필요한 경우만 Jira로 연결한다.
- 화면의 여섯 단계를 유지하면서 코드 구현 내부에 `작성 중 / 리뷰 대기 / 리뷰 중 / 수정 필요 / 리뷰 통과`를 표시하는 방안을 제안한다. 검증용 빌드는 문제 확인에 활용할 수 있으나 리뷰 미완료 상태를 구현 완료나 최종 완료로 집계하지 않는다.
- 리뷰 이후 코드가 바뀌면 변경된 리비전을 다시 리뷰하고 관련 빌드·검증 결과의 유효성을 확인한다. 리뷰 통과가 빌드·장비 테스트 통과를 대신하지 않는다.
- Opus로 전환해도 해결하지 못하면 반복 이력을 유지한다. 무한한 도구 전환을 하지 않도록 한도와 중단 기준을 정하고, 새 판단이 필요하면 Jira로 연결한다. 실제 호출·모델 식별자·실행 가능 여부는 설치 환경에서 확인한다.

### 3.2 도구 미설치 시 Claude 대체

**필요한 도구가 없으면 Claude로 대체하는 정책은 사용자 지시로 확정했다(D-33).** 다음 역할 배정과 기록 방식을 설계에 적용한다.

| 상황 | 구현 | 리뷰 |
|---|---|---|
| OpenCode·Codex 설치됨 | OpenCode 기본, 반복 문제·난항 시 Claude Opus | OpenCode 구현은 Claude / Claude 구현은 Codex |
| OpenCode 미설치 | Claude로 구현 대체. 구현 모델은 기존 Opus 경로를 사용하는 설계안 | Codex가 있으면 Codex |
| Claude가 구현했으나 Codex 미설치 | Claude 구현 유지 | 별도 Claude 리뷰 실행으로 대체 |
| OpenCode·Codex 모두 미설치 | Claude로 구현 대체 | 별도 Claude 리뷰 실행으로 대체 |

- 미설치에 따른 대체는 수정 2회 실패를 기다리지 않는다. 이는 설치 상태에 따른 경로 선택이며, OpenCode 실행 중 발생하는 반복 문제·난항 전환과 사유를 구분한다.
- Claude 구현을 Claude가 리뷰해야 하는 경우 구현 실행과 리뷰 실행을 분리한다. 고정된 변경 리비전·요구사항·로그를 리뷰 입력으로 제공하고, 구현 세션의 자체 완료 보고를 리뷰 통과로 재사용하지 않는다. 같은 도구 계열의 리뷰라는 사실을 기록하며 Codex 교차 리뷰로 표시하지 않는다.
- 사용 도구·모델·역할, 미설치 확인 결과와 대체 사유를 실행 이력과 모듈 상세에 표시한다. 기존 선행 조건, 순차 수정·빌드, 리뷰·검증 완료 조건은 유지한다.
- 미설치 도구를 대체했다는 이유만으로 Jira를 만들지 않는다. 새 판단·범위 변경·검증 예외가 필요한 경우만 기존 Jira 정책을 적용한다.
- 실제 호출 전 설치·인증·실행 가능 여부를 확인한다. 실행 중 응답 유실이나 상태 불명확을 미설치로 간주해 같은 작업을 Claude에 중복 배정하지 않는다. Claude도 실행할 수 없으면 해당 역할을 실행 대기로 표시하고 원인을 기록한다.

## 4. 공통 상태와 완료 원칙

### 4.1 단계 상태

| 상태 | 의미 |
|---|---|
| 대기 | 선행 조건 충족 또는 실행 지시를 기다림 |
| 실행 중 | 분석·구현·검증 등 작업이 진행 중 |
| 완료 | 해당 단계의 완료 조건과 근거가 충족됨 |
| 실패 | 실행이 실패했으며 원인과 후속 조치가 필요함 |
| 검토 필요 | 사람의 판단 없이는 해당 작업을 진행하거나 완료할 수 없음 |
| 해당 없음 | 적용 대상이 아님을 근거와 함께 확인함 |
| 상태 확인 중 | 연결 단절·재시작 등으로 실제 실행 여부를 확인 중. 확인 전 중복 배정 금지 |
| 재검증 필요 | 소스·의존성·테스트 조건 변경으로 이전 검증을 현재 기준에 적용할 수 없음 |

작업 전체에는 중지 요청·중지·재개 상태도 필요하다. 새 작업 배정 중지와 진행 중 작업 취소를 구분하는 §2.6의 제안을 기준으로 연동별 상세 동작을 결정한다. 상태 확인 중·재검증 필요는 이번 검토에서 추가한 상태 제안이다.

각 모듈 단계에는 선행 조건 대기와 보드 예약 대기 사유도 표시한다. 대기는 실패와 구분하며, 실행 상태와 검증 결과를 별도 기록한다.

전체 OS Upgrade 상태는 실행 여부와 실패 건수를 분리하는 다음 집계 기준을 제안한다.

- **진행 중:** 실행 또는 재개 가능한 작업이 남아 있다. 일부 실패가 있어도 독립 작업이 계속되면 `진행 중 · 실패 1 · 검토 대기 2`처럼 표시한다. 사람 검토·자원 대기만으로 실패 처리하지 않는다.
- **실패:** 필수 작업 실패로 현재 실행을 종료했거나 복구 없이 더 진행할 수 없다. 실패한 모듈·단계와 후속 조치를 표시한다. 전체를 실패로 종료하는 조건은 실행 정책에서 확정한다.
- **완료:** 필수 모듈 작업, 통합 빌드, 필수 검증·보드팜 테스트 및 관련 검토 결정 반영이 끝났다. 최종 사람 검토는 다음 전체 단계에서 처리한다.
- 중지 여부는 위 상태와 별도로 표시한다. 실패 해결 후 재실행하면 최신 상태를 집계하되 이전 실패 이력은 유지한다.

### 4.2 완료 원칙

- 코드 수정 완료와 검증 완료를 구분한다.
- 신규 OS에 이미 반영된 변경도 확인 근거와 필요한 검증을 남긴다.
- 해당 없음은 실패나 미진행을 숨기는 용도로 사용하지 않는다.
- 필수 검증과 사람 검토가 남아 있으면 최종 완료로 처리하지 않는다.
- 검증 불가 항목은 이유와 영향을 기록하고, 예외 허용이 필요하면 사람 검토로 연결한다.

## 5. 전체 흐름과 모듈별 상세 흐름

### 5.1 상단 종합 진행도

상단 제목은 **종합 진행도**로 표시한다. **요구사항 분석 % 완료 / 구현 % 완료 / 검증 % 완료 / 빌드 % 완료 / 테스트 % 완료**의 다섯 항목을 큰 완료율과 진행 막대, 완료/대상 작업 수로 보여준다. 좁은 화면에서는 여러 줄로 재배치한다. 화살표는 사용하지 않으며 각 값은 아래 모듈들의 실제 단계 상태에서 계산한다.

| 상단 항목 | 모듈 상세 단계와의 연결 | 표시 내용 |
|---|---|---|
| 요구사항 분석 | 각 모듈의 요구사항 분석 | 완료율, 완료/대상 작업 수, 대기·실패·검토 수 |
| 구현 | 디자인 변경 + 코드 구현 | 두 상세 단계의 필수 작업을 합산한 완료율 |
| 검증 | 모듈별 검증 | 필수 개별 검증의 완료율 |
| 빌드 | 모듈별 빌드 | 빌드 완료율 |
| 테스트 | 모듈별 장비 테스트: Windows 로컬 / 테스트 팜 / 수동 | 필수 장비 테스트 완료율. 연결·예약·다운로드 성공은 완료로 계산하지 않음 |

- 다섯 항목은 병렬로 조회하는 집계 지표이며, 표시 순서는 실행 순서 변경을 의미하지 않는다. 모듈 상세의 선후 관계와 부트로더 선행 그룹 전체 완료 조건을 유지한다.
- 구현에 디자인 변경과 코드 구현을 함께 집계하는 것은 여섯 상세 단계를 다섯 상단 항목에 빠짐없이 연결하기 위한 초기 설계안이다.
- 상단 검증과 테스트는 같은 결과를 중복 계산하지 않는다. 모듈별 개별 검증은 검증 항목에, 장비 테스트는 로컬/팜/수동 방식과 무관하게 테스트 항목에 연결한다.
- 단계별 완료율은 해당 단계에 속한 전체 적용 대상 필수 작업의 완료 가중치 / 전체 가중치로 계산한다. 초기 동일 가중치 기준으로 구현은 설계·코드 두 작업을 각각 센다. 모듈 완료율을 단순 평균하지 않는다.
- 선행 대기 중인 나머지 모듈도 대상이므로 분모에 포함한다. 아직 시작하지 않은 모듈을 제외하여 진행률을 높이지 않는다.
- 승인된 해당 없음은 분모에서 제외한다. 전체 대상이 없으면 100% 대신 해당 없음, 대상이 아직 정의되지 않았으면 산정 중을 표시한다.
- 재시도 접수·실행 중·실패·검토 대기는 완료에 포함하지 않는다. 재검증이 필요해지면 현재 기준의 완료 집계에서 제외하고 변경 이유를 남긴다.
- 상단의 요구사항 분석은 모듈별 분석 집계다. 실행 전 초기 범위 정리가 끝났다는 이유로 모든 모듈의 분석을 완료 처리하지 않는다.
- 통합 빌드·전체 회귀 검증·최종 사람 검토는 별도 완료 조건으로 남긴다. 다섯 항목 모두 100%여도 이 조건이 남아 있으면 전체 업그레이드 최종 완료가 아니다.

v0.7 시안 예시: 선행 2개 모듈의 분석·설계·코드·빌드·개별 검증이 완료되고 보드팜은 1개만 완료, 나머지 그룹은 1개 분석 완료·2개 분석 중이면 상단은 분석 60%, 구현 40%, 검증 40%, 빌드 40%, 테스트 20%다. 분석 진행 중이라는 이유로 완료율을 임의 가산하지 않는다.

#### 내부 작업 수명주기와 완료 조건

기존의 초기 범위 정리·OS Upgrade 실행·최종 검토는 내부 절차로 유지한다. 화면 상단을 이 세 단계의 화살표로 표시하지 않는다.

| 전체 단계 | 주요 작업 | 화면 표시 | 완료 조건 |
|---|---|---|---|
| 요구사항 분석 | 실행 환경·소스 기준·벤더 변경 목록·대상 모듈·선행 그룹·검증 범위의 초기 정리 | 기준 확인 상태, 발견 모듈 수, 초기 계획과 검토 요청 | 대상·그룹·초기 실행 조건이 정리됨. 나머지 그룹의 모듈별 상세 분석 완료를 이 단계의 조건으로 요구하지 않음 |
| OS Upgrade | 모듈별 설계·구현·빌드·검증, 보드팜 테스트, 통합 빌드·회귀 검증 | 진행 중 / 실패 / 완료, 선행 모듈 진행률, 병렬 모듈 진행률, 통합 검증 상태 | 필수 변경과 검증 완료, 이 단계에 영향을 주는 검토 결정 반영 |
| 최종 완료 | 변경·검증 결과와 예외 검토, 남은 이슈 정리, 최종 사람 검토 | 검토 대기 / 완료, 최종 검토자·결정·완료 시점 | 최종 검토 완료 및 필수 미해결 항목 없음 |

위 표는 내부 실행 절차다. 화면에서는 다섯 종합 완료율, 전체 실행 상태, 그룹별 진행률과 통합 검증·최종 검토 상태로 나누어 보여준다. 최종 검토 진입과 최종 완료를 구분한다.

전체 첫 단계는 실행 기준과 초기 범위를 정하는 과정이다. 기준이 준비되면 모든 모듈의 벤더 의도·신규 OS 반영 여부 상세 분석을 병렬로 시작한다. 대상 모듈의 필수 분석을 마친 뒤 모듈 목록·선행 그룹·변경 계획을 사용자에게 한 번 확인받는다. 이 최초 확인 전에는 선행 그룹을 포함한 모든 모듈의 디자인 변경 이후 실행을 보류한다. 확인 후에는 단계별 의존 조건에 따라 배정하며 독립 작업을 불필요하게 일괄 보류하지 않는다.

### 5.2 Start 버튼에서 작업 시작까지

1. 대시보드에서 대상 BSP, 현재·목표 OS, 서버·계정·폴더, 소스 기준과 실행 범위를 확인한다.
2. 실행 모드에 맞는 Linux 대상·빌드 설정·테스트 방식과 단계별 정책을 선택한다. Linux 실행 측이 경로·권한·실행 환경과 중복 실행 여부를 확인하고 작업을 기록한다. 별도 중앙 작업 관리자 서비스는 필요하지 않다.
3. 지정 Linux 계정의 프로젝트 작업 폴더에서 Claude Code 세션을 생성한다. 다른 작업 서버인 경우 SSH로 연결한다.
4. 작업 ID와 세션 ID를 연결하고 CLAUDE.md와 OS Upgrade Agent 지침을 적용한다.
5. 대상·범위와 시작 명령을 전달하여 요구사항 분석부터 시작한다.
6. 모든 모듈의 요구사항 분석을 병렬 수행한다. 분석 결과와 근거를 모아 모듈 목록·선행 그룹·변경 계획을 제시하고 최초 사용자 확인을 기다린다. 이 확인은 정규 계획 확인이며 그 자체로 Jira 티켓을 만들지 않는다. 분석 중 새로운 판단이 필요한 항목만 Jira로 연결한다.
7. 사용자가 확인한 계획 버전·소스 기준·실행 범위를 기록한다. 이후 선행 그룹의 디자인 변경·구현·빌드·검증·테스트를 진행한다. 나머지 모듈의 디자인 변경 이후는 선행 그룹 전체 완료까지 기다린다. 수정·빌드는 순차 실행하며 로컬/팜 결과를 수집하거나 수동 결과 등록을 기다린다.
8. 상태·로그·결과를 저장하고 전체 및 모듈별 흐름에 반영한다.
9. 진행 중 새로운 사람 판단이 필요하면 내부 검토 항목과 Jira로 연결한다. 영향받는 작업만 대기시키고, 단계별 실행 조건을 충족한 독립 작업은 계속 배정한다. 독립적인 요구사항 분석에는 부트로더 선행 완료 조건을 적용하지 않는다.

Start 기본 흐름과 최초 계획 확인은 D-01로 확정했다. 같은 승인 계획·소스 기준으로 재접속·재개할 때 최초 확인을 반복하지 않는다. 승인된 범위를 바꾸는 새 판단은 Jira로 연결하고 영향받는 작업만 보류한다. 단계마다 승인을 반복하지 않으며, 분석 전용 범위를 명시적으로 선택한 작업은 계획 확인만으로 구현까지 자동 확대하지 않는다. 본 문서 업데이트는 실제 코드 수정이나 장비 적용 실행을 의미하지 않는다.

### 5.3 OS Upgrade 내부의 두 작업 그룹

| 그룹 | 구성 | 표시 내용 |
|---|---|---|
| 부트로더 관련 선행 모듈 | 부트로더 및 다른 모듈 진행에 필요한 것으로 확인된 관련 작업 | 그룹 진행률(%), 모듈별 상태, 선행 조건, 부팅 검증 결과, 후속 작업을 막는 항목 |
| 나머지 모듈 | 요구사항 분석은 선행 그룹과 동시에 진행. 디자인 변경 이후는 선행 그룹 전체 완료 필요 | 분석 완료·진행 수, 후속 단계 선행 대기, 그룹 진행률과 실제 실행 정책 |

- 선행 모듈 목록은 실제 BSP와 의존성 분석으로 확정한다. 부트로더 종류나 관련 모듈을 임의로 확정하지 않는다.
- 모든 모듈의 요구사항 분석과 분석 단계 재시도는 부트로더 관련 선행 그룹 상태와 무관하게 허용한다. 분석 자체의 입력 누락·사람 판단 대기는 별도로 처리한다.
- 디자인 변경 이후 실행에는 최초 계획 확인(D-01)이 필요하다. 나머지 모듈에는 이에 더해 선행 그룹 전체 완료 조건을 적용한다. 실행 측이 두 조건을 모두 확인하며 화면 버튼 상태만으로 판단하지 않는다.
- 나머지 모듈의 디자인 변경·코드 구현·빌드·검증·보드팜 테스트와 해당 단계 재시도는 선행 그룹 전체 완료 후 허용한다. 분석 명령에 코드 수정을 포함하여 이 조건을 우회하지 않는다.
- 선행 그룹의 완료는 해당 필수 변경·빌드·검증·장비 테스트 및 관련 사람 결정 반영이 끝났다는 뜻이다. 수동 테스트도 같은 필수 검증 범위를 충족해야 한다. 단순 코드 수정 완료나 화면상 반올림된 100%로 실행을 허용하지 않는다.
- 선행 그룹에서 검토나 실패가 발생해도 전체 모듈의 독립적인 요구사항 분석은 계속한다. 나머지 그룹의 분석 이후 단계는 전체 선행 완료까지 대기한다.
- 특정 부팅 이미지나 선행 산출물이 필요한 빌드·장비 검증은 해당 조건이 충족될 때 실행한다.
- 공통 소스·빌드 자원·보드 사용이 충돌하는 작업은 순서를 조정하고 대기 사유를 표시한다.
- 모듈 화면에 선행 모듈, 필요한 산출물과 현재 막힌 단계를 표시한다.
- 통합 빌드 및 전체 회귀 검증은 그룹 진행률과 별도로 표시하고, OS Upgrade 완료 판단에 포함한다.
- 선행 완료 후 실행을 허용한 기준 버전을 기록한다. 이후 선행 결과가 무효화되면 나머지 그룹의 분석 이후 신규 실행·재시도를 막고, 해당 진행 중 작업을 안전하게 정리한다. 분석은 계속 가능하나 변경된 소스 기준의 영향을 받은 분석 결과는 유효성을 다시 확인한다.

#### 5.3.1 초기 실행 정책과 향후 병렬 확장

| 작업 | 초기 정책 | 향후 확장 시 조건 |
|---|---|---|
| 요구사항·변경 분석 | 선행 그룹 완료 여부와 무관하게 전체 모듈 병렬 분석 | 동일한 고정 소스 기준 사용, 모듈별 분석 결과 분리, 서버 자원에 맞춘 동시 실행 수 |
| 코드 수정 | 순차 실행 | 모듈별 수정 사본 분리, 공통 파일·의존성 충돌 확인, 통합 반영 순서 확정 후 병렬 허용 |
| 모듈·통합 빌드 | Linux 서버에서 순차 실행 | 고정된 소스 입력, 독립 빌드 결과 폴더, 자원·도구 사용 제한 확인 후 병렬 허용 |
| 보드팜 테스트 | 선택한 환경과 실제 보드 가용성에 따라 배정 | 동일 보드 독점 사용, 이미지 및 외부 작업 ID 추적. 동시 보드 수는 환경 확인 후 결정 |

- 초기에는 동일 BSP 작업 사본을 쓰는 코드 수정과 빌드를 하나의 배정 대기열에서 순차 처리하는 방안을 제안한다. 다른 모듈의 빌드 중 같은 소스를 수정하지 않는다. 통합 반영과 이슈 프롬프트의 수정 요청도 같은 규칙을 적용한다.
- 앞 작업이 사람 판단 때문에 대기하면 실행 자원 점유를 해제하고, 선행 그룹 완료 조건과 의존성이 허용하는 다음 작업을 선택한다.
- 병렬 분석은 수정 중인 작업 폴더의 변하는 내용을 읽지 않고 고정된 기준을 사용한다. 소스 수정이 필요해진 분석 작업은 수정 대기열로 넘긴다.
- 향후 단계별 동시 실행 수를 조정할 수 있게 설계하되, 값만 높여 공유 소스에서 동시에 수정·빌드하지 않는다. 작업 사본·빌드 결과 분리와 충돌 검증을 먼저 갖춘다.
- 초기 화면에 `요구사항 분석: 모든 모듈 병렬 / 나머지 모듈의 설계 이후: 선행 완료 필요 / 수정·빌드: 순차`를 구분해 표시한다.

### 5.4 각 모듈의 상세 흐름

**요구사항 분석 → 디자인 변경 → 코드 구현 → 빌드 → 검증 → 장비 테스트 → 모듈 완료**

여섯 번째 단계의 장비 테스트는 Windows 로컬, Linux 테스트 팜 또는 수동 테스트를 포함한다. 본 문서에서 보드팜 연동에 한정된 연결·예약·외부 작업 조회 항목은 수동 테스트에 그대로 적용하지 않고 아래 수동 결과 등록 절차로 대체한다. 선행 완료 조건과 필수 테스트 통과 기준은 모드에 따라 생략하지 않는다.

보드팜 연결·예약 상태는 테스트 단계와 별도로 보여준다. 보드 연결 및 준비는 앞 단계와 병행할 수 있으며, 실제 테스트는 필요한 이미지와 조건이 충족된 뒤 실행한다.

| 단계 | 작업 내용 | 주요 결과물 | 완료 조건 |
|---|---|---|---|
| 요구사항 분석 | 벤더 변경 목적, 신규 OS 반영 여부, 기능·호환성 요구사항, 의존성 분석 | 변경 목록, 요구사항, 분류 근거, 선행 조건, 검토 요청 | 변경별 처리 방향과 검증 요구사항 기록. 미결정 사항의 영향 범위 명시 |
| 디자인 변경 | 신규 API·인터페이스·초기화·전원 처리 등에 맞는 이식 설계 | 설계 변경 이유, 대안, 영향 범위, 수정 파일, 구현 지시 | 구현 범위·완료 조건 정의. 의존하는 사람 결정 해결 |
| 코드 구현 | OpenCode 기본 구현, 반복 문제·난항 시 Claude Opus 전환. OpenCode 변경은 Claude, Claude 변경은 Codex 리뷰 | 코드 변경, 커밋·차이, 전환·실행 로그, 리뷰 대상과 결과 | 계획한 변경 반영 또는 수정 불필요 근거 확인. 필수 리뷰 반영을 완료 조건에 포함하는 상세안은 §3.1 |
| 빌드 | 모듈 및 필요한 이미지 빌드, API·설정·의존성 확인 | 빌드 로그, 소스 기준, 산출물 식별 정보 | 해당 모듈에 필요한 빌드 성공 |
| 검증 | 정적 확인, 자동 테스트, 기능·회귀 확인 등 모듈 검증 수행 | 테스트 케이스, 통과·실패·미수행 결과, 근거 | 정의된 필수 검증 통과 또는 승인된 예외 기록 |
| 장비 테스트 | 선택한 로컬/테스트 팜 실행 또는 수동 적용·검증 및 결과 등록 | 보드·이미지·작업 ID, 장비 로그, 테스트 결과, 수동 수행자·시각 | 필수 장비 검증 통과 또는 승인된 제외·예외 기록. 수동 결과는 D-28의 확정 기준으로 완료 반영 |
| 모듈 완료 | 필수 단계와 검토 결정 반영 확인 | 모듈 결과 요약, 남은 예외, 완료 시점 | 필수 단계 완료 및 미해결 필수 이슈 없음 |

- 디자인 변경은 코드 수정 전의 설계 판단을 의미하며, UI 디자인 변경과 구분한다.
- 신규 OS에 이미 반영된 수정은 디자인·코드 구현을 해당 없음으로 처리할 수 있다. 확인 근거를 남기고 필요한 빌드·검증은 수행한다.
- 전체 분석 화면은 초기 범위와 이후 모듈 분석 결과를 함께 조회하되, 같은 분석을 전체 단계와 모듈 단계에서 중복 계산하지 않는다. 모듈 상세 분석을 첫 단계의 완료 조건으로 중복 요구하지 않는다.
- 개별 모듈 완료는 통합 빌드·전체 회귀 검증·최종 검토 완료를 의미하지 않는다.

#### 5.4.1 통합 이미지와 모듈 검증의 선후 관계

다음 순서를 설계 보완안으로 제안한다. 모듈 완료와 통합 이미지 생성이 서로를 기다리는 상황을 방지한다.

1. 먼저 선행 그룹의 준비된 변경을 순차 반영하고, 해당 그룹 검증에 필요한 이미지를 Linux에서 빌드한다. 나머지 모듈의 작업 완료를 조건으로 삼지 않는다.
2. 선택한 로컬/테스트 팜에 이미지를 전달·확인하거나 수동 테스트 담당자에게 이미지 묶음을 제공한다. 선행 그룹의 필수 부팅·장비 검증 결과 확인과 사람 결정 반영을 마친다.
3. 선행 그룹 전체 완료 후, 병렬 분석을 마친 나머지 모듈의 디자인 변경 이후 실행을 허용한다. 준비된 변경을 순차 반영하고 검증용 통합 이미지를 만든다.
4. 나머지 모듈의 장비 검증은 해당 검증용 이미지로 수행한다. 모든 모듈의 장비 검증 완료를 이미지 생성 조건으로 삼지 않는다.
5. 최종 통합 기준에서 필수 회귀 검증을 수행한다. 이전에 완료된 모듈도 변경 영향을 받으면 재검증한다.

나머지 그룹의 디자인 변경 이후 진입 조건은 선행 그룹 전체 완료로 고정한다. 요구사항 분석은 이 조건에서 제외한다. 선행 그룹 검증에 아직 대기 중인 나머지 모듈의 변경이 꼭 필요하다면 순환 의존으로 기록하고, 필요한 모듈을 선행 그룹에 포함할지 Jira에서 결정한다. 조건을 임의로 우회하지 않는다. 그룹 안의 세부 선행 조건은 필요한 변경·산출물·검증 결과로 정의한다.

#### 5.4.2 벤더 변경 추적과 검증 유효성

다음은 변경 누락과 오래된 검증 결과 사용을 방지하기 위한 설계 제안이다.

- 벤더 변경마다 ID를 부여하고 기존 원본·벤더 수정본·신규 원본의 기준, 목적, 관련 모듈을 기록한다.
- 변경별 처리 방향을 신규 OS에 이미 반영 / 이식 필요 / 제외 승인 / 판단 필요로 구분한다. 모듈 진행률만으로 변경 누락 여부를 판단하지 않는다.
- 변경 ID를 설계, 구현 결과, 빌드·테스트 결과 및 Jira 결정에 연결한다. 최종 검토 시 미분류·미반영·근거 없는 제외 항목이 없는지 확인한다.
- 검증 결과에는 소스 기준, 빌드 설정·도구, 이미지 목록·체크섬, 보드 및 테스트 버전을 연결한다.
- 관련 소스·의존 산출물·테스트 조건이 바뀌면 영향받는 결과를 재검증 필요로 표시한다. 영향 범위를 판단할 수 없으면 관련 검증을 다시 요구하거나 사람 검토로 연결한다.
- 과거 통과 기록은 보존하지만 현재 기준의 완료 근거로 자동 재사용하지 않는다. 필요한 재검증을 작업 목록과 진행률에 반영한다.

### 5.5 보드팜 연동 상태와 검증 결과

| 구분 | 상태 예시 | 표시 항목 |
|---|---|---|
| 연결 | 미설정 / 연결 확인 중 / 연결됨 / 오프라인 / 연결 실패 | Linux 또는 Windows 환경, 마지막 확인 시점, 오류 사유 |
| 보드 사용 | 미예약 / 예약 대기 / 예약됨 / 사용 중 / 해제됨 | 보드 ID·종류, 예약 및 사용 작업 |
| 이미지 준비 | 전달 대기 / 전달 중 / 일치 확인 / 적용 중 / 적용 완료 / 실패 | 소스·빌드 ID, 이미지 목록·체크섬, 수신 위치 |
| 테스트 실행 | 대기 / 실행 중 / 완료 / 실행 실패 | 테스트 작업 ID, 시작·종료 시점, 로그 |
| 테스트 결과 | 미검증 / 통과 / 실패 / 검토 필요 / 해당 없음 | 케이스별 결과, 실패 원인, 재검증 이력 |

- 보드팜 연결 성공은 테스트 통과를 의미하지 않는다.
- 연결 실패·예약 대기·테스트 실패를 구분하고 관련 이슈로 연결한다.
- 테스트 결과를 해당 모듈, 실제 보드와 실행한 이미지에 연결한다. 다른 이미지의 결과로 완료 처리하지 않는다.
- 재시도 시 이전 실패 결과를 보존하고 최신 실행 결과를 별도로 표시한다.
- 보드팜 서비스, API, 장비 목록, 예약 및 이미지 적용 방식은 아직 미정이다.
- 보드팜 연결 위치 선택은 확정했으며 구체적 실행 구성요소와 통신 방식은 §2.7의 제안을 환경 확인 후 결정한다.
- 보드 독점 사용과 예약 만료·연장을 관리하는 방안을 제안한다. 실행 여부를 확인할 수 없는 보드를 예약 만료만으로 즉시 재배정하지 않는다.
- 종료·취소 시 보드 복구 상태를 확인하고 사용을 해제한다. 이미지 적용·부팅 실패 후 복구되지 않은 보드는 사용 불가로 표시하고 후속 배정을 보류한다. 복구 명령과 수동 개입 기준은 실제 보드팜 환경에서 확정한다.

#### 5.5.1 수동 테스트 결과 등록 규칙

완료 반영 정책은 D-28로 확정했다. 아래 기록·회차 관리 방식은 상세 설계안이며 구체적인 필수 테스트와 근거 형식은 환경 확인 후 정한다.

- 테스트 회차를 먼저 만들고 대상 모듈, 필수 테스트 목록, 이미지 묶음 ID·체크섬, 대상 보드, 담당자를 연결한다. 자동 테스트와 같은 보드를 동시에 사용하지 않도록 수동 사용도 기록한다.
- 이미지 다운로드, 적용 시작, 테스트 수행, 결과 등록을 구분한다. 다운로드는 테스트 통과나 선행 그룹 완료를 뜻하지 않는다.
- 담당자는 수행 시각, 실제 보드·이미지 ID, 케이스별 통과/실패/미수행 결과와 로그 또는 재현 가능한 근거를 등록한다. 근거를 제출할 수 없는 필수 항목은 새 판단으로 Jira에 연결한다.
- 확정: 필수 테스트가 모두 통과하고 결과·로그 등 필수 근거와 실제 이미지·보드 정보가 현재 테스트 계획·회차에 일치하면 별도 사람 승인 없이 해당 테스트를 완료 반영한다. 단순 실패·미수행·입력 누락·불일치는 완료를 보류하고 보완 또는 재시도로 처리한다. 예외 허용이나 판정 불명확 등 새로운 판단이 필요한 경우만 Jira로 연결한다.
- 이 완료 처리는 해당 테스트 단계에 적용한다. 부트로더 선행 그룹 및 업그레이드 최종 완료는 나머지 필수 조건까지 충족해야 하며 최종 사람 검토를 생략하지 않는다.
- 실패 재시도는 새 테스트 회차를 만들고 수동 수행·결과 등록 대기로 전환한다. 수동 모드의 재시도 버튼이 장비를 자동 실행하는 것은 아니다.
- 테스트 도중 소스·이미지가 바뀌면 이전 결과를 보존하되 현재 완료 근거로 자동 재사용하지 않는다. 필수 테스트가 미완료면 선행 조건과 최종 완료를 해제하지 않는다.
- 테스트 팜과 수동 방식 전환 시 진행 중 작업의 종료·상태 확인을 먼저 수행하고 새 회차를 만든다. 연결 단절만으로 같은 보드에 수동 재실행을 자동 배정하지 않는다.

### 5.6 모듈 상세 화면의 공통 정보

- 담당 역할·에이전트·사람, 현재 단계, 실제 실행 유무와 시작·종료 시점
- 모듈 ID, 작업 ID, 실행 회차, 세션/외부 작업 ID, 마지막 상태 확인 시각과 이전 실행 이력. 배정 전에는 세션 없음으로 표시
- 단계별 상태와 완료 조건, 진행률, 선행 조건·대기 사유
- 변경 파일, 소스·커밋 기준, 설계 근거와 구현 결과
- 빌드·테스트·보드팜 실행 로그 및 산출물
- Linux 빌드 위치, 선택한 보드팜 환경과 연결 상태, 이미지 전달 상태, 실제 적용 이미지 및 외부 작업 ID
- 관련 이슈, 프롬프트 명령과 실행 이력
- 사람 검토 및 Jira 결정, 코드 반영·재검증 상태

### 5.7 모듈별 접기·펼치기 화면

모듈 목록은 선행 그룹과 병렬 그룹으로 나누고, 각 모듈을 펼치고 접을 수 있는 표 형태로 표시한다. 여러 모듈을 동시에 펼쳐 비교할 수 있다.

**접힌 행:** 펼침 표시, 모듈명·담당 역할, 여섯 단계의 상태 타일, 현재 단계·상태, 진행률(%)과 작은 진행 막대를 표시한다. 현재 실행이 없으면 담당 도구를 실행 중으로 표시하지 않는다.

| 모듈 / 담당 | 현재 단계 | 상태 | 진행률 |
|---|---|---|---|
| Bootloader / OpenCode | 보드팜 | 실패 · 재시도 가능 | 83% |
| Boot config / OpenCode | 모듈 완료 | 완료 | 100% |
| Ethernet / Claude | 분석 완료 · 디자인 변경 대기 | 후속 단계 선행 대기 | 17% |
| Camera / Claude | 요구사항 분석 | 실행 중 · 후속 단계 선행 대기 | 0% |

위 값은 화면 시안의 예시이며 실제 작업 데이터가 아니다.

- 행을 접어도 여섯 단계의 상태와 현재 처리 위치를 보여준다. 나머지 모듈은 분석 진행·완료 상태와 디자인 변경 이후의 선행 대기를 함께 표시한다.
- 필수 단계가 모두 완료된 모듈은 현재 단계를 모듈 완료, 상태를 완료로 표시한다.
- 현재 단계는 실행 중인 단계 또는 진행을 막고 있는 실패·검토·대기 단계로 정한다. 여러 단계가 병행 중이면 대표 단계와 추가 실행 수를 표시하는 방안을 제안한다.
- 색상만으로 상태를 구분하지 않고 상태 문구와 기호를 함께 표시한다.

**펼친 행:** 해당 모듈 바로 아래에 상세 표를 표시한다.

| 열 | 표시 내용 |
|---|---|
| 단계 | 요구사항 분석, 디자인 변경, 코드 구현, 빌드, 검증, 장비 테스트(로컬/팜/수동) |
| 상태 | 완료·실행 중·실패·검토 필요·대기·해당 없음 및 제안된 상태 확인 중·재검증 필요와 상태 기호 |
| 작업·결과 | 수행 내용, 결과 요약, 관련 파일 또는 로그 근거 |
| 상세 | 선택한 단계의 근거·로그·이슈·명령창을 여는 동작 |

- 현재 처리 단계의 행을 강조하고, 앞뒤 단계의 상태도 함께 보여준다.
- 상세 표 아래에 선행·대기 조건, 보드팜 연결, 보드 예약·사용, 테스트 실행 및 결과 요약을 표시한다.
- 보드팜 상세에는 선택한 Linux/Windows 환경, 마지막 연결 확인 시점과 이미지 전달·일치 확인 결과를 함께 표시한다. 모듈 요약에서는 대기 원인이 Jira 판단인지 수정·빌드 순서인지 보드팜 연결인지 구분한다.
- 단계별 상세 보기 또는 이슈·명령 열기로 해당 모듈·단계 문맥을 연결한다. 상세를 닫아도 모듈의 펼침 상태는 유지한다.
- 행을 펼치거나 접는 동작은 조회 동작이다. 에이전트 실행·재시도·Jira 생성은 별도 명령으로 처리한다.
- 키보드로도 펼치고 접을 수 있게 하고, 펼침 여부를 접근성 정보로 제공한다.
- 좁은 화면에서는 모듈 요약을 두 줄로, 상세 표를 단계별 행 묶음으로 재배치해 상태와 결과를 읽을 수 있게 한다.
- 초기 펼침 대상은 실패·검토 필요 모듈을 우선하는 방안을 제안한다. v0.4 시안에서는 기본적으로 Bootloader를 펼쳐 실패 단계와 재시도를 보여준다.
- 펼침 상태는 조회 상태로 보존한다. 사용자별 저장 범위와 유지 기간은 실제 구현 시 정한다.

### 5.8 실패한 단계 재시도

**실패 단계의 재시도 버튼은 사용자 요구사항으로 확정했다.** 아래 실행·기록 규칙은 상세 설계 제안이다.

- 펼친 상세 표의 실패한 단계 행에 `재시도` 버튼을 표시한다. 대상 단계·실패 이유·마지막 실행 회차와 로그를 함께 확인할 수 있게 한다.
- 버튼은 해당 단계의 재실행 요청을 접수한다. 전체 모듈을 처음부터 다시 실행하지 않으며, 재실행 전 입력·선행 조건·Jira 결정·실행 환경을 확인한다.
- 요구사항 분석 단계는 선행 그룹 완료 전에도 재시도할 수 있다. 나머지 그룹의 디자인 변경 이후 재시도에는 선행 그룹 전체 완료 조건을 적용한다. 미결정 Jira, 상태 확인 중 또는 중복 실행 중이면 해당 이유에 따라 재시도를 보류한다.
- 접수 후 같은 버튼을 반복 눌러 중복 실행하지 못하게 한다. 자원이 사용 중이면 `재시도 대기`, 배정 후에는 `실행 중`을 표시하며 수정·빌드 순차 정책을 따른다.
- 재시도는 새 실행 회차로 기록하고 이전 실패·로그를 보존한다. 실패한 보드팜 작업은 기존 외부 작업이 종료되었는지, 보드가 복구되었는지 확인한 뒤 배정한다.
- 재시도 성공이 곧 모듈 완료를 뜻하지 않는다. 후속 필수 검증을 계속하며 소스·이미지가 바뀌면 해당 결과를 재검증 필요로 처리한다.
- 코드 구현 단계 재시도 시 남아 있는 변경을 먼저 확인한다. 같은 변경을 중복 적용하거나 사용자 수정을 덮어쓰는 초기화를 자동 수행하지 않는다.
- 새 판단 없이 해결할 수 없는 실패는 프롬프트 명령 또는 Jira 검토로 연결한다. 재시도 버튼을 누른 사실을 새 설계·예외의 승인으로 취급하지 않는다.

## 6. 전체 및 그룹별 진행률 표시

진행률은 코드 수정량이나 실행 시간이 아니라 필수 작업의 완료 조건을 기준으로 계산한다.

| 지표 | 표시 내용 |
|---|---|
| 전체 진행률 | 요구사항 분석, 모듈별 필수 작업, 통합 검증 및 최종 검토를 포함한 완료율 |
| 단계별 종합 완료율 | 전체 대상 모듈의 분석·구현·검증·빌드·테스트별 완료율. §5.1의 매핑으로 계산 |
| 이번 실행 범위 진행률 | 분석만 실행 등 Start에서 선택한 범위의 완료율. 전체 업그레이드 진행률과 별도 표시하는 방안 제안 |
| 선행 그룹 진행률 | 부트로더 관련 선행 모듈의 필수 작업 완료율(%) |
| 병렬 그룹 진행률 | 나머지 병렬 모듈의 필수 작업 완료율(%) |
| 모듈별 진행률 | 요구사항 분석·디자인·코드·빌드·검증·보드팜 필수 작업의 완료율 |
| 보드팜 검증 현황 | 연결 상태, 예약 대기 수, 실행 중 테스트, 통과·실패·미검증 수 |
| 통합 검증 현황 | 통합 빌드 및 전체 기능·회귀 검증 상태 |
| 사람 검토 대기 | 해결되지 않은 검토 항목과 진행을 막는 작업 수 |

계산 원칙:

- 초기에는 정의된 필수 작업 단위에 동일 가중치를 적용하는 방안을 제안한다. 모듈별 필수 테스트가 여러 건이면 작업 단위를 명시한다.
- 완료 작업 가중치 합 / 적용 대상 필수 작업 가중치 합 × 100으로 계산하는 방안을 기본으로 한다. 실행 중인 작업의 임의 추정치는 완료로 계산하지 않는다.
- 전체 요구사항 분석 표시와 모듈 분석, 그룹별 집계 등 같은 작업을 중복 합산하지 않는다.
- 그룹 진행률의 단순 평균으로 전체 진행률을 계산하지 않는다. 전체는 원래 필수 작업을 기준으로 집계한다.
- 상단 다섯 단계 완료율의 단순 평균으로 전체 진행률을 계산하지 않는다. 단계별 작업 수와 통합 검증·최종 검토의 포함 범위가 다르므로 같은 원본 작업 기록으로 각각 계산한다.
- 모듈별 난이도 가중치를 적용할 경우 기준과 변경 이력을 공개한다.
- 해당 없음 항목은 근거 확인 후 계산 대상에서 제외한다. 적용 대상 작업이 없는 그룹은 100% 대신 해당 없음으로 표시한다.
- 분석·계획 중 작업이 추가되면 진행률이 내려갈 수 있으며 변경 이유를 표시한다.
- 사람 검토 결정 후 코드 반영·재검증이 필요하면 그 작업이 끝나기 전까지 완료하지 않는다.
- 보드팜이 필수인 모듈은 미연동·예약 대기·미검증 상태에서 완료하지 않는다. 제외·예외는 사람 결정과 이유를 남긴다.
- OS Upgrade 내부 완료와 최종 완료를 구분한다. 최종 검토까지 끝나야 전체 100% 및 최종 완료로 표시한다.
- 정확한 작업 단위, 가중치 및 예외 처리 산식은 구현 설계 시 확정한다.
- 분석만 실행한 작업은 선택 범위에서 완료될 수 있지만 전체 업그레이드 완료를 뜻하지 않는다. 실행 범위를 명시하여 서로 다른 100%가 혼동되지 않게 한다.
- 재검증 필요 항목은 현재 기준의 완료 분자에서 제외하고 진행률 변경 사유를 표시하는 방안을 제안한다. 작업·의존성 기준이 바뀌면 집계 기준 버전도 기록한다.
- 진행률은 작업 완료율이며 남은 시간의 추정치가 아니다. 원인별 대기 수와 실패·재검증 수를 함께 표시한다.
- 선행 그룹 완료 전에도 나머지 그룹의 분석 진행·완료를 표시하고 완료 결과를 집계한다. 디자인 변경 이후에는 선행 대기를 표시한다. 실행 허용 여부는 완료 조건과 결과 유효성으로 판단하며 진행률 숫자만으로 대기를 해제하지 않는다.

## 7. 이슈 대응 프롬프트 명령창

### 7.1 목적과 입력

이슈 상세 화면에서 관련 문맥을 확인하고 에이전트에 후속 작업을 지시한다.

명령에 연결할 정보:

- 업그레이드 작업 및 이슈 ID
- 대상 모듈과 적용 범위
- 오류 로그, 코드 변경, 이전 실행 결과
- 이전 수정·검증 시도
- 관련 Jira 결정과 작업 제약
- 사용자가 입력한 프롬프트

### 7.2 명령 예시

- 이 빌드 오류의 원인을 분석하고 수정 방안을 정리해줘.
- 해당 모듈의 벤더 수정 의도가 신규 API에서도 유지되는지 확인해줘.
- Jira에 기록된 결정에 따라 해당 모듈을 수정하고 재검증해줘.

예시는 기능 설명이며 실제 실행 지시가 아니다.

### 7.3 처리 흐름

**이슈 선택 → 문맥·적용 범위 확인 → 명령 접수 → 실행 → 결과 기록 → 재검증 → 이슈 해결 여부 판단**

- 명령 작성자, 시점, 대상 에이전트, 적용 범위와 결과를 기록한다.
- 동일 모듈 또는 공유 소스·빌드 자원의 실행 중 작업과 충돌하면 대기 상태로 접수한다. 프롬프트를 통한 수정도 §5.3의 선행 그룹 완료 조건과 순차 실행 정책을 따른다.
- 요구사항 분석만 요청하는 명령은 선행 그룹 완료 전에도 허용한다. 분석 명령에 포함된 수정·빌드·장비 실행은 별도 작업으로 분리하고 각 단계 조건을 확인한다. 분석 단계 선택만으로 후속 실행 조건을 우회하지 않는다.
- 명령 실행 성공과 이슈 해결을 구분한다. 관련 검증을 통과해야 해결로 판단한다.
- 사람 검토 사항이 발견되면 검토 목록 및 Jira 처리 흐름으로 연결한다.
- 명령이 기존 계획이나 결정 범위를 바꾸면 변경 이유와 영향을 남긴다.
- 명령 ID로 접수·실행·결과를 연결하고 중복 전송을 구분하는 방안을 제안한다. 실행 중 세션에 새 프롬프트를 무조건 끼워 넣지 않고 차례를 기다리거나 명시적인 중지·취소 절차를 따른다.
- 대기 중 소스 또는 Jira 결정이 바뀌면 실행 직전에 문맥과 적용 범위를 다시 확인한다. 새 판단이 필요한 부분만 검토로 넘기고 기존 결정 범위를 임의로 넓히지 않는다.

## 8. 사람 검토 및 Jira 목록

### 8.1 검토 대상

- 벤더 변경의 의도가 불명확한 경우
- 신규 OS에 이미 반영되었는지 판단하기 어려운 경우
- 구현 대안 사이에서 기능·유지보수·호환성 선택이 필요한 경우
- 검증 불가 또는 실패 항목에 대해 예외 판단이 필요한 경우
- 기존 계획을 넘어서는 변경이 필요한 경우

### 8.2 목록 필드

| 필드 | 내용 |
|---|---|
| 검토 항목 ID | Jira 생성 전부터 유지하는 내부 식별자 |
| 관련 작업·모듈 | 업그레이드 작업, 변경사항, 모듈 및 이슈 |

### 8.3 처리 흐름

**새 판단 필요 발견 → 내부 검토 항목 기록 및 영향 범위 지정 → Jira 연결 → 사람 검토·결정 → 결정 기록 → 해당 작업 재개·구현·검증 → 검토 항목 완료**

- 진행 중 새 판단이 필요한 사항을 Jira 티켓으로 연결한다. 기존 결정과 실행 범위로 처리할 수 있는 작업은 선행 조건에 따라 계속 진행한다.
- 검토 항목에 의존하는 단계와 후속 작업만 대기시킨다. 선행 그룹의 미결정 검토는 나머지 그룹의 디자인 변경 이후를 막지만, 해당 판단에 의존하지 않는 요구사항 분석은 전체 모듈에서 계속할 수 있다.
- 단순 빌드 실패나 연결 오류는 우선 실행 이슈로 기록한다. 새로운 설계 선택·범위 변경·예외 허용 등 사람 판단이 필요해질 때 Jira 검토로 전환한다.
- Jira 연결 원칙은 확정했다. 자동 생성 실행 방식과 프로젝트별 필수 입력값은 실제 Jira 환경 확인 후 결정한다.
- Jira 생성 실패 시에도 내부 검토 항목을 유지하고 재시도 상태를 표시한다.
- 동일 검토 항목으로 중복 티켓을 생성하지 않는다.
- Jira 결정 완료와 코드 반영·검증 완료를 구분한다.
- Jira 처리 상태의 동기화 방식과 주기는 연동 설계 시 확정한다.

다음 동기화 규칙은 설계 보완안이다.

- 사람 결정의 기준은 Jira의 명시된 결정 내용으로, 실행·구현·검증 상태의 기준은 대시보드 기록으로 구분한다. 양쪽에서 같은 상태를 서로 덮어쓰지 않는다.
- Jira 완료 상태만으로 후속 구현을 시작하거나 검토 항목을 완료하지 않는다. 결정 내용·결정자·적용 대상 버전을 확인한 뒤 실행 범위와 대기 해제 대상을 정한다.
- Jira 생성 응답을 받지 못했으면 내부 검토 ID로 기존 티켓부터 확인한다. 생성 여부가 불명확한 동안 새 티켓을 반복 생성하지 않는다.
- Jira 장애가 나도 내부 검토 항목과 영향받는 작업의 대기를 유지한다. 실행이 허용된 독립 작업은 계속하며 동기화 복구 후 연결 상태를 확인한다.
- 중복·지연된 변경 알림이 와도 같은 결정을 중복 실행하거나 최신 결정을 과거 상태로 되돌리지 않도록 결정 버전과 반영 이력을 기록한다.
- 초기 동기화는 Linux 실행 측이 선택한 직접 연결 또는 MCP 연결을 통해 Jira를 주기적으로 조회하는 방안을 우선 검토한다. 웹훅을 사용하면 외부 연결 가능 여부와 알림 누락 시 재조회 방법을 확인한다. 선택한 MCP가 제공하는 조회·검색 기능에 맞춰 동기화 가능 여부를 확인한다.
- 사용자 확인: 사내 Jira를 사용한다. 실제 URL, 배포 형태·버전, 인증, 프로젝트, 이슈 유형과 필수 필드는 설정 단계에서 확인한다. 현재 사내 Jira나 Claude의 MCP에 실제 접속하여 검증한 상태는 아니다.

### 8.4 Jira 연결 설정 및 Claude MCP 목록

**사내 Jira를 직접 설정하거나 Claude의 연결된 MCP 목록에서 선택하는 방식은 D-35로 확정했다.** 다음 필드·상태·연결 확인 절차는 상세 설계안이다.

| 연결 방식 | 사용자 설정 | 연결 확인 |
|---|---|---|
| 직접 설정 | 사내 Jira URL, 인증 방식·보관된 자격증명 참조, 프로젝트, 이슈 유형, 담당자·결정 필드 매핑 | 실행 위치에서 접근 가능 여부, 조회 권한, 필요한 생성·수정 기능과 필수 필드 |
| Claude MCP 선택 | 지정 Linux 계정·프로젝트에서 Claude가 사용하는 MCP 목록 조회, Jira 기능을 제공하는 연결 선택, 프로젝트·이슈 필드 설정 | 설정에 등록된 상태와 실제 연결 성공을 구분. 제공 도구와 해당 계정의 권한 확인 |

- MCP 목록은 현재 작업의 Claude 실행 환경을 기준으로 한다. 이 대화의 Codex 도구 목록이나 다른 계정의 연결을 Claude의 목록으로 간주하지 않는다.
- 목록에는 MCP 이름, 실행 환경·설정 범위, 등록/연결/오류 상태, 마지막 확인 시각, Jira 조회·검색·생성·수정 지원 여부를 표시한다. 목록 새로고침과 연결 확인을 제공하고 Jira 기능이 있는 항목을 구분한다.
- 도구 이름만 보고 기능을 확정하지 않는다. 실제 도구 정의와 연결 확인 결과를 근거로 표시하며 읽기 전용 연결은 생성 가능한 연결과 구분한다. 연결 확인만으로 시험 티켓을 생성하지 않는다.
- MCP 목록·도구 정보를 프로그램으로 가져오는 방법과 인증 재사용 가능 여부는 설치된 Claude 환경에서 검증한다. 자동 조회가 지원되지 않으면 연결 프로필을 직접 등록하도록 안내하고 자동 조회 성공으로 표시하지 않는다.
- 화면에 인증 토큰·비밀 환경 변수·원본 인증 설정을 노출하지 않는다. 직접 연결은 인증 정보를 프롬프트 대신 연결 설정으로 관리하고, MCP 선택은 기존 연결 설정 참조를 우선한다.
- 하나의 Jira 연결 경로를 작업에 지정한다. 직접 연결과 MCP가 같은 검토 항목을 각각 생성하지 않게 하며 내부 검토 ID·Jira 티켓 키·연결 프로필을 기록한다. 연결 변경 시 기존 티켓을 먼저 확인한다.
- 연결이 없거나 생성·수정 기능이 부족하면 내부 검토 목록에 미연결·생성 대기·동기화 대기 사유를 표시한다. 영향받는 작업의 대기는 유지하고 독립 작업은 계속한다. 연결 복구 후 기존 티켓 존재 여부부터 확인한다.
- Jira 결정과 실행 상태의 기준, 중복 방지, 새 판단만 티켓으로 연결하는 원칙은 두 연결 방식에 동일하게 적용한다. MCP 사용 자체가 결정 승인이나 실행 완료를 의미하지 않는다.

### 9.1 전체 화면 비교 결과

v0.6에서 다음 다섯 안을 비교했고, 사용자가 **3번 모듈 비교형**을 선택했다. 명칭은 모두 '종합 진행도'로 통일했으며 이후 화면 개선은 선택한 모듈 비교형을 기준으로 한다.

| 시안 | 화면 배치와 확인 초점 |
|---|---|
| 균형형 | 위에 종합 진행도, 아래에 모듈 상세와 오른쪽 실행·Jira·명령 영역. 전체 현황과 조치를 함께 확인 |
| 진행률 중심형 | 단계별 긴 진행 막대와 큰 전체 완료율, 아래에 넓은 모듈 표와 연동·조치 영역. 진행률 차이를 빠르게 비교 |
| 모듈 비교형 | 종합 진행도를 짧게 요약하고 모듈 행에 여섯 단계 상태를 나란히 표시. 행을 펼쳐 상세·재시도 확인 |
| 문제 대응형 | 선행 대기 원인과 현재 조치·명령 영역을 강조하고 옆에 모듈 상세 배치. 실패 대응에 집중 |
| 선행·후속 분리형 | 선행 그룹과 나머지 그룹의 모듈을 좌우로 구분. 선행 완료 여부와 후속 작업 대기 관계 확인 |

- 모든 안에 모듈별 접기·펼치기, 실패 단계 재시도, Jira 검토, 프롬프트 명령과 Linux/Windows 보드팜 선택을 유지한다.
- 색상뿐 아니라 완료율·완료 수·실패·대기 문구로 상태를 구분한다. 같은 정보를 반복하기보다 각 안의 주된 확인 목적에 맞게 배치한다.
- 비교안은 검토 이력으로 남기고, 현재 시안은 모듈 비교형 한 가지를 다듬는다. 5개 운영 화면이나 실제 시스템을 각각 구현한다는 의미가 아니다.

### 9.2 선택한 모듈 비교형의 표시 규칙

- 상단 종합 진행도에는 큰 완료율·완료 수·진행 막대를 배치한다. 전체 완료율, 통합 검증과 최종 검토는 별도로 표시한다.
- 모듈 행에서 여섯 단계를 같은 열에 정렬하고 완료·진행·실패·검토·선행 대기를 아이콘과 문구로 함께 표시한다. 실행 중·실패한 현재 위치를 강조한다.
- 모든 모듈의 분석 열은 선행 조건과 분리한다. 나머지 모듈은 분석 완료/실행 중과 설계 이후 잠김을 한 행에서 비교할 수 있게 한다.
- 행을 펼치면 단계별 결과·재시도와 실행 회차·담당 도구·세션 정보를 표시한다. 접기·펼치기만으로 실행이 시작되지는 않는다.
- Linux 빌드, Windows/Linux 실행 모드와 테스트 방식, Jira 목록, 이슈 명령은 모듈 표 아래에 배치한다. 수동 방식은 이미지 묶음과 결과 등록 상태를 표시한다. 좁은 화면은 단계 타일과 하단 영역을 여러 줄로 재배치한다.
- v0.7 시안의 수치·세션·모듈명은 모두 예시다. 시작·재시도·명령은 시안 상태만 바꾸며 실제 연결이나 작업을 수행하지 않는다.

## 11. 사용자 지시 이후의 구현 단계 제안

아래는 향후 순서 제안이며 현재 구현에 착수하지 않는다.

1. **현황 확인 및 설계 확정:** Linux 서버·계정·소스 경로·빌드 명령, 에이전트 실행 방식, Jira 종류 및 Linux/Windows 보드팜 환경을 확인한다. 현재 구조, 제안 아키텍처, 변경 파일, 데이터 저장 구조, 충돌 가능성과 미결정 사항을 정리한다.
2. **역할별 지침 작성:** CLAUDE.md와 분석·구현·검증·사람 검토 역할별 세부 지침을 작성한다.
3. **상태·결과 형식 정의:** 작업·모듈·단계·명령·실행 회차·벤더 변경·검토 항목과 소스·이미지·보드·테스트 근거의 연결 형식을 정한다. 선행 그룹 완료 조건, 단계별 실행 제한과 연동 공통 형식을 정의한다.
4. **최소 연동 확인:** 지정 계정·폴더에서 에이전트 지침 로딩·결과 수집과 Linux 빌드 호출을 확인한다. 초기 장비 테스트는 이미지 묶음 다운로드·수동 결과 등록 흐름을 확인하며 테스트 팜 연결을 요구하지 않는다. 실제 연동 미확인 항목을 완료로 표시하지 않는다.
5. **조회 화면 구성:** 상단 다섯 단계의 모듈 종합 완료율, 그룹별 진행률, 모듈별 접기·펼치기, 선행 대기, 재시도 버튼, 단계별 실행 정책, 보드팜 환경 선택·연결·이미지 전달 상태 및 집계를 구현한다.
6. **작업 실행 및 이슈 명령 연결:** 전체 모듈 분석 병렬, 나머지 모듈의 설계 이후 선행 완료 조건, 수정 및 빌드 순차 배정, 프롬프트 대기열, 재시도·중복 방지·중지·재개·상태 확인을 구현한다. 브라우저·SSH 종료 후 작업 유지와 재접속 조회를 확인한다.
7. **Jira 검토 연결:** 새 판단 항목 연결, 영향받는 작업만 대기, 선행 조건을 충족한 독립 작업 계속, 생성 실패·중복 방지, 결정과 후속 구현·재검증 연결을 구현한다.
8. **수동 장비 테스트:** 이미지 묶음 다운로드, 테스트 회차·보드·수행자·결과·근거 등록 및 D-28 완료 판정을 제공한다. 재시도는 새 수동 회차를 만들고 결과를 기다린다. Windows 로컬 도구·Linux 테스트 팜의 자동 연결·예약·적용·결과 수집·취소·복구는 후속 구현으로 분리한다.
9. **단계별 및 통합 확인:** 아래 시나리오로 정책과 복구를 확인한다. 로컬 확인과 실제 외부 연동 결과를 구분한다. 수정·빌드 병렬화는 작업 사본·빌드 결과 분리와 충돌 검증을 갖춘 별도 후속 단계로 둔다.

## 13. 현재 산출물과 제외 범위

- 현재 산출물: 본 Markdown v0.7.8 검토본 및 모듈 비교형 v0.7 예시 화면 시안. 시안의 수동 결과·시작 범위·담당 도구·자동 테스트 연결은 결정 전 예시이며 최신 확정 기준은 본 문서 D-28·D-01·D-11·D-30·D-34를 따른다. 미결정 항목은 §10.2~10.3에 명시한다.

- 초기 7단계·상단 3단계 화살표 및 v0.6의 5개 비교 화면은 이전 시안이다. 현재는 사용자가 선택한 모듈 비교형을 기준으로 한다. 최신 실행 규칙은 본 문서 v0.7.8을 따른다. 시안의 진행 중 예시는 최초 계획 확인 후 상태로 해석한다.

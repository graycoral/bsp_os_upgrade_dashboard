# 회사 대시보드로 코드 이식하기

Codex 세션의 모델별 위임 지침은 원본 개발 도구 규칙이며 회사 Claude 설치나 이식의 필수 의존성이 아니다. 회사 현지 지침과 도구·모델 정책을 우선하고 구현·독립 리뷰·시험 역할과 실제 증거를 유지한다. 제품 실행 중 BSP 에이전트 정책은 별개다.

이 저장소에서 구현·검증한 코드와 시험을 회사 대시보드에 재사용한다. 회사판은 별도로 발전한 프로젝트이므로 회사 추가 기능을 보존하며 구조가 다른 연결 부분을 수정한다. 문서는 코드의 위치·의도·검증 방법을 안내한다. 로컬 검증 완료와 회사 환경 인수 완료는 구분한다.

2026-11-05 GUI Test 현재 경로는 [구조 계약](../design/GUI_TEST_LAYOUT.md)을 따른다. 과거 `gui_test/`는 단독 앱 `apps/gui-test/`, Python `backend/gui_test/`, 공유 화면 `packages/gui-test-ui/src/`로 나뉜다. 독립 반입은 세 경로 내보내기를 사용하며 설치 wheel의 `gui_test.*`는 유지한다. 고정 커밋 PORT 문서와 과거 로그의 경로는 해당 버전의 근거로 보존한다. 회사 적용 시 선택한 커밋의 구조를 COMPANY_MAP에 대응하고 과거 파일명을 현재 경로로 일괄 치환하지 않는다.

TC 목록 대기 설정·진행 표시 이식은 [PORT-005](PORT-005.md)를 따른다. 원본 기준은 `0a378cda23262cafaa8f962c3c7eae5765a18755`이며 대상 코드 `7cad856f65798e3891e200d60e1301057161e3b8`은 로컬 검증 후 고정했으며 회사 인수는 별도다. 기존 승인 Runner ZIP/EXE를 유지하고 Linux 호출자·공유 UI와 선택적 소스 마법사만 갱신한다.

## 저장 위치와 담당

| 위치 | 파일 | 담당·내용 |
|---|---|---|
| 원본 저장소 | `docs/porting/README.md` | 공통 절차와 요청문. 원본 작업자가 유지 |
| 원본 저장소 | `docs/porting/PORT-001.md` 등 | 기능별 고정 커밋·선행 조건·변경 위치·시험. 원본 작업자가 작성 |
| 원본 저장소 | 기존 코드·시험 경로 | 코드·시험을 문서 폴더에 복제하지 않고 Git 커밋으로 참조 |
| 회사 저장소 | `docs/porting/COMPANY_MAP.md` | 회사 담당 에이전트가 원본과 회사의 구조 대응·보존할 기능·검증 명령 기록 |
| 회사 저장소 | `docs/porting/APPLIED.md` | 회사 담당 에이전트가 기능별 적용 범위·회사 커밋·시험·미완료 기록 |

회사 구조·내부 경로·적용 기록은 회사 저장소에서 관리한다. 공개 원본에는 아래 빈 양식만 둔다. 비밀정보는 어느 기록에도 넣지 않는다.

현재는 이식 절차·양식과 [다이어그램 탭 PORT-001](PORT-001.md)을 제공한다. PORT-001의 소스·시험·호스트 접점과 원본 구현 커밋을 고정했으며 실제 검증 결과와 전달 기준은 해당 안내서에서 확인한다. 시험 당시 미커밋 manifest와 이후 고정한 커밋은 구분한다. 회사 코드·적용 상태와 실제 ACON 인수는 아직 확인하지 않았다.

## 재사용 기능 스킬

[공통 portable-feature 지침](../../.agents/skills/portable-feature/SKILL.md)은 승인된 재사용 기능 개발과 PORT 준비·적용에 사용한다. Codex는 `.agents/skills`의 본문을 `$portable-feature`로, Claude Code는 `.claude/skills`의 얇은 진입점을 `/portable-feature`로 사용한다. OpenCode는 두 디렉터리를 지원하며 어느 진입점에서도 같은 본문을 읽는다. 사용 가능한 skill 도구로 `portable-feature`를 불러오도록 요청한다. 자동 발견이 불가능하면 공통 `SKILL.md`를 직접 읽는다.

회사에 두 스킬 디렉터리와 참조하는 `docs/porting`, 관련 코드·계약을 복사하고 기존 지침에는 짧은 연결만 병합한다. 회사 정책을 덮어쓰지 않는다. 디렉터리 지원은 [Codex](https://learn.chatgpt.com/docs/build-skills), [Claude Code](https://code.claude.com/docs/en/skills), [OpenCode](https://docs.opencode.ai/docs/skills/) 문서 기준이며 실제 설치 CLI의 발견·호출은 NOT_RUN이다.

## 처음 한 번 준비

1. 사용자는 원본을 회사 프로젝트와 별도 폴더에 받는다. 이식할 기능을 지정하고 원본 경로·회사 경로를 에이전트에게 알려준다. 원본은 비교 자료로 사용한다.
2. 회사 담당 에이전트는 회사 브랜치·미커밋 변경·필수 지침을 확인한다. `docs/porting/README.md`와 `templates/`를 회사에 가져오되 기존 파일이 있다면 비교해 갱신한다.
3. [구조 차이 양식](templates/COMPANY_MAP_TEMPLATE.md)을 회사의 `docs/porting/COMPANY_MAP.md`로, [적용 이력 양식](templates/APPLIED_TEMPLATE.md)을 회사의 `docs/porting/APPLIED.md`로 복사한다. 기존 기록이 있으면 이어서 갱신한다.
4. 관련 기능부터 원본·회사 대응 위치와 이미 적용된 동작을 조사한다. 같은 Git 이력이 남아 있으면 공통 조상을 참고하되, 커밋 해시나 코드 모양만으로 적용 완료를 판단하지 않는다. 모르는 상태는 `UNKNOWN`으로 둔다. 회사 프로젝트 전체를 처음부터 분석할 필요는 없다.
5. 회사 `AGENTS.md`와 `CLAUDE.md`의 기존 지침을 유지하면서 아래 안내를 연결한다. 원본의 역할 지침 전체로 회사 지침을 교체하지 않는다. OpenCode 등 도구의 실제 지침 로딩 여부는 회사 설치 환경에서 확인한다.

```text
회사 이식 작업은 docs/porting/README.md를 따른다.
회사 필수 지침 → 기능별 이식 안내서 → COMPANY_MAP.md·APPLIED.md →
관련 코드·시험 → 필요한 상세 설계 순으로 읽는다.
회사 추가 기능을 보존하고, 코드 재사용·회사 검증·적용 이력을 함께 남긴다.
```

## 여기서 기능을 전달할 때

1. 기능 하나를 검토 가능한 변경 단위로 묶는다. 관련 코드·시험·설계는 함께 변경하고 관련 없는 정리는 분리한다. 기존 기능도 같은 방식으로 이식 안내서를 작성할 수 있다.
2. [기능 안내 양식](templates/PORT_TEMPLATE.md)을 다음 미사용 `PORT-NNN.md`로 복사하고 이 문서에 목록을 추가한다. 요구사항·시험 ID와 원문 절을 연결하고 계약 필드 전체를 복제하지 않는다.
3. 원본 기준 커밋과 대상 코드 커밋을 전체 해시로 고정한다. 대상 코드가 먼저 커밋된 뒤 그 해시를 안내서에 기록해 문서 커밋을 만든다. 안내서가 가리키는 코드와 실제 시험 기준의 차이가 있다면 그 차이와 미검증 범위를 밝힌다. 안내서 자기 자신의 커밋을 미리 적지 않는다.
4. 선행 PORT/커밋·의존성·설정·DB 영향·복원 방법, 신규 모듈과 회사 조정 접점을 명시한다. 기준 커밋이 회사의 마지막 적용 커밋과 같다고 가정하지 않는다. 회사가 일부만 가져갔다면 기능별 이력으로 대조한다.
5. 고정 커밋의 코드와 관련 시험을 제공한다. 선택한 커밋 또는 파일 범위의 패치를 추가 제공할 수 있다. 광범위한 누적 diff를 그대로 적용하지 말고 선행 변경 누락과 관련 없는 변경 포함 여부를 확인한다. 별도 패치 파일을 전달하면 생성 기준·파일 범위·SHA256을 기록한다.
6. 실제 실행한 시험 명령·환경·기대 결과·증거와 `NOT_RUN/BLOCKED`를 안내서에 적는다. 로컬/Mock와 회사/장비 인수를 분리한다. 검토되지 않은 내용을 독립 리뷰 완료로 표시하지 않는다.

## 회사에서 매번 이식할 때

1. 회사 필수 지침·공통 운영 정책을 확인한 뒤 해당 PORT 안내서, `COMPANY_MAP.md`, `APPLIED.md`와 관련 코드·시험부터 읽는다. 원본의 일반 개발용 문서 전체를 반복해서 읽지 않는다. 의존성·계약·정책이 불명확하면 필요한 원문을 추가 확인한다.
2. 선택한 PORT/기능에 한정해 `APPLIED.md`의 증거로 완전 반영이 확인된 원본 기준과 최근 조사·부분 적용 목표를 구분한다. 완전 반영 기준이 없으면 UNKNOWN이다. 업데이트 목록은 완전 반영 기준→새 PORT 고정 대상의 차이, 기존 미반영·보류·실패 항목, 선행 영향을 합치고 중복을 제거해 각 항목을 모두 대조한다. 관련 diff·manifest·코드·시험과 선행 PORT·계약·설정·데이터 영향, 회사의 미커밋 변경을 확인한다. 이미 반영된 부분은 회사 코드·시험으로 확인해 중복 적용에서 제외한다. 저장소 전체 HEAD를 모든 기능의 적용 기준으로 삼지 않는다. 전체 Git 이력이 없으면 두 고정 소스 snapshot을 비교하고 기준을 모르면 적용 완료를 추정하지 않는다. 최초 기록이 없으면 선택 기능의 접점만 조사해 기존 상태 어휘로 기록한다.
3. 신규 독립 모듈은 의존성과 시험을 함께 가져온다. 변경되지 않은 접점은 선택 커밋/패치로 반영하고, 회사가 수정한 곳은 원본 변경 전·후와 회사 코드를 비교해 필요한 동작만 반영한다. 파일 전체 덮어쓰기나 재구현을 기본으로 삼지 않는다.
4. 원본 코드와 다르게 구현한 부분은 이유·대응 경로를 남긴다. 같은 파일을 고쳤거나 패치가 깨끗하게 적용되었다는 사실만으로 의미상 호환을 단정하지 않는다. 회사 기존 게이트·데이터·추가 기능을 유지한다.
5. 지정 시험과 영향받는 회사 회귀 시험을 실행하고 명령·환경·코드 기준·증거를 기록한다. 원본 시험을 회사 구조에 맞게 조정할 때도 인수 조건을 약화하지 않는다. 전체 로그는 파일에 보관하고 요약·실패 지점부터 확인한다. 필요한 독립 리뷰는 회사 지침대로 별도로 수행한다.
6. `APPLIED.md`에 적용 범위·원본/회사 커밋·시험·미완료를 추가하고 구조 변화는 `COMPANY_MAP.md`에 반영한다. 회사 코드 커밋 후 그 해시를 후속 기록 커밋에 적을 수 있다. 미커밋 상태라면 해시를 꾸미지 말고 변경 파일/해시와 미커밋 상태를 남긴다.

회사 기록에 변경별 추적표를 남긴다: 변경 목록 → 기능별 적용·이미 존재·회사 맞춤·보류·해당 없음과 이유 → 파일 대응 → 지정 시험 → `APPLIED.md` 갱신. 제안 처리와 실제 처리를 구분하며 조사만으로 완전 반영 기준을 전진하거나 적용 상태를 변경하지 않는다. 구조 대응은 `COMPANY_MAP.md`를 사용하며 계약 필드를 복제하지 않는다. 승인된 기능의 통상 판단은 자율 진행하고 모호한 범위·정책 충돌·파괴적인 데이터 변경은 멈춰 질문한다. 원본 PASS와 회사 코드 동등 확인은 실제 회사 인수 PASS가 아니다.

적용 상태와 검증 상태는 별도다. 코드가 모두 반영되면 `APPLIED`, 일부만 반영되면 `PARTIAL`, 판단/환경 문제로 진행할 수 없으면 `BLOCKED`, 확인 전이면 `UNKNOWN`이다. `APPLIED`만으로 회사 인수 완료를 뜻하지 않는다. 시험은 실제 실행별 `PASS/FAIL/BLOCKED/NOT_RUN`로 남기고, 과거 FAIL·부분 적용 기록을 삭제하지 않는다.

사용자는 전달할 기능을 선택하고 원본을 회사에서 받아 이식 작업을 지시한다. 실제 회사 환경·장비 인수는 사용자가 승인한 범위에서 진행한다. 이 절차와 코드 이식 지시는 실제 장비 적용·BSP 실행·Jira 발송을 자동 승인하지 않는다.

## Claude 또는 OpenCode에 보낼 요청문

아래 경로와 ID를 실제 값으로 바꾼다. 조사만 요청하거나 지정 기능 적용을 요청할 수 있다. 회사 기록이 없으면 위 준비 절차로 만든다. 원본에 해당 PORT 안내서가 없다면 원본에서 작성해 전달할 항목이며, 회사 에이전트가 원본 검증 결과를 추측해 만들지 않는다.

업데이트 조사만 요청할 때:

```text
원본 저장소: <다운로드한 원본 폴더>
회사 저장소: <회사 대시보드 폴더>
조사할 PORT/기능: <지정 목록>

회사 지침과 이식 절차를 따라 기능의 증거 있는 완전 반영 기준과 최근 조사·
부분 적용 목표를 구분해라. 기준→새 PORT 고정 대상 차이와 기존 미반영·
보류·실패 항목 및 선행 영향의 합집합을 중복 제거해 각 항목을 대조해라.
관련 diff·manifest·코드·시험, 선행 PORT·계약·설정·데이터 영향을 확인해라.
회사 코드·시험으로 이미 반영된 부분을 확인하고 제안 처리와 실제 처리를
구분해 이유·파일 대응·필요 시험을 APPLIED/COMPANY_MAP에 추적해라.
기준이 불명확하면 UNKNOWN으로 남겨라. 조사만 수행하고 제품 적용, 완전 반영
기준 전진이나 적용 상태 변경은 하지 마라. 실제 회사 적용 여부를 보고해라.
```

## PORT-007 · BSP 플러그인 연동

[PORT-007](PORT-007.md)은 계획·초안이며 적용 준비가 되지 않았다. 원본 참조는 `476d95f08169d4a4fbb4a999a94d417d9e59cef3`이다. 최초 설계는 DESIGN_ONLY / IMPLEMENTATION_NOT_STARTED였으며 회사 인수는 NOT_RUN이다.

후속 로컬 구현과 모의 검증은 [실행 기록](../testing/runs/20261107-bsp-upgrade-integration.md)에 있다. 대상 구현 커밋은 `1a18ea6fab8b1caead3935ce70cb1e30153d631b`이며 최종 패키지는 로컬 검증되었다. 실제 Linux 설치·복원과 회사 인수는 남아 있다.

## PORT-008 · 편집 가능한 Windows Runner

[PORT-008](PORT-008.md)의 원본 기준은 `0178d045db16526560a155f05693c1f2dc0bbb47`이다.

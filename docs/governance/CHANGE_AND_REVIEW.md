# 변경·검토·회귀 방지 절차

## 변경 단위

각 변경은 요구사항 ID → 설계 절 → 코드 경로 → 시험 ID → 실행 기록으로 추적한다. 변경 전 현재 diff와 최신 정상 기준을 확인한다. “이전 버전이 단순하다”는 이유로 현재 수정 전체를 되돌리지 않는다.

| 변경 종류 | 함께 갱신할 문서·검증 |
|---|---|
| 운영 정책·범위 | 요구사항, D/ADR, 흐름/UI, 관련 시험·계획. 새 사용자 판단 필요 여부 기록 |
| 상태·게이트·데이터 | 상태/데이터/API, migration, 실패/복구/역순/무효화 시험 |
| UI | 화면 명세, 접근성·표시/버튼 조건 시험 |
| 외부 어댑터 | 기능 지원표, 실제 호출 근거, mock/live 구분, 계약 시험 |
| 오케스트레이터·모듈 보고 계약 | 두 전용 명세의 버전/지원 범위, 역할·구조·상태·데이터/API/UI, 구현/이전 계획, RQ/T·현재 결과. 제안 적용과 실행 사실을 분리하고 기존 v1 이력 보존 |
| 결함 수정 | 회귀 기록, 실패 재현 시험, 수정 revision, 재시험 실행 |
| 문서만 수정 | 링크·ID·정책 일관성 검사. 제품 시험을 실행한 것으로 표시하지 않음 |

## 검토 기록 템플릿

```text
review_id:
reviewer / tool / model:
reviewed_revision / scope:
status: NOT_REVIEWED | CHANGES_REQUESTED | APPROVED
findings: [severity, requirement_id, location, trigger, impact, suggested_fix, test_id]
tests_actually_run / run_ids:
unverified_integrations:
follow_up_owner:
```

Claude 검토가 요청되면 이 형식으로 작성한다. “Claude가 검토할 수 있도록 문서를 썼다”와 “Claude가 검토했다”를 구분한다. 변경 후 이전 revision 승인만으로 새 revision을 승인하지 않는다.

## 롤백과 재발 방지

1. 되돌릴 필요와 대상 커밋, 사라지는 수정, DB/설정 호환성, 영향 시험을 확인한다.
2. 정상 기준이 없으면 임의 버전을 정상으로 지정하지 않는다. 작업 변경을 보존하고 별도 수정으로 원인을 해결한다.
3. 되돌림이 필요하면 역변경을 추적 가능한 커밋으로 남기고 관련 회귀 시험을 다시 실행한다. 기존 FAIL·수정 이력은 유지한다.
4. 테스트 삭제/기대값 완화가 필요하면 요구사항 변경 근거와 검토를 기록한다. 코드를 통과시키기 위한 임의 완화는 금지한다.
5. 코드 보호는 문서만으로 보장되지 않는다. 구현 시 CI에 핵심 게이트·중복 실행·무효화 회귀 시험을 연결하고 저장소의 필수 검사 설정 가능 여부를 확인한다. 현재 CI/브랜치 보호는 미구현이다.

## 계약 문서의 단일 관리

[오케스트레이터 명세](../design/ORCHESTRATOR_SPEC.md)는 조정 입력·출력·권한, [모듈 보고 계약](../design/AGENT_STATUS_CONTRACT.md)은 각 agent의 보고 필드를 소유한다. 역할/구조/API 문서에는 의미와 연결만 적고 필드 목록을 복제하지 않는다. 현재 계약과 미구현 목표 계약을 같은 예시로 혼용하지 않는다. 사용 중인 문서는 함께 갱신하되 과거 testing/runs·FAIL 기록은 수정하지 않고 새 문서 검사 실행을 추가한다.

수동 Claude 패키지는 agent 정의/사용 안내/예시/검증 코드/패키지 시험을 함께 갱신한다. 내보낸 기준 문서와 manifest는 해당 배포 시점 사본이므로 원문 변경 시 새 디렉터리에 다시 내보낸다. 모델을 호출하지 않은 자동 시험을 Claude 검토 완료로 기록하지 않는다.

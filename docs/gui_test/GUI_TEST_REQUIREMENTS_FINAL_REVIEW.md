# GUI Test — 구현 요구사항 (승인된 설계)

- 기준일: 2026-10-25
- 상태: **요구사항·설계 확정 / 구현 미착수**
- 적용 범위: **공통 Test Core + Windows 단독 웹 실행**. BSP Dashboard 연결은 [`DASHBOARD_GUI_TEST_INTEGRATION.md`](DASHBOARD_GUI_TEST_INTEGRATION.md)를 따른다.
- 기준: 대화에서 합의한 기능 요구사항을 통합했다. 중복 설명·선택 과정·변경 이력은 제외했다.
- 표기: `[채택 설계]`은 사용자가 승인한 권장 구현 기준, `[실환경 확인]`은 실제 명령·회사 API 등 현장에서 확인할 기술 계약을 뜻한다.

## 적용 상태 및 구현 경계

- **확정:** 사용자 결정 1~67 및 이후 승인한 폴더 분리·Mock 우선·기존 Dashboard 최소 변경 기준을 적용한다.
- **COM 인자 전달:** **기존 TC 실행 명령은 COM 포트를 인자로 전달하는 기능을 이미 지원한다(사용자 확인).** Single 실행은 선택한 COM A, Dual 실행은 선택한 COM A/B의 값을 **기존 명령의 COM 인자 슬롯**에 적용한다. COM 인자를 받을 수 있는지 여부는 더 이상 미정이 아니다.
- **추후 정의:** 기존 명령의 **정확한 실행 파일·옵션명·인자 순서·호출 주체·프로세스 실행 호스트**는 실제 성공한 Single/Dual 명령을 받아 정의한다. 이 값이 없어도 Core/UI/Demo 개발은 가능하지만 **실제 하드웨어 TC 실행 성공을 주장하지 않는다**.
- **구현 상태:** 요구사항 문서만 갱신. 공개 GitHub 소스/회사 코드/실제 보드에 대한 구현이나 실행 검증은 수행하지 않았다.

## 1. 목표와 운영 모드

| 모드 | GUI / Run 관리 | TC 실행 | 보드·COM 조회 | 결과 보관 및 연동 |
|---|---|---|---|---|
| Dashboard 통합 | 기존 React UI + Linux FastAPI 내부 `TestRun Manager` | 기존 Linux Python TC 경로 | RBC → RBM 우선, 장애 시 수동 | Linux 관리, 검증된 결과만 BSP `device_test` 반영 |
| Windows 단독 | Windows 로컬 웹 GUI + **Windows Local TestRunner** | 기존 Linux Python TC 경로 | Windows 실제 COM 포트 자동 열거 | Windows 로컬 저장. **Dashboard/RBM 불필요, 결과 공유·동기화 없음** |

- 두 모드는 **동일한 TC 탐색·실행·판정·리포트 계약**을 재사용하지만 **Run/제어권/저장소는 분리**한다. 서로 다른 모드의 Run을 실시간 공유하거나 제어권을 이전하지 않는다.
- Windows 단독은 *Dashboard 독립*이지 *Linux TC 서버 독립*이 아니다. 설정에는 Linux 호스트·TC 경로·기존 실행 명령·접근 권한과 Windows COM 연결 프로파일이 필요하다.
- 기존의 성공한 **Windows → Linux Python TC 호출 경로**를 `TestRunner Adapter`로 감싼다. TC 코드·기존 실행 명령의 일반 인자는 변경하지 않고, **이미 지원되는 COM 인자로 선택한 COM A 또는 COM A/B 값을 전달**한다. 구체 명령 옵션·순서는 실제 명령 제공 후 매핑한다. 새 Linux TC 실행 API, 새 RBC 기능 또는 강제 TC 포팅은 기본 요건이 아니다.
- GUI 브라우저 종료/새로고침은 Run 종료가 아니다. 실행 관리자/프로세스의 생존 여부를 확인해 재접속 시 상태·로그·예약을 복원한다.

| IO-05 | 동일 보드임이 신뢰성 있게 확인되고 COM이 변경되면 새 매핑을 **제안**하되 사용자 확인 후 적용한다. 식별 불가능·중복이면 수동 재선택하게 한다. 실행 중인 Run의 매핑은 자동 변경하지 않는다. |

| IO-07 | 동일 관리 영역에서 보드·COM 예약 충돌 시 실행 대기/차단한다. 실제 COM 핸들을 Runner가 계속 점유한다고 가정하지 않는다. TC가 포트를 열고 닫는 기존 방식을 유지한다. |
| IO-08 | 프로세스의 **실제 종료를 확인한 뒤** 예약을 해제한다. 종료/연결 상태가 불명확하면 `UNKNOWN`으로 보존하며 임의 만료·중복 실행을 금지한다. |

## 4. 실행·제어·복구

| ID | 구현 요구사항 |
|---|---|
| RUN-01 | Run 생성 시 `run_id`, TC 목록·순서, 소스 커밋, Suite/메타데이터 버전, 연결 프로파일 스냅샷, 보드/COM, 타임아웃을 고정한다. TC를 **하나씩 순차 실행**한다. 각 Attempt에는 COM 값과 실제 적용한 **명령 인자 배열(비밀정보 제외)**을 기록한다. |
| RUN-02 | 시작 전 Preflight: Linux/TC 경로·명령·의존 환경, 각 보드 식별과 COM 매핑, Single/Dual 구성, 예약 가능성, 관련 파일을 확인한다. 실패 시 원인을 표시하고 실행을 차단한다. |
| RUN-03 | **각 TC 시작 직전** 현재 포트/보드 유효성을 재확인한다. 기존 Python TC가 자체 Setup/Teardown을 수행하며 GUI는 별도 초기화·강제 리셋을 하지 않는다. **선택된 COM 값은 그 TC의 기존 명령 인자로 전달**하되 Runner의 프로세스 실행 전에 매핑을 검증한다. |
| RUN-04 | TC가 검증 **FAIL**이면 자동 재시도 없이 기록하고 다음 TC를 실행한다. 선행 TC 실패라도 후속 TC를 계속 실행하며 `선행 조건 미충족` 경고를 남긴다. 단, 실행 안전 조건 미충족 시 해당 TC 시작은 차단한다. |
| RUN-05 | COM/Linux 환경 오류 시 현재 Attempt의 종료/상태를 확인하고 Run을 **일시 정지**한다. 연결 복구는 자동 감지·점검하되 사용자가 `[재개]`를 눌러야 **오류 TC부터 새 Attempt**로 이어서 실행한다. 앞선 PASS와 실패 이력은 유지한다. |
| RUN-06 | 공통 기본 타임아웃 + TC별 타임아웃을 지원한다. 초과 시 종료 요청 → 실제 종료 확인 → `TIMEOUT` 기록 및 일시 정지. 종료 확인 불가 시 `UNKNOWN`, 중복 실행 금지. |
| RUN-07 | 사용자의 `[일시 정지]`는 **현재 TC 종료 후** 적용한다. `[테스트 중단]`은 실행 중 프로세스에 종료 요청하고, 실제 종료 확인 뒤 `CANCELLED` 및 Run 종료로 처리한다. |
| RUN-08 | 브라우저 종료/새로고침·일시적 UI 연결 손실은 Run에 영향 주지 않는다. 실행 관리자 자체 장애 시 실행 프로세스를 조회해 복구하고, 조회 불명은 `UNKNOWN` 상태로 둔다. |
| RUN-09 | 한 **모드 내부의 동일 Run**은 여러 브라우저 세션에서 조회할 수 있으나 제어권은 1개 세션만 보유한다. 접속 중인 제어자는 이전을 승인하고, 세션 만료 시에는 실행 상태 조회 후 명시적으로 인수한다. 권한 이전으로 TC/보드 예약을 변경하지 않는다. |
| RUN-10 | 1차는 제한된 단일 사용자·사내 접속/SSH 환경을 전제한다. 세션 제어권은 사용자 신원 인증을 대체하지 않는다. 향후 타인 보드 공유와 사용자별 인증/권한은 확장 범위로 둔다. |
| RUN-11 | 완료된 Run의 판정은 **불변**이다. FAIL TC의 사후 재검증은 **새 Run**으로 수행한다. 이전 PASS 계승은 소스·이미지(해당 시)·시험 계획·보드·TC·파싱 규칙 등 유효 기준이 일치할 때만 허용하며 원본 참조를 남긴다. |

### 4.1 표준 실행 흐름

`TC·Suite 선택 → Git/COM·보드 설정 고정 → Preflight·보드 전체 예약 → TC 순차 실행 → Attempt 판정 → Run 집계·리포트 → 예약 해제`

- **PASS/FAIL:** 결과 저장 후 다음 TC. **환경 ERROR/Timeout:** 종료 확인 → PAUSED → 자동 연결 점검 → **사용자 재개** → 문제 TC의 새 Attempt. **사용자 일시 정지:** 현재 TC 종료 후 PAUSED. **중단:** 종료 요청·확인 후 CANCELLED.
- Run 완료 후 재검증은 원본 Run을 변경하지 않고 새 Run을 생성한다. Dashboard 모드에서만 별도 연동 문서의 최종 검증·동기화를 수행한다.

### 4.2 상태 및 최종 판정

- TC 상태: `PENDING / RUNNING / PASS / FAIL / ERROR / TIMEOUT / SKIPPED / CANCELLED / UNKNOWN`.
- Run 제어 상태: `QUEUED / RUNNING / PAUSE_REQUESTED / PAUSED / CANCEL_REQUESTED / CANCELLED / COMPLETED / UNKNOWN`. 최종 **판정**은 제어 상태와 별도 필드에 둔다.
- 최종 판정: **PASS** = 대상 TC 전부 유효 PASS; **FAIL** = 전부 유효 PASS/FAIL로 판정됐고 1개 이상 FAIL; **INCOMPLETE** = 미해결 ERROR·TIMEOUT·UNKNOWN·SKIPPED·미실행·취소가 하나라도 있음.
- 진행률 = `(현재 유효한 PASS 또는 FAIL TC 개수) / 전체 대상 TC 개수 × 100`. **PASS 비율과 다름**. 재시도/기준 무효화로 감소할 수 있다.
- 환경 오류 복구 전 `ERROR`·`TIMEOUT` Attempt 이력은 보존하되, 그 TC가 **새 Attempt에서 정상 판정되면** 해당 Run은 최종 판정을 계산할 수 있다.

## 5. TC 결과 판정

| ID | 구현 요구사항 |
|---|---|
| RES-01 | 기존 stdout/stderr/결과 파일에서 **`Test Result: PASS` 또는 `Test Result: FAIL`** 문구를 판정 근거로 사용한다. 임의의 `PASS` 단어를 검색해 판정하지 않는다. |
| RES-02 | 기본적으로 한 TC Attempt에 **유효한 최종 판정 문구 정확히 1개**를 요구한다. 누락·중복·모순은 `ERROR`. 검증된 복수 출력 TC만 버전 관리된 메타데이터에 파싱 예외를 정의한다. |
| RES-03 | 프로세스 종료가 확인된 뒤 판정 문구와 **종료 코드**를 함께 확인한다. 정상 종료 코드 0이 기본이고, 비영 정상 종료 예외는 TC별 메타데이터에 명시한다. 모순되면 `ERROR`, 모호한 PASS 추정 금지. |
| RES-04 | TC·Attempt별 원본 stdout/stderr, 종료 코드, 적용 파싱 규칙/버전, 오류·Timeout 원인과 결정 근거를 저장한다. 출력 도중 PASS가 보여도 종료 전에는 확정하지 않는다. |
| RES-05 | stdout/stderr는 가능한 범위에서 **실시간 표시**한다. 스트리밍을 지원하지 않는 기존 호출 경로라면 수집 가능한 시점부터 표시하되, 그 제한을 명시한다. |

## 7. 안전·접근 경계

- `[채택 설계]` Windows 로컬 웹/API는 기본적으로 **loopback(127.0.0.1)만 수신**한다. Dashboard는 회사판의 기존 Host/Origin 및 변경 요청 보호를 유지하며, 외부 공개가 필요하면 사내 승인된 인증·TLS를 먼저 적용한다.
- `[채택 설계]` TC 실행은 **등록된 Python/스크립트·허용 경로**에 한정하고, 사용자 입력 TC 이름·COM 포트를 그대로 임의 셸 명령으로 연결하지 않는다. 기존 실행 명령은 안전한 인자 전달을 적용한다.
- `[채택 설계]` SSH 자격증명·사내 토큰을 설정 파일, 실행 로그, 리포트에 포함하지 않는다. 로그와 산출물에는 접근 경계·크기 제한·민감정보 마스킹을 적용한다.

## 8. 데모 모드

- 실제 **RBM / Windows COM / Linux TC 실행 / Dashboard 동기화**의 접점을 모두 Mock으로 대체한다. 실제 장비·운영 DB·운영 API를 수정하지 않는 **완전 격리 환경**이다.
- 실제 Core 상태 전이·판정·예약·리포트 로직을 동일하게 사용하되 Mock 어댑터와 별도 데모 저장소/실행 식별자를 사용한다.
- 기본 시나리오: Single/Dual 정상 완료, 일부 FAIL 후 계속 실행, COM 끊김과 사용자 재개, Timeout, 수동 일시 정지·중단, 보드 예약 충돌, Dashboard 동기화 실패·재시도, Git/Job 기준 변경.
- 데모 컨트롤러: 자동 시나리오 실행, 속도 조절, 원하는 시점의 오류 주입·복구·일시 정지·사용자 재개. **실제 `device_test`에는 절대 반영하지 않는다.**

## 10. 최종 정합성 검토 및 남은 확인 사항

### 10.1 충돌 해결 — 적용할 최종 규칙

1. **실행 모드 분리**: Windows 단독 Run은 로컬 관리/보관, Dashboard와 무관. **같은 Run의 공동 조회·제어권 이전**은 **동일 모드 안의 복수 GUI 세션**에 한정한다.
2. **FAIL과 실행 불능 구분**: 일반 FAIL 또는 선행 TC FAIL은 다음 TC 실행. 사전 점검 실패·장치 안전 문제·환경 ERROR/Timeout은 실행/진행 보류. GUI는 TC Setup/Teardown을 강제로 수행하지 않는다.
3. **전체 판정과 모듈 판정 분리**: 미매핑 TC도 전체 Run 판정에 포함한다. 미매핑 TC의 ERROR 등으로 **Run 전체가 INCOMPLETE면 Dashboard 전체 자동 반영 보류**. 모듈별 판정은 매핑된 필수 TC만 사용한다.
4. **재검증과 복구 구분**: 완료 Run의 사후 재검증은 **새 Run**, 미완료 Run의 환경 복구는 **같은 Run의 새 Attempt**다.

### 10.2 승인된 구현 기본값

- `[채택 설계]` Windows Local TestRunner는 로컬 웹 UI와 **독립적으로 생존하는 백그라운드 실행 관리자**를 둔다. 로컬 SQLite 등 영속 저장을 사용하고 브라우저 생명주기와 분리한다. 저장 기술 자체는 강제하지 않는다.
- `[채택 설계]` 사용자 명령은 `command_id`/기대 상태 버전으로 멱등 처리하고 Run·Attempt·예약 변경을 원자적으로 기록한다. 종료 불명 프로세스에는 자동 재시도를 하지 않는다.
- `[채택 설계]` **동일 물리 Windows 호스트에서 통합/단독 모드가 동시에 실행되면** 각각의 관리자만으로는 보드 배타 예약을 보장할 수 없다. 공통 잠금/점유 확인이 검증되지 않은 1차 운영에서는 **동일 호스트의 두 모드 동시 하드웨어 실행을 금지**한다. 이 제약을 해제하려면 호스트 단위 상호 배타 시험을 통과해야 한다.
- `[채택 설계]` 타임아웃 값·로그 보존 일수/용량·동기화 재시도 횟수는 **임의 숫자를 채우지 않고 환경 설정에 필수 운영값**으로 정의한다.

### 10.3 실제 연동·하드웨어 시험 전에 확인할 인터페이스

1. Windows에서 성공한 TC **실제 명령 예시(Single/Dual)**의 COM 옵션명·인자 순서·실행 호스트, 취소·로그 수집 가능 여부. **COM을 명령 인자로 전달한다는 사실은 확정**이며, 문법은 후속 정의한다.
2. Linux TC의 탐색 단위·폴더 구조, `Test Result:` 출력 예시, 정상 PASS/FAIL 종료 코드, Python 의존성, 타임아웃 분포.
3. Windows의 보드 고유 식별 방법, COM 변동 시 일치 검증, 다른 프로세스와의 장치 점유/충돌 제약.
4. 회사 보안 정책상 로컬 웹 서버·실행 관리자·SSH 인증·로컬 로그/증빙 저장 및 배포 허용 범위.
5. Dashboard 기능과 인터페이스는 별도 연동 문서의 **실제 회사판 Delta**를 검증한다.

> 이 문서는 **구현 명세 검토안**이다. `[실환경 확인]` 항목의 실제 값·지원 능력을 확인하기 전에는 해당 통합 기능이 이미 동작한다고 표시하지 않는다.
